erkamyaman/rust-anything · crates.io / npm 1.5.1（main には未リリースの変更あり） · Rust 製 CLI と MCP サーバー · 対象 TypeScript/JavaScript、Python、C、Go、Ruby、Java（PHP と C# はプレビュー） · MIT

01 — 元のコードの振る舞いを記録し、Rust の移植をそれと照合する

PROFILE → PLAN → BRIDGE → RECORD → PORT → DIFF → BENCH → SHADOW → GATE

コードを翻訳するツールではない。Rust を書くのはエージェントか人で、rust-anything は「どこを移すか」「元と同じ振る舞いか」「出荷してよいか」を判定する。

rust-anything は、既存のアプリを 1 単位（unit）ずつ Rust に移すための CLI です。元のコードを生成した境界値入力で実行して結果を cases.jsonl に記録し、Rust 側の実装をその記録と 1 件ずつ照合します。呼び出し側は元の API のまま Rust を呼べるよう、言語ごとのバインディング（ブリッジ）も生成します。

使い方は 2 通りあります。遅い部分だけを移す（ホットパスの移植）か、CLI・HTTP サーバー・ライブラリをまるごと純粋な Rust にする（アプリ全体の移植）かです。どちらも同じループを単位ごとに回し、gate が通るまで完了とみなしません。

WHOLE APP

アプリをまるごと移す

アプリの入出力を外側から記録し、入口を Rust の「フロントドア」に置き換えてから、単位ごとに Rust へ切り替えます。最後に app lift で元のコードへのフォールバックを外します。

AGENT

エージェントから使う

rust-anything setup が Claude Code・Codex・Cursor・Gemini CLI に MCP サーバーとワークフロー用スキルを登録します。各ステップは MCP ツールとして呼べます。

02 — 移植のループ

1 単位の移植は次の流れで進みます。元のコードが常に正（source of truth）で、記録したすべてのケースが一致し、gate が通るまで出荷しません。呼び出し側は最初から最後まで元の API を使い続けます。

README「The loop」より
コマンド何をするか
profile <repo> -- node bench.mjs実際のワークロードを言語ごとの標準プロファイラー（node --cpu-prof、cProfile、go test の pprof、JFR、Ruby のトレーサー）で走らせ、関数を包含時間順に並べ、呼び出し元とバッチ化すべきループを示す。numba・Cython・JAX でコンパイル済みのコードは移しても速くならないと警告する
analyze <repo>単位の一覧、移植順序（ウェーブ）、file:line つきのリスク、単位ごとのブリッジ、依存パッケージに対応するクレート、最初に移すべき単位（start_here）。--json はスキーマ rust-anything/analyze@1
bridge <repo> <unit>バインディング（lib.rs と元の言語が読み込むラッパー）と移植用のスタブ port.rs を持つクレートを作る。空でないフォルダーには書かない
record <crate>元のコードを生成した境界値入力（非 ASCII、絵文字、-0、NaN、浮動小数を期待する箇所への整数など）と、引数ごとの意味上の罠（文字列長と大小文字、符号付き除算、オーバーフロー、浮動小数の表示、マップと並び順）で実行し、cases.jsonl に保存。--from-tests -- npx jest（または -- pytest）で元のテストスイートが行う呼び出しも記録する
build <crate>Rust 側をビルド（.node、wasm パッケージ、Python 拡張、共有ライブラリ）
diff <crate>記録したケースを、元の呼び出し側と同じ経路で Rust に流し、不一致を列挙
bench <crate>記録したケースで元と Rust をブリッジ込みで計測し、「出荷」「遅い関数は残す」「もっと大きな単位を移す」などの判定を出す（1.1x 以上で速い、0.9x 未満で遅い）
shadow <crate>両方を実行して元の結果を返し、不一致だけを報告するドロップイン。RUST_ANYTHING_MODE=old|shadow|new で切り替え
gate <crate>fmt、clippy -D warnings、テスト、unsafe の監査、未移植の関数がないこと、元のエラー経路ごとに失敗ケースが記録されていること、元がエラーを返す箇所に unwrap/expect/panic! がないこと、ビルド、API、振る舞い、コード量（元の 3 倍＋50 行まで）
記録は直さない：SKILL.md は「不一致は振る舞いの違いであり、直すのは移植側で、記録ではない」としています。意図して違う結果にするケースは known-diffs.jsonl に理由とともに書き、diff と gate はその結果のときだけ合格として数えます（CHANGELOG の Unreleased 項目）。

record は元の単位のファイルの指紋（recorded-from.json）も保存します。後で元のコードが変わると diff が警告し、gate は再記録するまで失敗します。

03 — 言語ごとの単位とブリッジ

手順は全言語で共通で、違うのはブリッジだけです。言語は go.mod、pom.xml、pyproject.toml、Gemfile、package.json などから判定され、--lang で上書きできます。型は各言語のソース（TS の型、Python の型ヒント、C・Go・Java の宣言、Ruby の YARD タグ）から取り、型のない引数でも数値として使われていれば数値と推定します。

元のリポジトリには何も書き込みません。記録と照合は元の言語の実行環境で、生成したドライバーを使って行います（DECISIONS.md の M4）。エラーの比較は例外の型（Python、Ruby、Java）、Go の error はメッセージ、Go の panic は panic であることで行い、移植側は Err("TypeName: message") を返します。C で入力が契約外になりクラッシュしたケースは crash: <signal> と記録され、移植側の結果は何でも合格になります。

04 — アプリ全体を純粋な Rust にする

目標は、元のアプリと同じ振る舞いをする純粋な Rust のアプリで、元のコードは参照用に残します。record と diff が 1 単位を検証するのに対し、app record と app replay はアプリを外側から（ブラックボックスとして）検証します。

  1. 計画する

    rust-anything analyze . --whole-app

    アプリの形（CLI・サーバー・ライブラリ）と入口、import か宣言されているすべての外部依存と対応するクレート、互いに import し合う単位をまとめた移植順序、推奨回答つきの番号つき決定事項を出します。

  2. アプリの振る舞いを外から記録する

    rust-anything app record . -- python3 cli.py   # 元のアプリを起動するコマンド
rust-anything app replay .                     # 元のアプリ自身が 100% 合格すること

    入力は、アプリの Markdown やシェルファイルにある $ mytool ... の例、--inputs の JSONL、そこから派生させた罠（非 ASCII、負の除算、オーバーフロー、ファイルなしなど）です。各ケースを 2 回実行し、2 回で違った部分は [..] のワイルドカードにします。ケースは trycmd 形式で rust/app-cases/ に保存され、手で読んで編集できます。

  3. 入口を Rust にする

    rust-anything app front-door .                   # rust/app: 全コマンドを元のアプリに転送
rust-anything app wire . textkit --command upper # textkit-rs が gate を通った後

    app front-door は記録したケースのコマンドとフラグを clap で受け付ける Rust のバイナリ rust/app を作り、最初は全コマンドを同じ argv・stdin・環境変数で元のアプリに渡します。直後の replay は「100% 合格、フォールバック率 100%」です。app wire は単位のクレートに gate をかけてから rust/app に組み込み、指定したコマンドを Rust に振り向けます。RUST_ANYTHING_UNIT_<NAME>=original で単位ごとに元へ戻せます。

  4. 純粋な Rust にする

    rust-anything app lift .

    フォールバック率 0 かつ全単位が gate を通るまでは拒否し、何が阻んでいるかを示します。条件を満たすと、まずコピー上でフォールバック経路と切り替えスイッチを外し、各単位をバインディングなしの普通のライブラリにし、cargo test でケースを走らせる rust/app/tests/app_cases.rs を追加します。チェックリスト（fmt、clippy、テスト、rust/DECISIONS.md の全ターゲットのビルド、純粋なバイナリでの replay）がすべて通ったときだけ書き戻します。元のコードには触れません。

サーバーとライブラリ

HTTP SERVER

--http

app record . --http -- node server.js で、ドキュメント中の curl 行、--inputs、パスやクエリ・本文の罠からリクエストを作ります。フロントドアは axum のサーバーで、どの単位も答えないルートを元のサーバーにプロキシします。app wire . api --route 'GET /users/{id}' でルート単位に切り替えます。

LIBRARY

公開 API が入口

プロセスを再生できないので、各単位の記録ケースが証拠になります。rust/app は公開 API を持つライブラリクレートになり、app wire は元のパッケージが単位の代わりに import するシャドウを書きます。フォールバック率は Rust がまだ答えていない公開エクスポートの割合です。

app replay のレポート rust/app-cases/replay-report.md には時刻や一時パスが入らないため、2 回の replay は同じファイルになります。README はこれをコミットし、CI で git diff --exit-code にかける運用を勧めています。合格状況が良くも悪くも変われば CI が落ちます。

エージェント向けの手順（whole-app スキル）

スキルの whole-app.md は、Matt Pocock の skills から取り入れた次の進め方をエージェントに指示します。

  • Grilling：移植が依存する決定事項を、推奨回答つきの質問で数回に分けて利用者に聞き、決まったものを ADR として rust/DECISIONS.md に書く。元の用語と Rust 側の名前の対応は rust/GLOSSARY.md。
  • Research：バックグラウンドのエージェントが依存ごとに一次資料を読み、見つけた罠を rust/research/<topic>.md に書く。
  • セッションをまたぐ：rust/MAP.md に全単位の状態を置き、セッションは着手前に 1 単位を確保し、区切りごとに rust/HANDOFF.md を残す。同じウェーブの単位はサブエージェントで並行して移せる。
  • Cutover：デプロイ、DNS、シークレットなど利用者にしかできない手順は、各段階に戻し方を持つ対話式スクリプト rust/cutover.sh にする。

05 — ホットパス：1 回ずつ呼ぶのでなく、ループごと移す

小さな関数を 1 件ずつ Rust で呼ぶと、呼ぶたびにブリッジの費用がかかり、V8・JVM・Go が数ナノ秒で済ませる処理に負けます。README と DECISIONS.md はこれを前提にしていて、勝つのは「データを Rust 側に置いたまま、ループごと移す」場合です。

rust-anything profile ../x18n -- node --experimental-strip-types $PWD/demo/x18n-search/search.ts .
# -> fuzzyScore: 実行時間の 4 分の 1。matched がキーごとに呼んでいる。バッチ化せよ
rust-anything bridge ../x18n packages/core/src/fuzzy.ts --batch fuzzyScore:text
const search = new FuzzyScoreBatch(keys)   // 1 回だけ
const order = search.rank(query, 0)        // キー入力ごと。インデックスを良い順に返す

--batch fn:param は、param の値の集合を 1 回だけ Rust に渡して保持するクラスを生成します。run は全件の結果を 1 つの配列で返し、rank は閾値以上の項目のインデックスを良い順に返します。全コアで実行され、エラーは元と同じです。port.rs に FuzzyScoreIndex のような構造体を書くと、小文字化や文字マスクなど項目ごとの前処理を 1 回で済ませられます。

記録したケースが捕まえた違い

README と docs/real-world.md には、単純なテストは通ったが diff で落ちた例が挙がっています。

198/200 cases match
- fuzzyScore("b😀", "a😀b😀c"): expected {"ok":1997}, got {"ok":1998}
  • JS の indexOf は UTF-16 のコード単位で数えるため、絵文字は 2 位置になる。Rust の char で数えた最初の移植は不一致になり、生成された utf16 ヘルパーを使って 2000/2000 になった。
  • u フラグなしの /.../i は ASCII しか大文字小文字を同一視しないが、Rust の regex は Unicode で同一視する。"1 ſ"（long s）やケルビン記号が秒として解釈されるところだった（vercel/ms）。
  • Math.round は .5 を正の方向に丸める（-2.5 は -2）が、Rust の round は 0 から離れる方向に丸める。
  • Fuse の Bitap は 32 ビットの JS 整数で動き、1 << 31 は負になる。移植はその値を JS と同じに保つ。

移植の過程でツール自身の不具合も見つかり、修正されています（serde_json 経由で浮動小数が 1 ULP ずれる、C の記録中のクラッシュなど）。

07 — analyze と bridge が決めること

analyze の単位と順序

  • 単位：ソースファイルのフォルダー、またはパッケージのソースルート直下のファイル。node_modules、ビルド出力、fixtures、playground、ツール設定は除外。
  • ウェーブ：単位の import 先は前のウェーブに入る。import が循環する単位はまとめて移す。
  • ブリッジ：単位か、その import 先が Node を必要とするなら napi-rs、移植可能なコードは wasm-bindgen（ブラウザで動き続ける必要があるため）、UI とエディターのコードは JS に残す。
  • readiness と priority：readiness は安全さ（100 からリスク・規模・被依存数を引き、テストがあれば加点）。priority は readiness と価値（ループと文字列処理の密度、テスト、80〜600 行の規模）の半々。
TS のリスク分類（README「What analyze looks at」より）。DECISIONS.md の A6 は、これらがヒューリスティックで誤検知を含むと明記している

bridge が元の言語に残すもの

ブリッジを越えられないエクスポートは理由つきで元の言語に残し、シャドウモジュールが元を再エクスポートします。TS では、関数を受け取る・返す関数、ジェネレーターとイテレーター、RegExp、instanceof の判定、ジェネリクス、型に関数を含む値（import・再エクスポート・extends をたどって判定）が対象です。--keep "name: reason" で追加できます。x18n の core では 55 エクスポートのうち 26 がこれに該当しました（DECISIONS.md の X1）。

JSON で表せない undefined、NaN、Infinity、-0、孤立サロゲートは、{"$undefined": true} などのマーカーで運びます。構造化された値は通常、生成したバイナリワイヤーで渡し、JSON はワイヤーが扱えない形のときだけ使います。

08 — 検出できないこと

合格が意味するのは「記録されたすべてのケースで Rust が一致した」ことだけです。README は書き直しで問題になる箇所の多くが記録の外にあるとして、次を挙げています。

README「What it can't catch」より
項目内容と対策
誰も記録しなかった入力生成ケース、罠、元のテストスイート、--inputs が上限。本番のサンプルやバグ報告など実際の入力を足す
その後変わった元のコード指紋（recorded-from.json）で検出し、gate は再記録まで失敗する
正規表現regex クレートは先読みと後方参照を持たず、コンパイルできるパターンでも非 ASCII の \w、\b、\d、大文字小文字の扱いが JS・Python・Java と違うことがある。record は正規表現を使うファイルに罠（トルコ語の ı、ケルビン記号、ゼロ幅接合子など）を足すが、実際のパターンを実際のテキストでも試す
実行ごとに変わるもの2 回の実行で違った値はワイルドカード、行の順序の違いは順不同で比較、行数の違いは ...（何にでも一致）になる。ハッシュ順や並行処理の違いは移植で本当に変わりうるため、record が列挙する各項目を確認する
浮動小数数値の文字列化（1e21、-0、桁数）は言語ごとに違い、完全一致が必要。--float-tolerance が許すのは丸め誤差だけ
出力に出ないもの時間、メモリ、負荷時の並行性、stdout・stderr・終了コード・書いたファイル・HTTP 応答以外の副作用（ネットワーク呼び出し、DB、シグナル）は比較しない
他のプラットフォーム記録が示すのは記録したマシンでの振る舞い。型のサイズ・エンディアン・コンパイラに依存する C はターゲットで違いうるため、analyze はハードウェア寄りの C を C に残す
対象外：APK、JAR、.exe などのバイナリしかないアプリは移植できません（ソースを解析して関数単位で記録するため）。Kotlin と Swift は未対応です。Electron アプリはメインプロセスのロジックを移し、レンダラーはそのまま残します。

09 — 導入とエージェント連携

cargo install rust-anything   # crates.io から
rust-anything setup           # Claude Code、Codex、Cursor、Gemini CLI に登録

Rust のツールチェーンがなければ、GitHub のリリースに macOS・Linux・Windows のビルド済みバイナリがあり、JavaScript のプロジェクトでは npm install -g rust-anything でも同じバイナリが入ります。Claude Code ではプラグインとしても入れられます（CLI は別途 PATH に必要）。

/plugin install rust-anything --marketplace erkamyaman/rust-anything
rust-anything setup が追加するもの（README「Works with」より）
エージェント追加先
Claude CodeMCP サーバーを ~/.claude.json、スキルを ~/.claude/skills/
CodexMCP サーバーを ~/.codex/config.toml、スキルを ~/.codex/skills/
CursorMCP サーバーを ~/.cursor/mcp.json
Gemini CLIMCP サーバーを ~/.gemini/settings.json
その他の MCP クライアントrust-anything mcp を stdio サーバーとして手で追加

setup は既存ファイルを変える前に <file>.rust-anything.bak を残し、他の設定とキーの順序を保ち、パースできないファイルは書き換えません。再実行しても安全で、setup --remove で rust-anything の項目だけを外せます。

MCP ツールは profile、analyze、bridge、refresh、record、build、diff、bench、shadow、gate と、アプリ全体用の app_record、app_replay、app_front_door、app_wire、app_lift です。スキルはエージェントに、計画（analyze）を示した後は利用者が計画と最初の単位を承認するまで止まるよう指示しています。

実行に必要なもの

record、diff、bench は元のコードをその実行環境で動かすため、Node 22.6 以上（.ts を直接実行）、Python 3.9 以上（Python と C）、Go 1.21 以上、Ruby 3 以上、JDK 17 以上が必要です。Node の profile は Node 24 以上、C には C コンパイラー、wasm のブリッジには wasm32-unknown-unknown ターゲットと、クレートと同じバージョンの wasm-bindgen-cli が要ります。Cargo.toml の rust-version は 1.97 です。

10 — 注意点

速くなるとは限らない

README の FAQ は「Rust が常に速いか」に No と答えています。x18n の core は全関数が正しく移せたうえで、JS から呼ぶと遅くなりました。bench は gate とは別のステップで、出荷前に測る前提です（DECISIONS.md の X5）。速度目的なら profile から始め、バッチで移せるループがあるかを先に確かめます。

合格は記録の範囲での一致

08 節のとおり、生成ケースと罠は実際の入力の代わりになりません。正規表現、浮動小数、ハッシュ順、外部への副作用を含むコードでは、本番の入力を --inputs で足し、shadow で本番トラフィックでも比べてから切り替えます。shadow は同期的な結果だけを比べ、引数を書き換える関数では 2 つ目の実装が書き換え後の入力で動く、という制限も DECISIONS.md に書かれています。

言語ごとの制限

  • C：スカラーと const char * の API だけがブリッジを越える。出力バッファや状態構造体、マクロで定義された関数は C に残る。
  • Go：メソッド、ジェネリクス、可変長引数、ポインター、インターフェイス、チャネルは Go に残る。
  • Ruby：モジュール関数のみ。クラスとブロックを取るメソッドは Ruby に残る。
  • Java：公開クラスの public static メソッドのみ。record は javac だけでコンパイルするため、Maven の依存が必要なコードはまだ記録できない。
  • PHP と C# はプレビューで、単位を Rust に移すブリッジはまだない。

その他

  • プロジェクトは新しく、最初のコミットは 2026-11-16、v1.5.1 は 2026-11-18 のリリースです。CHANGELOG の Unreleased にも変更が続いており、本ページの Fuse.js の結果は未リリースの 1.6 で取られたものです。
  • rust-anything はローカルで動き、コードを外部に送りません。ただし Rust を書くエージェントは、そのモデル提供元のポリシーのもとでコードを送ります。
  • gate は移植のコード量を元の 3 倍（＋50 行）までに制限します。超える場合はクレートで済む処理を手書きしているか、ケースを個別に処理している可能性が高い、とされています。
  • Rust プロジェクトや Rust Foundation とは無関係の独立したプロジェクトです。
