Superpowers

obra/superpowers · v7.0.2（2026-11-03） · 15 スキル · 15 ハーネス対応 · MIT

1 — 概要
何か

Superpowers は、コーディングエージェント向けのソフトウェア開発の進め方一式。組み合わせ可能な「スキル」と、エージェントがそれらを確実に使うための初期指示（using-superpowers の bootstrap）で構成される。作者は Jesse Vincent と Prime Radiant。

7.0.2確認したバージョン
15対応ハーネス（Codex App/CLI を 1 と数える）
15スキル
0 deps第三者依存

エージェントは「何か作る」と判断すると、すぐにはコードを書かず、何をなぜ作りたいかを確認する。設計を承認したら実装プランを書き、プランを人が確認してから実行に移る。実行方式は、タスクごとにサブエージェントとレビューを回す subagent-driven-development と、同じセッションで全タスクを実装して最後に 1 回だけレビューする executing-plans（Native）から選ぶ。

2 — v6〜v7 の変更
v5.1.0（2026-04-30）以降の主な変更

前回このページが基準にした v5.1.0 から、v6.0.0・v6.4.1・v7.0.0 の 3 回で構成が大きく変わった。RELEASE-NOTES.md から利用者に影響する変更を抜き出す。

版変更利用者への影響
6.0.0SDD のタスクレビューを 1 本に統合（task-reviewer-prompt.md）。最後に全ブランチを最上位モデルで 1 回レビューspec-reviewer-prompt.md と code-quality-reviewer-prompt.md は削除。リリースノートでは、評価条件で Claude Code と Codex がおよそ 2 倍速く、トークンを約 50% 減らしたとしている（ハーネスや作業内容によって変わる、と注記付き）。
6.0.0worktree をプロジェクト内（既存の .worktrees/ か worktrees/、無ければ .worktrees/）に作る旧来の ~/.config/superpowers/worktrees/ は使われなくなった。
6.0.0brainstorming の visual companion にセッション鍵を導入URL に付く一回限りの鍵がないとリクエストも WebSocket も通らない。アイドル時間は 30 分から 4 時間に延長。
6.0.0スキル本文を特定ベンダーの用語から切り離す「Task tool を使う」は「サブエージェントを起動する」に。ハーネスごとの対応表は skills/using-superpowers/references/。
6.1.0using-superpowers の bootstrap を圧縮全セッションに注入されるため、そのトークン量を削減。Codex は SessionStart hook をやめ、スキル検出だけで動く。
6.2.0SDD の作業ディレクトリをプランごとに分ける（.superpowers/sdd/<plan>/）。修正ループは実装役を再開して進め、5 ラウンドで打ち切る別プランの進捗台帳を読み違えなくなった。最終レビューが通ると作業ディレクトリは削除される。
6.2.0finishing-a-development-branch の選択肢から「破棄」を外す破棄は利用者が明示的に頼んだときだけ。PR 作成は gh 固定ではなくなった。
6.3.0SDD の実行中、計画の矛盾はコントローラが判断して台帳に記録し、作業を止めない人を待つのは破壊的・不可逆な操作だけになった。現行の SKILL.md では止まる条件を 4 種類に限定している（5 章）。
6.4.1executing-plans を Native 実行として作り直し。diagnosing-superpowers を追加プランの引き渡し時に Subagent-driven と Native のどちらにするか、理由付きで推奨が出る。保存したプランを人が確認するまで実行しない。プランには、仕様から読み取れるがどのタスクのテストも扱わない入力や失敗を最大 5 件挙げる Review Focus 節が付く。
6.4.2writing-plans はコード全文ではなく決定事項を書く手順にはシグネチャ・テストのアサーション・仕様の値を書き、本文は仕様から決まらないアルゴリズムだけ。再現した報告ではプラン作成の時間が 1/4、トークンが約 1/3 になった。
7.0.0brainstorming を作り直し作業の大きさを判断してから進め方を変える。設計書のレビュー役は「builder check」（作る立場で読んで不明点を挙げるサブエージェント）に置き換え。
7.0.1brainstorming の再調整。長い 3 スキルを短縮（subagent-driven-development と writing-skills は references/ に分割）Claude Code は圧縮後にスキルを 20,000 文字で切って再添付するため。SKILL.md が 20,000 バイトに達するとテストが落ちる。
7.0.2brainstorming の質問を減らす。6 ハーネスの bootstrap 不具合を修正。SDD 補助スクリプトが現在のリポジトリを対象にし、-C DIR を受け付けるコミットの無い新規プロジェクトでは、git init と最初のコミットをしてから SDD を始める必要がある。
削除・名前変更されたもの: SDD のレビュー用プロンプト 2 本（6.0.0）、plan-document-reviewer-prompt.md と CLAUDE.md（6.4.2。貢献ガイドは AGENTS.md に一本化）、TDD の testing-anti-patterns.md は writing-good-tests.md に改名（6.2.0）。Gemini CLI は 6.1.0 でいったん外され、6.2.0 で戻っている。
3 — 基本ワークフロー
7 ステップ

エージェントはタスクの前に必ず関連スキルを確認する。README は「提案ではなく必須のワークフロー」と書いている。

順スキル発動する場面と役割
1brainstorming何かを作る前。質問で何をなぜ作りたいかを引き出し、理解した内容を返して訂正を受ける。小さな変更はチャットで合意し、プロジェクト規模なら設計書を書く。
2using-git-worktrees設計の承認後。新しいブランチの worktree を作り、セットアップしてテストが通る状態を確認する。
3writing-plans承認された設計をもとに、確認できる結果を 1 つ持つ手順単位まで分解する。ファイルパス、シグネチャ、テストのアサーション、検証コマンドを書く。
4subagent-driven-development / executing-plansプランの確認後。タスクごとにサブエージェントとレビューを回すか、同じセッションで全タスクを実装して最後に全ブランチを 1 回レビューするか（5 章）。
5test-driven-development実装中。RED-GREEN-REFACTOR を守らせ、テストより先に書いたコードは削除する。緑の判定はそのテストファイルではなくプロジェクトのテスト全体（6.4.1）。
6requesting-code-reviewタスクの間。プランとの整合を深刻度別に報告し、Critical は先へ進ませない。
7finishing-a-development-branch全タスク完了時。テストを確認し、ローカルマージ / PR 作成 / そのまま残す の 3 択を出して worktree を片付ける。
4 — brainstorming
7.0 系での振る舞い

7.0.0 で作り直し、7.0.1 と 7.0.2 で質問の出し方を調整している。現行の skills/brainstorming/SKILL.md から要点をまとめる。

段階やること
最初に判断依頼に必要なことが全部あるか（例:「アイコンをコーンフラワーブルーに」）。あればそのまま実行して、何をしたかを伝える。足りなければ会話を始める。
聞く前に読む既存プロジェクトや渡された仕様・プラン・ファイルは、最初のメッセージの前に読む。プロジェクトや文脈で答えが出ることは聞かない。
最初のメッセージ要望が具体的なら約 200 語で依頼を言い直し、調べて分かったことを添える。理由が書かれていなければ、選択肢を付けずに理由を聞く。決めることが残っていなければ短い設計を示して承認を求める。
質問の条件答えで作るものが変わり、依頼にもプロジェクトにも答えが無いときだけ聞く。それ以外は判断と理由を、訂正できる提案として書く。書き起こし・ファイルの置き場所・追加調査といった進め方は自分で決めて報告する。
選択肢の出し方選択肢を挙げられる判断は、それぞれのトレードオフと推奨を付けて出す。7.0.2 のリリースノートでは、Ctrl+K が 2 機能に割り当てられた仕様のシナリオで、7.0.1 は 8 回中 8 回「どちら？」とだけ聞き、7.0.2 は 8 回中 8 回選択肢と推奨を示した。
読み返し理解した部分ごとに 200〜300 語で説明を返し、相手が言ったことと自分が補ったことを分けて書く。画面や印刷物なら文字のスケッチを付ける。
作業の大きさ小さな変更なら会話の内容をまとめた短い設計書、プロジェクトなら完全な設計書。どちらにも検討した 2〜3 案とトレードオフ、選んだ案と理由（Approaches）を入れる。途中で大きくなったら止まって段階を上げる。
実装に入る条件案を選んでもらう → 設計書を書く → 承認を得る → writing-plans を呼ぶ、の順。依頼者が質問を断った場合と、合意済みのスパイクは例外。
visual companion: 画面・レイアウト・フロー・図など、見たほうが早い内容のときにブラウザで開く小さな Web サーバー。既定ではロゴを Prime Radiant のサイトから読み込み、その際に Superpowers のバージョンが送られる。止めるには SUPERPOWERS_DISABLE_TELEMETRY を設定する。Claude Code の DISABLE_TELEMETRY と CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC も有効。
5 — プランの実行方式
Subagent-driven と Native

writing-plans はプランを保存すると、人にプランの確認を頼み、どちらの方式で実行するかを推奨付きで尋ねる。推奨の理由は、タスク間のインターフェースの依存度、タスク数、誤りを出荷したときのコストから 1 文で示す。

Subagent-driven（subagent-driven-development）Native（executing-plans）
実装タスクごとに新しいサブエージェント現在のセッションが全タスクを実装
レビュータスクごとに 1 回（仕様準拠と品質の 2 判定）＋最後に全ブランチを 1 回最後に全ブランチを 1 回（最上位モデル）
コストタスクとレビューごとに新しいコンテキスト1 コンテキスト＋最終レビュー 1 回。中位モデルのセッションでも動く
向く場面タスクごとにレビューを挟みたい。プランが長く、後半が圧縮後のコンテキストで走るコストを抑えたい。ハーネスにサブエージェントの道具が無い
共通同じプラン単位の作業ディレクトリ（.superpowers/sdd/<plan>/）と進捗台帳 progress.md を使い、タスクの間で止まらない。最終レビューが通ると作業ディレクトリを削除して finishing-a-development-branch へ進む。

止まらずに判断する

どちらの方式も、計画の矛盾や曖昧さで人を待たない。仕様を最優先、プランをその根拠とし、どちらにも答えが無ければ自分で決めて、台帳に次の形で記録する。

Ruling: <何を決めたか> — <理由> — <間違っていた場合のコスト>

止まって聞くのは次の 4 つだけ。

  • 取り返しのつかない操作、破壊的な操作
  • セキュリティに関わる操作
  • この worktree の外への副作用で、通常は事前に聞くもの（マージ、共有ブランチへの push、公開）
  • プランが壊れていて、どの進め方も当て推量になる場合

SDD のモデル選択

役割モデル
プランに完全なコードがある実装、1 ファイルの機械的な修正最も安い層
複数ファイルの統合、デバッグ、文章の指示からの実装、レビュー中位を下限にする（安いモデルは手数が 2〜3 倍になり、総額でかえって高くなるため）
設計判断、最後の全ブランチレビュー使える中で最上位
修正ループの 4〜5 ラウンド目行き詰まった実装役より 1 段上
モデルは必ず明示する: 省略するとセッションのモデル（多くは最上位で最も高い）を引き継ぐ。6.0.0 のリリースノートでは、ある実行で 26 回のレビューがすべて最上位モデルで走った例を挙げている。

7 — 不具合の調べ方
diagnosing-superpowers

スキルが発動すべきでないときに発動した、発動しなかった、プランを無視した、同じ作業を繰り返した、トークンを使いすぎた、といったときに使う。エージェントに次のように頼む。

figure out what went wrong with superpowers in this session
figure out what went wrong with superpowers in session <id>
手順内容
1. 問題の聞き取り対象セッション、期待したこと、起きたこと、気にしている指標（時間・トークン・繰り返し）が書けるまで 1 問ずつ聞く
2. 特定セッションのトランスクリプトを実ファイルのパスまで解決し、~/.superpowers/diagnosing-superpowers/<session-id>/ に作業ファイルを作る
3. 切り分け7 つの観点（スキルの時系列、プラン遵守、重複作業、つまずき、品質の証拠、依頼の衝突、コストと時間）ごとに分析用サブエージェントを並列に起動する。path:line の無い指摘は捨てる
4. 報告テンプレートに沿ってレポートを書き、パスを示す
5〜7. 任意GitHub issue の検索と下書き（承認後に作成）、匿名化バンドルの作成（頼まれたときだけ）、似たセッションの検索
扱い: セッションファイルは読むだけで変更しない。数値はトランスクリプトか実行したコマンドから取り、記憶から書かない。匿名化は取りこぼしがありうるので、共有前に全ファイルを自分で確認するよう明記されている。

9 — 貢献時の注意
AGENTS.md の要件

貢献ガイドは AGENTS.md に一本化された（6.4.2 で CLAUDE.md を削除）。冒頭は AI エージェント向けで、PR の却下率は 94% と書かれている。新しいスキルの持ち込みは原則受け付けず、スキルの変更は対応する全ハーネスで動く必要がある。

PR 前に必須: PR テンプレートの全項目を具体的に埋める。open / closed の両方で重複 PR を探す。人間のパートナーが実際に遭遇した問題か確かめる。core に入れるべき変更か判断する。モデル・ハーネス・バージョン・導入済みプラグインと、依頼内容を開示する。完全な diff を人間に見せて承認を得る。「Human-authored summary」は人間が 200 語以内で書く。ターゲットブランチは dev。
受け付けない変更理由
他人が起票した issue をエージェントが直す PRメンテナが頼んだ場合を除く。同じ問題に遭遇したなら既存 issue に報告を足す（7.0.1 で追加）。
第三者依存の追加新ハーネス対応を除き zero-dependency。外部ツール依存は別プラグインにする。
Anthropic のスキル文書に「合わせる」書き換えスキル本文は実際の挙動で調整済み。変えるには結果が良くなる評価の証拠が必要。
ドメイン・プロジェクト固有のスキルや設定core は汎用。固有のものは独立したプラグインにする。
issue を拾ってまとめて出す PR、推測だけの修正実際のセッション・エラー・体験を示せないものは出さない。
無関係な変更の同梱、fork 固有の変更、作り話分割する、または出さない。
新ハーネス対応でセッションの記録が無いものエンドツーエンドで動く証拠が必要。

スキルの挙動テストは別リポジトリ superpowers-evals の drill を evals/ に clone して使う。プラグイン本体のテストは tests/ にあり、run-*.sh または npm test で動かす。
