データベースのメタデータからオントロジーを組み立て、エージェントの誤答を減らす NVIDIA のコンテキスト層

NVIDIA/auto-ontology · v1.1.0（pyproject.toml）· 2026-11-03 時点の main · Apache-2.0

概要

Auto-Ontology は、社内のデータベースの横で動かすサービスです。テーブルとカラムのメタデータを読み、業務用語とカラムの対応、レビュー済みの SQL 式、テーブル間の結合関係をまとめたオントロジーを Postgres に作ります。エージェントはスキーマを直接読む代わりに、このオントロジーを経由して質問を SQL に変換します。人は Web UI で定義を確認し、正しいものを認定（certify）します。

README が掲げる狙いは「エージェントの誤答を減らすこと」です。速く出た売上の数字も、間違っていれば使えません。そこで、質問の前に「データがどこにあり、何を意味し、どう結合し、そもそも答えられる質問か」をエージェントへ渡します。

オントロジーの中身

オントロジーは 3 種類の定義で構成されます。いずれも Postgres に保存され、検索用の埋め込みは pgvector に入ります。

用語（Terms）

Customer や Invoice Line のような業務概念。説明と同義語を持ち、値を保持するカラムに対応付けられます。

例: Wide World Importers を 1 回コンパイルすると 31 用語

SQL 属性（SQL attributes）

用語の下に置くレビュー済みの SQL 式。粗利や移動合計など。エージェントはこれを再利用するので、同じ指標は毎回同じ式で計算されます。

クエリ履歴からも候補を提案

関係（Relationships）

テーブル同士の結合方法。ブリッジテーブルを含み、キーとデータの両方から推定します。

ブリッジテーブル用 SQL 属性は RERANK モデルで候補を絞る

セマンティックモデルの交換標準 Apache Ossie に対応しており、Ossie 側にある Auto-Ontology 用コンバーターでモデル定義を Ossie YAML として取り込み・書き出しできます。UI では Settings → Import / Export、API では POST /api/model/import と POST /api/model/export です。

カタログ取り込み時には PII 検出も走ります。LLM の分類器がカラムを判定し、確信度 0.9 以上のものには PII タグが自動で付きます（auto_ontology/pii_detection/）。

実線の枠はクライアントから到達させるサービス、破線の枠はプライベートネットワークに閉じるサービス。

3001 と 3002 は外に出さない。 FastAPI はフロントエンドが転送する x-auto-ontology-user-id ヘッダーをそのまま信頼します。取り込みサービスの ingest / delete / reset / compile には独自の認証がありません。クライアントは必ずポート 3000 の Web アプリを経由させてください。

MCP サーバーは公開 API の HTTP クライアントにすぎず、DB の認証情報もモデル設定も持ちません。認証と権限チェックは Next.js 側にあるため、MCP のセッションはサインインした本人の権限でしか動きません。

生成・認定・回答

Auto-Ontology は、オントロジーを生成し、人が認定し、エージェントがそれを使って答える、という 3 段階で動きます。

生成（Generate）

取り込みサービス
  1. ソースを読む: スキーマ抽出、カラムのプロファイル、サンプル値をカタログへ
  2. エンティティ命名: テーブルごとに用語を抽出し、カラムに対応付け
  3. 関係の解決: 結合とブリッジテーブルを推定し、クエリ履歴から SQL 属性を提案
  4. 書き込み: 用語・関係・SQL 属性を Postgres に、埋め込みを pgvector に保存

認定（Certify）

人（UI / API）
  1. 実際の質問で試す。Chat、または MCP の check_answerable と ask_question
  2. 用語、説明、SQL 属性を UI か API で直す
  3. 正しくなった名前、説明、SQL 属性を認定する

回答（Answer）

Text-to-SQL エージェント
  1. 意図を分類し、質問中のエンティティを抽出
  2. 埋め込み検索で用語・カラム・SQL 属性の候補を取得
  3. 候補から SQL を書く
  4. フィルター値とクエリを DB で確かめ、失敗したら SQL を直す
  5. 実行し、答えに SQL と手順を添えて返す

コンパイルは auto_ontology/semantic/pipeline.py がテーブル単位で進めます。LLM による抽出は 3 ワーカーで並列に走らせつつ、書き込みはテーブルの順番どおりにコミットします。取り消しが入ったときは、待ち行列のテーブルを順番待ちせずにスキップ扱いにして、ワーカーをすぐ解放します。

回答エージェントの処理

回答エージェントは LangGraph のグラフとして auto_ontology/retrieval/text_to_sql/text_to_sql_graph.py に定義されています。上から順に進み、検証に落ちると reconstruct_sql へ戻って SQL を作り直します。

question_intent質問の意図を分類する。予測系の質問かどうかもここで判定する。再開指定（path_state の _resume_from）がある実行は、入口から reconstruct_sql へ直行する
question_extraction質問が名指ししているエンティティを抜き出す。
retrieve_candidates埋め込み検索で用語・カラム・SQL 属性の候補を集める。データの中身ではなくメタデータを尋ねる質問（question_type が information）→ information_agent で答えて終了
prepare_candidates候補を整える。KumoRFM 設定時の予測質問 → prepare_prediction_graph → kumo_predict で終了 / 証拠が足りない → refine_evidence
construct_sql_from_candidates候補から SQL を組み立てる。候補で SQL が組めない → unconstructable_sql_response（答えられないと返す）
validate_sql_values / validate_sql_queryフィルターの値と SQL そのものを検証する。
precheck_combined任意。リテラル値、結合経路、JSONB パスの事前プローブをまとめて行う。
execute_sql_queryDB で実行する。試行回数の上限もここで管理する。
check_empty_like_result / check_value_repair結果が空のとき、LIKE 条件やフィルター値の誤りを疑って修復を試みる。
format_and_respond答え、SQL、手順を返す。
reconstruct_sql検証・実行・修復チェックで落ちたときの戻り先。作り直した SQL は再び検証に回る。

Chat では各回答の SQL が見え、行の表示、CSV のダウンロード、チャート表示ができます。

クイックスタート（Docker Compose）

Microsoft のサンプル販売 DB である Wide World Importers を相手に、Docker Compose で起動します。Docker（Compose v2）、uv、build.nvidia.com の NVIDIA API キー（nvapi-...）を用意してください。

  1. リポジトリを取得し、.env を作ります。

    git clone https://github.com/NVIDIA/auto-ontology.git && cd auto-ontology
cp .env.example .env

    .env に次の値を設定します。

    DEFAULT_MODELS_API_KEY=nvapi-...
AUTH_SECRET=<長いランダム文字列。openssl rand -base64 32 など>
APP_URL=http://localhost:3000
POSTGRES_PASSWORD=<新しいパスワード>
CONNECTION_STRINGS=postgresql://postgres:<同じパスワード>@postgres:5432/wideworldimporters
AUTO_ONTOLOGY_ADMIN_PASSWORD=<新しいパスワード>
PGADMIN_PASSWORD=<新しいパスワード>

    Compose は Postgres、pgAdmin、Web アプリをホストに公開するので、既定のパスワードはすべて差し替えてから起動してください。.env.example にはモデルロールごとの API キー行もあります。各 nvapi-your-api-key-here を自分のキーにするか、行を消して DEFAULT_MODELS_API_KEY にフォールバックさせます。

  2. Postgres を起動し、サンプル DB を投入します。シードスクリプトは評価用リポジトリ auto-ontology-eval にあります。

    docker compose up -d --wait postgres
git clone https://github.com/NVIDIA/auto-ontology-eval.git ../auto-ontology-eval
(cd ../auto-ontology-eval && uv sync && cp .env.example .env && \
  POSTGRES_PASSWORD='<同じパスワード>' \
  uv run python scripts/seed/seed_wwi.py --database-name wideworldimporters --drop)

  3. 残りのスタックをビルドして起動します。

    docker compose up -d --build

  4. http://localhost:3000 を開き、.env の AUTO_ONTOLOGY_ADMIN_EMAIL と AUTO_ONTOLOGY_ADMIN_PASSWORD でサインインします。Settings → Semantic Compilation をオンにすると、起動時に済んだ取り込みに続いてコンパイルが始まり、終わると「Semantic compilation is ready」と表示されます。

  5. Chat で質問します。エージェントは revenue、product、state を用語に解決し、関係をたどって結合を決め、クエリを実行します。

    質問:   What was revenue for the USB food flash drive - sushi roll in Pennsylvania in June 2015?

Answer: Revenue ... in June 2015 was $588.80, from 3 invoice lines.
SQL:    SELECT SUM(il.extendedprice) AS revenue, COUNT(*) AS invoice_lines
        FROM sales.invoicelines il
        JOIN sales.invoices i        ON il.invoiceid = i.invoiceid
        JOIN warehouse.stockitems si ON il.stockitemid = si.stockitemid
        JOIN sales.customers c       ON i.customerid = c.customerid
        JOIN application.cities ct   ON c.deliverycityid = ct.cityid
        JOIN application.stateprovinces sp ON ct.stateprovinceid = sp.stateprovinceid
        WHERE ...
Steps:  Resolved terms: Invoice Line (revenue), Stock Item, State Province, Invoice
        Joined: invoice line -> invoice -> customer -> city -> state province
        Validated the filter values against the data, then executed

  6. データにない質問もしてみます。Wide World Importers には広告データがないので、広告費に関する質問は解決先の用語がありません。MCP 経由のエージェントは先に回答可能性を確かめ、確認を求めます。

    You: What was return on ad spend for the sushi roll flash drive in June 2015?
    Agent: check_answerable -> coverage 0.5; no term covers "ad spend"
    Agent: その製品の売上は出せますが、広告費のデータがないため ROAS は計算できません。6 月の売上で代わりにしますか、それとも広告費を持つ別のソースを接続しますか。
再起動後に UI の左ナビゲーションが出ない場合は、古いセッション Cookie が残っています。localhost:3000 のサイトデータを消してサインインし直してください。その他の失敗は skills/nvidia-ontology-setup/references/troubleshooting.md にまとまっています。

接続先と認証情報

接続できる DB エンジンは 10 種類です。

PostgreSQLMySQLDatabricksSnowflakeClickHouseTrinoApache KyuubiHeavyDBDuckDB*SQLite*

* DuckDB と SQLite は接続文字列（duckdb://、sqlite://）でのみ指定でき、UI からは追加できません。

接続の登録先は 2 つあります。Settings → Connections（API では POST /api/connections/test の後に POST /api/connections、権限 connection:manage）と、環境変数 CONNECTION_STRINGS です。UI の接続はスキーマの許可リストと table_allow_regex / table_deny_regex で範囲を絞れます（deny が優先、名前は修飾なし・大文字小文字を区別）。CONNECTION_STRINGS には絞り込みがありません。

1 つのデプロイではどちらか一方だけを使う。 質問への回答は UI の接続を優先し、なければ CONNECTION_STRINGS を使います。取り込みは逆で、CONNECTION_STRINGS があればそちらを使い、空のときだけ UI の接続を読みます。両方あると、取り込んだ DB と問い合わせる DB が食い違います。
Vault の設定UI で追加した接続の認証情報の置き場所
なし（既定）パスワードを含む接続オブジェクト全体を JSON にし、Postgres のカタログ行に暗号化せず保存する
ありDB 名をキーに Vault へ書き込み、カタログ行には保存しない

Vault は VAULT_ADDR、VAULT_NAMESPACE、VAULT_ROLE_ID、VAULT_SECRET_ID の 4 つがすべて設定されたときだけ有効になります。一部だけの設定は警告付きで無視され、平文保存に戻ります。

モデルの割り当て

モデルは 4 つのロールに分かれています。nvapi- キーを使う場合、既定はすべて build.nvidia.com の NVIDIA NIM です。

ロール既定モデル担当
REASONINGnvidia/nemotron-3.5-lightning-30b-a3bオントロジー構築（用語、関係、SQL 属性）、回答の SQL と説明の作成、回答可能性の採点
NON_REASONINGnvidia/nemotron-3.5-lightning-30b-a3bエージェントの軽い工程。意図分類、エンティティ抽出、候補選択、SQL のチェックと修復
EMBEDnvidia/nemotron-3.5-embed-1bテーブル、カラム、用語、SQL 属性を pgvector に索引し、質問と照合する
RERANKnvidia/nemotron-3.5-rerank-8bブリッジテーブル用 SQL 属性を作るときに候補テーブルを順位付けする

自前の NIM や OpenAI 互換エンドポイントを使うときは <ROLE>_ENDPOINT、<ROLE>_API_KEY、<ROLE>_MODEL を設定します。未設定の項目は DEFAULT_MODELS_<FIELD> にフォールバックするので、DEFAULT_MODELS_* を埋めて差分だけ上書きするのが最も簡単です。構造化出力に対応したモデルを選び、埋め込みモデルは取り込み時と問い合わせ時で同じものにしてください。

予測（KumoRFM）

KUMO_RFM_API_KEY を設定すると、予測を求める質問は KumoRFM に回されます。KumoRFM はホスト型サービスで、回答のために接続先のテーブルをアップロードします。上限は KUMO_MAX_TABLES（既定 20）と KUMO_MAX_ROWS_PER_TABLE（未設定なら無制限）です。有効にする前に、何が送られるかを確認し、組織のデータレビューを済ませてください。

MCP サーバー

MCP サーバーは、MCP クライアントにオントロジー上の読み取り専用ツールを提供します。各ユーザーは Auto-Ontology でサインインし、すべての呼び出しがそのユーザーの権限で実行されます。設定ファイルに認証情報は書きません。

用途ツール内容
準備状態check_readinessこのデプロイで何か答えられる状態か。全ブロッカーを一度に返す
回答可能性check_answerableオントロジーが質問をカバーしているか。ask_question 前の安価な事前確認
質問ask_question答え、実行した SQL、行を別々のフィールドで返す。最大 100 行
用語search_terms、get_term、get_term_columns、get_term_sql_attributes、get_sql_attribute、describe_table用語集の検索と、用語・カラム・SQL 属性・テーブルの参照

DB、スキーマ、生のカラムを閲覧するツールは意図的に置いていません。カタログを閲覧できると、エージェントがセマンティック層ではなく生のテーブルで推論し始めるからです。サーバーはハンドシェイク時にツールの使う順番を説明する instructions も送ります。何も指示がないとモデルはいきなり ask_question を呼びがちなためです。

check_readiness が分けて見るのは、コンパイル済みのセマンティック層と、SQL を実行できる DB 接続の 2 つです。片方だけある状態では用語集は読めて用語も解決するのに、質問は数分のモデル呼び出しの後に曖昧に失敗します。

# サーバーを起動（リポジトリの clone は不要）
AUTO_ONTOLOGY_API_URL=http://localhost:3000 \
  uvx --from "git+https://github.com/NVIDIA/auto-ontology.git#subdirectory=mcp" auto-ontology-mcp

# Cursor（~/.cursor/mcp.json）
{ "mcpServers": { "auto-ontology": { "url": "http://localhost:3003/mcp" } } }

# Claude Desktop（mcp-remote でブリッジ）
{ "mcpServers": { "auto-ontology": { "command": "npx", "args": ["mcp-remote", "http://localhost:3003/mcp"] } } }

設定後にクライアントを再起動し、求められたらサインインします。公開 API には 87 のオペレーションがありますが、ツールは mcp/auto_ontology_mcp/tools.py の許可リストで絞っています。リスト上のオペレーションが仕様から消えると起動時に失敗するので、上流での名前変更でツールが黙って消えることはありません。

Agent Skills

コーディングエージェント向けに 3 つのスキルがあり、入口は AGENTS.md です。スキルは nvidia/skills にも同期され、npx skills add nvidia/skills で導入できます。

スキル担当使う場面
nvidia-ontology-setupインストール、接続、取り込み、コンパイル、準備状態の確認、トラブルシュートまだ起動していない、または起動中に失敗した
nvidia-ontology-management確認、モデリング、変更、認定、Import/Export、公開とロールバック定義を直したい。MCP は書き込めないので、承認された書き込み経路をここで扱う
nvidia-ontology-queryMCP 優先・REST 予備での呼び出し、SQL・行・回答文の検証デプロイ済みで質問したい

想定されている一連の流れは次のとおりです。製品が対応していない手順に当たったら、操作を作り出さずに「未対応」と明示して返すことがスキル側の約束になっています。

導入・接続・準備確認→確認・モデリング→段階適用と読み戻し→質問で検証→公開→再度質問して確認

REST API と認証

質問は Web アプリと同じオリジンの POST /api/chat/completions で送ります。応答は Server-Sent Events で、result イベントに答えが入り、data: [DONE] で終わります。API トークンはユーザーメニューの API Tokens で発行します。

curl -N http://localhost:3000/api/chat/completions \
  -H "x-api-key: $AUTO_ONTOLOGY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"question": "How many orders shipped last week?"}'
for line in response.iter_lines(decode_unicode=True):
    if not line or not line.startswith("data:"):
        continue
    payload = line.removeprefix("data:").strip()
    if payload == "[DONE]":
        break
    event = json.loads(payload)
    if event["type"] == "result":
        print(event["answer"]["response"])
        print(event["answer"]["sql_code"])
    elif event["type"] == "error":
        raise RuntimeError(event["message"])

認証は Better Auth で、各呼び出しを呼び出し元のロールで認可します。/api/... の全ルートは frontend/auth/resolve-user.ts で次の順に呼び出し元を解決します。

ブラウザのセッション Cookie→API トークン（x-api-key / Bearer）→MCP クライアントに発行した OAuth Bearer→信頼済み呼び出し元が転送した SSO ID トークン

API トークンは SHA-256 のハッシュだけが保存されるため、表示されるのは発行時の 1 回だけです。失くしたら新しく発行します。有効期限の既定は無期限です。SSO は Settings → Single Sign-On で設定し、IdP にはリダイレクト URI <APP_URL>/api/auth/sso/callback を登録します。

評価

精度の測定は別リポジトリ NVIDIA/auto-ontology-eval で行います。BIRD、BEAVER、FDABench-Lite、Wide World Importers では、各問題が質問と正解 SQL の組になっていて、同じモデルに 2 通りで答えさせます。

アームモデルに渡すもの
Controlプロンプトに DB スキーマを入れる
TreatmentChat と同じ Auto-Ontology の回答エージェントが、コンパイル済みオントロジーを使う

決定的な検証器が両アームの SQL を実行結果の一致で採点します（ベンチマークに公式ルールがあればそれに従う）。レポートには正答率の差と、オントロジーで直った問題・壊れた問題の一覧が出ます。確認質問をする多ターンのベンチマーク BIRD-Interact は専用のハーネスで動かします。README には具体的な正答率の数値は載っていません。

uv run python main.py --database-name bird

注意点

  • 非公開ポート: 3001（Backend）と 3002（取り込み）はヘッダーを信頼するか認証がないため、プライベートネットワークに置く。
  • 平文の認証情報: Vault を設定しないと、UI で追加した接続のパスワードは Postgres に暗号化されずに入る。Vault の 4 変数は一部だけでは無効。
  • Compose の既定パスワード: Postgres、pgAdmin、Web アプリがホストに公開されるので、起動前にすべて変更する。
  • 外部へのデータ送信: 既定のモデルエンドポイントは NVIDIA API カタログ（integrate.api.nvidia.com、ai.api.nvidia.com）。KumoRFM を有効にするとテーブルの内容がアップロードされる。
  • 接続設定の二重化: UI の接続と CONNECTION_STRINGS を併用すると、取り込み対象と問い合わせ対象が分かれる。
  • MCP は読み取り専用: 定義の変更は Web UI か Next.js の /api/... を使う。
  • 貢献の受け付け: 外部からのプルリクエストは受け付けていない。連携の要望とバグ報告は Issue、脆弱性は SECURITY.md の手順で報告する。
  • ライセンス: Apache-2.0。サードパーティ部品は THIRD_PARTY_NOTICES.md と CONTAINER_THIRD_PARTY_NOTICES.md に記載。
