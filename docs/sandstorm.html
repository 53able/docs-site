01 — 使われていないサンドボックスを止めて、1 台に多く載せる

HOT · FROZEN · SNAPSHOT · DETACHED

アイドルなサンドボックスを一時停止し、ディスクへ退避し、リクエストが来たら戻す。同時に動かせる数より多くのサンドボックスを 1 台に抱えるためのランタイム。

Sandstorm は AI エージェントのコード実行などに使うサンドボックスを、複数台のマシンにまたがって管理する Rust 製のデーモンです。README の前提は「エージェントは待っている時間が長い」ことです。そこで、使われていないサンドボックスを 4 段階で少しずつ眠らせ、CPU、メモリ、ローカルディスクを順に返させます。リクエストが届くと、そのノードが自分でサンドボックスを起こしてから転送します。

サンドボックスの実体は 2 種類から選べます。既定は gVisor（runsc）のコンテナで、KVM を必要としません。KVM のあるホストでは Firecracker の microVM をノード単位で選べます。どちらのサンドボックスも専用のネットワーク名前空間を持ち、1 つのフリートに両方を混在させられます。

リポジトリの歴史は 2026-05 に始まり、v0.5.3 までは Firecracker のフォーク（実行中 VM の複製）を中心にした別物でした。v0.6.0 で名前を Sandstorm に改め、gVisor を既定にし、1 台からフリートへ構成を変えています。v0.5 からのその場アップグレードはなく、SDK 名も forkd から sandstorm-sdk・@deeplethe/sandstorm・sandstorm-mcp に変わりました。

02 — 4 つの階層：アイドル時間で 1 段ずつ下げ、リクエストで一気に hot へ戻す

各サンドボックスは常に 4 つの階層のどれかにあります（tier.rs）。master の降格ループが 5 秒ごとにアイドル時間を見て、あるべき階層を 1 段ずつ冷たい側へ動かします。戻るときは途中を経由せず、直接 hot に戻ります。

階層状態返すもの残るもの
hot実行中—すべて
frozen同じノードで cgroup.freeze=1CPUメモリ（冷えたページは zswap / zram へ圧縮）
snapshotrunsc checkpoint などでノードのローカルディスクへ保存し、プロセスを終了CPU とメモリローカルディスク上の書き込み層
detachedどのノードにもいない。書き込み層はボリュームへアーカイブCPU・メモリ・ローカルディスクボリュームのみ。メモリの状態は失われる

設計時の案には、凍結したまま memory.high を下げてメモリを回収する cold 階層もありました。1 台なら 7 ms で 90% を回収できたものの、8 台を同時に回収すると 8 台とも目標に届かず 85 秒のタイムアウトに達しました。同じ 8 台をチェックポイントすると 1.1 秒で 413 MiB を解放できたため、cold は採用されていません（ADR 3）。

階層ごとの帰結：frozen はメモリを解放しないため、メモリの収容数を増やすのは snapshot 階層です。ディスクの収容数を増やすのは detached 階層です。frozen や snapshot の間に、サンドボックス内の TCP 接続はタイムアウトすることがあります。別ノードへの移動は detached からのコールドスタートで行い、チェックポイントは運びません。

03 — master と node：あるべき状態と、実際の状態を分ける

役割は master と node に分かれます。どちらも同じバイナリ sandstormd で、serve --master、serve --node、両方を付けると 1 台構成になります。1 台構成でも node は master とループバック上で同じプロトコルを話します（ADR 10）。

DB はあるべき状態だけを持つ

master の SQLite（--state-db）には「どのサンドボックスが、どのノードの、どの階層にあるべきか」だけを書きます。実際の状態は毎回ノードの報告から読み、差分がそのノードの仕事になります。v0.5 ではコントローラーの再起動時に管理中の VM と孤児を区別できず、全部を殺していました（issue #301）。

再起動しても止めない

runsc create / start でサンドボックスはデーモン化され、sandstormd の子プロセスではありません。コントローラーを kill -9 しても 20 個中 0 個が失われ、134 ms で 20 個すべてを引き取り直したと記録されています。master が落ちていても、node は起床を含めて既存のサンドボックスを動かし続けます。

制御面は mTLS

master が自前の CA を持ち、node は登録時にクライアント証明書を受け取ります。登録トークンは <CA の指紋>.<秘密> の形で、node は最初の接続で CA を固定し、トークンは 1 回で失効します。node の識別は証明書で行い、メッセージに書かれた ID は信用しません。

プールは移行できる範囲

スナップショットは runsc の版、ホストのカーネル、CPU の機能に依存します。そこで node はこれらのハッシュを指紋として計算し、指紋が違う node は <pool>#<fp> という派生プールに入ります。復元できない node へのフォークは配置の時点で 409 になります（ADR 6）。

参加する node は、master 自身のバイナリと CA を master から取得します。インターネットへの接続は不要で、master と node のバージョンがずれることもありません。Web コンソールは HTML 1 ファイルとしてバイナリに埋め込まれています。

04 — トラフィックで起こす：接続拒否を「眠っている」の合図にする

公開されたポートへの通信は、サンドボックスがいるノードの gateway（node/gateway.rs）が受けます。gateway は階層の状態を持ちません。hot 以外のサンドボックスは TCP リセットで接続を拒否するので、拒否されたら起こして転送し直す、という動きだけで済みます。

  1. トークンを確認する

    x-sandstorm-sandbox-token ヘッダーを定数時間で比較し、サンドボックスへは転送しません。単純な DNAT ではトークンを読めず、master はデータ経路にいないため、この確認は gateway が担います。

  2. 転送し、拒否されたら起こす

    接続が拒否されたら、そのノード上でサンドボックスを起こし（node/wake.rs）、もう一度転送します。呼び出し側からはエラーではなく遅い応答に見え、起床を待った応答にはその旨のヘッダーが付きます。

  3. 足りなければ場所を空ける

    メモリやスワップが下限を下回っていれば、需要の低いサンドボックスから（hot より frozen を先に）ディスクへ退避します。1 回の起床で退避するのは最大 4 個です。需要は 1 リクエストごとに 1 増え、30 秒ごとに e 分の 1 に減衰します。処理中のリクエストがあるサンドボックス、起動から 2 秒以内のもの、階層の変更中のものは退避の対象から外れます。

  4. 2 秒で始められなければ断る

    復元の枠の確保とメモリ圧力（PSI）の低下を待てるのは 2 秒です（--wake-budget-ms）。超えたら retry-after 付きの 503 を返します。枠数の 2 倍を超える起床が待っていれば、待たずに断ります（--wake-max-waiting）。

  5. あとで master に伝える

    node は次の報告でリクエストの発生（traffic）と退避したもの（evicted）を伝え、master はアイドル時間の計測をやり直して、あるべき状態をそれに合わせます。master が退避されたものを戻させると、node がまた別のものを退避することになるためです。

05 — ノードの自己防衛：SSH が届かなくなる前に新しい仕事を断る

メモリを使う処理（作成と hot への昇格）の前に、node は自分の現在値を確認し、次のどれかに当たれば保留します（ADR 8）。master も直近の報告にもとづいて配置を判断しますが、最終的な判断は現在値を持っている node が行います。

条件オプションと既定値
空きメモリが下限を下回る--admit-min-free-mib（既定 512）
スワップがあるとき、スワップの空きが下限を下回る同じ設定から算出
メモリ圧力が上限を超える（PSI some の 10 秒平均）--admit-max-psi（既定 8）、起床用は --wake-max-psi
  • 削除と降格は保留しません。ノードの不足を解消する手段だからです。
  • /proc の読み取りに失敗した場合は 0 として扱い、拒否しません。読めないことでフリート全体が止まらないようにするためです。
  • 過負荷はキューに積まずに素早く断ります。node が保留した作成は held_back として報告され、5 秒以内に再試行されます。どこにも置けない作成と、間に合わない起床は 503 です。

この仕組みがない状態では、master がマシンの SSH が応答しなくなるまで作成を受け付け続けた、と docs/SECURITY.md に書かれています。

06 — gVisor と Firecracker：隔離の強さと、必要なホストが違う

v0.6 で既定を gVisor にした理由は、KVM のないクラウドインスタンスで動かすためです。開発と計測に使っている 3 台はいずれも /dev/kvm がなく、多くの運用者も同じ状況だと ADR 2 は述べています。Firecracker は --backend firecracker でノード単位に選ぶ 2 つ目のバックエンドで、フォークではなく upstream の Firecracker を使います。

docs/SECURITY.md の「Which boundary you actually get」より
gVisor（既定）Firecracker
サンドボックスrunsc のコンテナmicroVM
ゲストのカーネルユーザー空間の gVisor Sentry専用の Linux カーネル
ホストのカーネル全サンドボックスで共有KVM 経由でのみ到達
脱出に必要なものSentry のバグ、またはその背後の seccomp の穴KVM か Firecracker のバグ
/dev/kvm不要必要（PVM 上でも動作確認済み）
メモリ上限の既定なしゲスト 512 MiB（cgroup には VMM 分の 64 MiB を加算）

2 つのバックエンドは Backend トレイト（node/backend.rs）の裏にあり、同じ cgroup に入るため、凍結、メモリの計測、cgroup.kill は同じコードで扱えます。Firecracker 側の主な決まりは次のとおりです（ADR 11）。

  • メモリとディスクを一緒に保存する：ゲストのページキャッシュはディスクのブロックを参照するため、別の時点のメモリとディスクを組み合わせるとファイルシステムが壊れます。各イメージは vmstate、mem.*、VM 停止中に reflink した rootfs.ext4 をまとめて持ちます。
  • reflink が必須：作業ディレクトリは FICLONE に対応した XFS（reflink=1）か btrfs である必要があり、全コピーへのフォールバックはありません。
  • 差分スナップショット：8 回未満の書き込みの連鎖からなるメモリは Diff、それ以外は Full で保存し、最初の復元時に連鎖を組み立ててキャッシュします。
  • ゲストのアドレスは 1 つ：どのゲストも名前空間内で 10.42.0.2 を使うため、スナップショットのネットワーク設定はどの名前空間でも通用します。ゲスト内ではエージェントがポート 8888 を使うので、テンプレートはこのポートを使えません。

v0.5 にあった実行中 VM のライブフォーク、hugepages、Firecracker のボリュームは持ち越されていません。API で live_fork や hugepages を指定すると 410 Gone が返ります。実行中のサンドボックスを複製したい場合は、branch でチェックポイントを取ってタグにし、そこからフォークします。

07 — 計測値：ホストが違うので列ごとに読む

README の表（2026-10-31 計測）です。各ノードから自分の gateway へリクエストを送っており、ネットワークは経路に入っていません。3 列はホストの性能が大きく違うため、列どうしを比べる表ではありません。

gVisorFirecracker（KVM）Firecracker（PVM）
ホスト2 コア・2 GB16 スレッド・31 GB2 vCPU・3.8 GB
frozen から起床（64 MiB のアプリ）100 ms165 ms78 ms
ディスクから起床（16 / 64 / 256 MiB）130 / 150 / 720 ms150 / 150 / 500 ms80 / 135 / 450 ms
ディスクから起床（512 MiB / 1 GiB）1.1 / 3.3 s0.7 / 1.4 s0.4 s / 未計測
1 ノードのメモリに保持できた数（web / 64 MiB / 256 MiB）76 / 18 / 6293 / 160 / 8545 / 34 / 18
同時に起こした 10 / 40 個のうち応答した数6 / 610 / 288 個中 5.5

トラフィック試験はノードあたり 40 個のサンドボックスに、一部へリクエストが偏る負荷をかけています。p50 は gVisor で 6〜10 ms、p99 は約 2 秒で、p99 は復元を待ったリクエストです。gVisor のノードは 2 個ずつ並行して復元し、4 個までを待たせるため、10 個以上を同時に起こすと 6 個が応答し、残りはすぐに 503 になります。「保持できた数」はスワップありで動き続けた数で、応答の速さは表していません。

他のランタイムとの比較

README 冒頭の図は、64 MiB のアプリを 1 つずつ 20 回起動した p50 です。起動済みのアプリのイメージから復元する「warm テンプレート」（オプトイン）では、クラウド VM 上で Sandstorm on Firecracker が 84 ms、CubeSandbox が 87 ms、KVM マシンでは 100 ms と 129 ms でした。同じ図で Docker + gVisor は 685 ms、microsandbox は 1.1 s、Kata は 3.4 s です。実行中のアプリを 20 個に複製する時間は、KVM マシンで Sandstorm 361 ms、CubeSandbox 1,064 ms と記録されています。README 自身が、同じバイナリで前日に計測した 64 MiB アプリの値が 74 ms と 78 ms だったため相対値として読むよう注記しています。

バックエンドごとの最適化（凍結したページの zswap への回収、ディスク速度に応じたスナップショットの圧縮、PS/2 の検出を止めるカーネルオプションなど）と、その前後の計測値は docs/OPTIMIZATIONS.md にまとまっています。

08 — API・SDK・MCP：コンソールでできることはすべて HTTP API にある

master は既定で 127.0.0.1:8080 に TLS で HTTP API を提供します。証明書は master 自身の CA で署名されるため、クライアントには ca.pem（GET /ca.pem でも取得可）を渡します。トークンは /var/lib/sandstorm/pki/api-token にあります。

主なルート（docs/API.md の「Quick look」から抜粋）
ルート内容
POST /v1/sandboxesテンプレートから起動、またはタグからフォーク。n で最大 256 個。サンドボックスのトークンはこの応答でしか返らない
POST /v1/sandboxes/:id/{touch,tier,retry}起こす、階層を動かす、失敗を再試行する
POST /v1/sandboxes/:id/{exec,eval,ping}コマンドやコード片を実行する。API トークンに加えてサンドボックスのトークンが必要
POST /v1/sandboxes/:id/branch実行中のサンドボックスをチェックポイントしてタグにする。親は短く止まったあと動き続ける
POST /v1/templates/from-imageコンテナイメージから各ノードがテンプレートを作る。ノードに Docker は不要。公開イメージのみ

外への通信（egress）

サンドボックスは既定で自分のノードの外へ何も届きません。ポリシーは internet（パブリックアドレス。プライベート範囲、他のサンドボックス、クラウドのメタデータサービスは含まない）、allow、deny（IPv4 アドレスと CIDR）の 3 つで、ドメイン名は指定できません。

{ "internet": true, "allow": ["10.1.0.0/16"], "deny": ["203.0.113.0/24"] }

クライアント

Python SDK

pip install sandstorm-sdk。依存なしで、E2B 互換の書き方ができます。SANDSTORM_URL・SANDSTORM_TOKEN・SANDSTORM_CA で接続先を渡します。

TypeScript SDK

npm install @deeplethe/sandstorm。Node 20 以上。証明書の検証を無効にする手段は意図的に用意されていません。

MCP サーバー

pip install sandstorm-mcp（0.3.0）。spawn_sandboxes、branch_sandbox、exec_command など 13 個のツールを MCP クライアントに公開します。

from sandstorm import Sandbox

with Sandbox("python") as sandbox:              # master 上のテンプレート名
    result = sandbox.commands.run("python3 -c 'print(2 + 2)'")
    print(result.stdout)        # 4

with Sandbox(tag="checkpoint-1") as sandbox:    # タグからフォーク
    print(sandbox.commands.run("ls /work").stdout)

公式の E2B SDK もそのまま使えます。master を --e2b-bind と --e2b-domain 付きで起動し、recipes/e2b-codeinterpreter で E2B の envd（固定したタグからビルド）を入れたテンプレートを作ります。E2B_API_KEY には master の API トークンを使います。

09 — 動かす

1 台で試す

cgroup v2 の Linux、PATH 上の runsc、Rust、コンソールのビルド用に Node 22.12 以上が必要です。

git clone https://github.com/deeplethe/sandstorm.git && cd sandstorm
npm --prefix web/console ci && npm --prefix web/console run build
cargo build --release -p sandstorm-core
sudo ./target/release/sandstormd serve --master --node

master と node が 1 プロセスで起動します。ブラウザで https://127.0.0.1:8080 を開き、自前 CA の警告を越えて、/var/lib/sandstorm/pki/api-token のトークンでサインインします。「+ From an image」でテンプレートを作り、そこからサンドボックスを起動します。

複数台のフリート

ssh で入れるマシンがあれば、scripts/fleet.sh で master とノードをまとめて立ち上げられます。ノードは master が配る install.sh で参加します。

scripts/fleet.sh up --master m1 --nodes n1,n2,n3 --listen 80
scripts/fleet.sh seed     # 各ノードにテンプレートを置く
scripts/fleet.sh verify   # サンドボックスを 1 つ起動して動作を確認

別のマシンのクライアントが master に接続する名前は、master の証明書に含まれている必要があります。--tls-san で追加します。すでに入っているノードや、NAT の内側から master に接続するノードは docs/API.md の Nodes の手順で参加させます。

10 — 注意点

  • アルファ版：docs/SECURITY.md は自らをアルファと位置付けています。第三者のセキュリティ監査は未実施で、1.0 までは minor バージョンで互換性が壊れることがあります。
  • gVisor は VM と同等ではない：gVisor のサンドボックスはホストのカーネルを共有するため、Sentry からの脱出はホストと同じノードの他のサンドボックスに届きます。敵対的なコードを動かすなら、KVM のあるホストで Firecracker を選ぶよう SECURITY.md は勧めています。
  • API トークンは root 相当：トークンは 1 種類でスコープもテナントもなく、master につながる全ノードのサンドボックスを操作できます。マルチテナントにするなら、テナントごとに master と専用ノードを分けるよう書かれています。--api-open で認証を外すと、届く相手なら誰でもノードトークンを発行できます。
  • 既知の穴：ノードの gateway は平文の HTTP で、サンドボックスのトークンとアプリの通信は暗号化されません。E2B 用の入口はサンドボックスのポートへのリクエストを認証しないため、ID を知っていれば到達できます。egress はアドレス単位で、ドメインでの制御や中身の検査はありません。API の監査ログは配線されていません。
  • master は冗長化されない：master の状態は SQLite 1 ファイルで、HA とフェイルオーバーは未実装です。--pki-dir の CA 鍵を失うと全ノードの再登録が必要になるため、状態 DB と一緒にバックアップします。
  • メモリ以外の上限がない：cpu.max、io.max、pids.max は API から設定できません。スナップショットのサイズにも上限がなく、1 個あたり 50.2 MiB と計測されているので、1,000 個で約 50 GB のディスクを使います。受け入れ判断はディスクを見ません。
  • 眠っている間の接続：frozen と snapshot の間に、サンドボックス内の TCP 接続はタイムアウトすることがあります。detached から戻るとメモリの状態は失われ、コールドスタートになります。
  • Kubernetes は未対応：公式のマニフェストはありません。ノードには privileged: true と root、/sys/fs/cgroup の書き込み可能なマウントが必要で、sandstormd の Pod が侵害されるとホストまで届きます。
  • 未完の項目：README のロードマップでは、配置時に master が容量を予約し、バーストがノードの直近の報告を超えないようにする項目が未完です。
