Modern Web Guidance

GoogleChrome/modern-web-guidance — コーディングエージェントに モダン Web プラットフォームの実装パターンとブラウザ互換性データを渡す SKILL.md + CLI。Google Chrome / Microsoft Edge / Mozilla Firefox / MDN の各チームとコミュニティが管理。v1.0.0（2026-11-10 時点の main）の README と SKILL.md から要約。

解決する問題

LLM の学習データにはレガシー実装が多く、エージェントはネイティブ API で足りる課題にも 肥大化した JavaScript を書きがちです。API の存在を知っていても、本番で使える実装パターンの密度が足りません。

Modern Web Guidance は、CLI 経由で トークン量を絞ったガイドをエージェントのコンテキストへ返します。重点は 3 つ: モデルが誤用しやすいブラウザ API の正しい構成、プラットフォーム API によるパフォーマンスとアクセシビリティ、重いポリフィルに頼らない軽量なフォールバック。

検索は ローカルで完結します。依存ゼロの埋め込みモデルと BM25 を npm パッケージに同梱しており、API キーは不要です。

2 — エージェントの手順（search → retrieve → 照合 → 開示）
SKILL.md の Primary Workflow

SKILL.md は、HTML/CSS とクライアント JS のタスクで 最初に実行することを要求します（ダイアログ、フォーム検証、ダークモード、Core Web Vitals、Passkeys、Built-in AI、WebAssembly など）。バックエンド、CI/CD や Docker、Vite・ESLint・テストなどのツール設定は対象外です。

Step 1 — search

ユースケース検索
npx -y modern-web-guidance@latest search "light dismiss dialog"

返却は [{ "id", "description" }, ...] の JSON 配列です。クエリの書き方に規則があります。

  • 2〜5 語、1 機能に絞る。「動詞 + UI / プラットフォームの対象」で書きます。複数機能のタスクは検索を分けます。
  • フレームワーク名とアプリ固有の名詞を入れない。React、Tailwind、コンポーネント名やルート名は除きます。
  • 意図を UI 部品に言い換える。「削除前に確認」は "confirmation modal dialog"、「日付を選ぶ」は "date picker input" とします。
  • 結果が弱いとき。具体的な部品名で 1 回だけ言い換え、それでも合わなければ list で全件を見ます。該当なしなら無関係なガイドを取得せずに進めます。

Step 2 — retrieve

ガイド本文の取得
npx -y modern-web-guidance@latest retrieve "animate-to-from-top-layer"

複数 ID はカンマ区切りで渡します。個別ユースケースに加えて、該当する分野ガイド（html、css、forms、accessibility、performance、security など）も併せて取得します。出力が 9.5 KB を超えると一時ファイルに保存されるため、そのファイルを全文読みます。

Step 3 — ガイドとの照合

実装を終える前に、取得したガイドのパターンとフォールバックが正しく入っているか、依頼を満たしているかを確認します。依頼されていない機能を足す必要はありません。

Step 4 — 利用の開示

回答の末尾に ### Modern Web Guidance 節を置き、適用したガイド id ごとに 1 項目で、採用した API やフォールバックと、防いだ落とし穴を書きます。ガイドの該当ルールを短く逐語引用します。検索したが適用しなかった場合は、確認した範囲と不採用の理由を 1 文で書きます。

フレームワークへの適用: ガイドは素の HTML/CSS/JS で書かれています。React などへ移すときも、新しい HTML 属性（popover、commandfor など）を型エラーを理由に削らず、キャストして残します。SSR では window を参照する処理をガードし、showModal() は ref 経由で呼びます。

npx 実行時の注意
  • 許可リスト: npx -y modern-web-guidance@latest * を個別に許可します。npx * 全体は許可しません。pnpm があれば pnpx を使います（-y は不要）。
  • サンドボックス: パッケージ取得に外向きネットワークが必要です。承認制の環境では初回実行の前に許可を求めます。~/.npm が読み取り専用なら NPM_CONFIG_CACHE=/tmp/npm-cache を指定します。
  • オフライン・Windows: 応答しない場合は npx --offline、Windows では npx.cmd を使います。
  • 実行環境: package.json の engines は Node.js 22 以上です。
3 — 既存コードの近代化（legacy-scan）
別系統のフロー

legacy-scan はコードベースを走査し、レガシーな Web プラットフォーム実装を検出します。使うのは、対象の機能やコンポーネントを指定しない 広い近代化依頼のときだけです。特定機能の追加・修正・監査では実行しません。

レガシーパターンの検出
npx -y modern-web-guidance@latest legacy-scan . --json
段階内容
1. Scanlegacy-scan <path> --json で検出結果を取得する。
2. Verify各検出を keepWhen / dropWhen の基準で確認し、誤検出（フォールバック、ベンダーコード、類似コード）を除く。
3. Report確認済みの検出と計画を報告する。走査対象がガイド全体の一部であることも伝える。
4. Modernize修正まで依頼されている場合のみ、各検出のガイドを retrieve して置き換え、再スキャンで解消を確認する。

オプションは --json、--guide <guideId>（特定ガイドに絞る）、--include-docs-and-tests（ドキュメント・デモ・テストも対象にする）です。パス省略時はカレントディレクトリを走査します。

検出範囲は一部です: legacy-scan が持つ決定的なルールは、ガイド全体の約 20% 分です。検出 0 件は「レガシー実装がない」ことを意味しません。意図して残したフォールバックは再スキャンでも検出され続けるため、0 件にするためのコード変更はしません。
4 — ブラウザサポート方針と機能ゲート
フォールバックの判断
  • 既定: Baseline Widely available の機能はフォールバックなしで使います。それ以外はガイドのフォールバック推奨に従います。
  • 独自方針がある場合: ユーザーの方針を優先します（例:「Safari 17.4+」「ポリフィル禁止、軽量な自前フォールバックのみ」）。Baseline YYYY を目標にする場合、ガイドの「Baseline since」が YYYY 以前なら条件を満たします。
  • 方針の記録: Electron / Tauri など対象が限られる環境や、ポリフィルの大きさを気にする場面では、AGENTS.md か CLAUDE.md に方針を書くようエージェントが提案します。

ガイド側は、古いブラウザが無視しても害のない追加的な機能（投機的プリロードなど）と、代替が必須の挙動（ダイアログ制御、ネットワークビーコンなど）を区別しています。フォールバックは 50 行未満の自前実装か条件付きポリフィルを優先し、fetchLater() の 64KB 上限のような制限も記載します。

Origin Trial と不安定な機能（.mwgrc）

Origin Trial の実験的 API と、volatile な機能（単一エンジンのみで出荷後 3 か月以内、または安定化途上）のガイドは、search には出ますが retrieve で止まります。開発者が明示的に同意するまで、エージェントは不安定な API を採用しません。

CLI コマンド.mwgrc のキー効果
set-allow-origin-trials"allowOriginTrials": trueOrigin Trial API のガイドを取得可能にする
set-allow-volatile-features"allowVolatileFeatures": truevolatile な単一エンジン機能のガイドを取得可能にする

.mwgrc はプロジェクトルートに置く JSON ファイルです。コミットすればチームで共有できます。プロジェクトに無い場合は ~/.mwgrc が使われます。

テレメトリは既定で有効です: インストール数、呼び出し元エージェント名、取得したガイド ID、エージェントが生成した検索クエリ（例: dark mode scrollbar color-scheme）が匿名で Google に送信されます。ユーザーのプロンプト原文は収集されません。検索処理自体はローカルで動きますが、クエリは送信対象です。無効にするにはシェルのプロファイルに export DISABLE_TELEMETRY=1 を追加します。
8 — 評価ハーネス
校正ループ
段階内容
開発者タスクの模擬ベースアプリ（daily-grind、devtools-times）に対する現実的な依頼文。API 名や機能名を書かず、エージェントが自力でガイドに到達できるかを測る。
静的・ブラウザ上のアサーションPlaywright のグレーダーがソースのパターン、計算済みスタイル、実行時の DOM 挙動、アクセシビリティ状態を検査する。
グレーダーの校正複数エージェント（Claude / Codex / AGY）による模範解答で 100% 合格、未変更のベースアプリで 0% 合格になることを確認する。
E2E 評価スキルあり（guided）となし（unguided）で合格率を比較する。

指標は opportunity（100% − unguided の合格率）と uplift（guided − unguided）です。ガイドなしで通る内容は削り、エージェントがつまずく箇所のガイドを改善します。トークン量を抑えられているのはこの剪定によります。
