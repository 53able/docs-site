google-research/paper-orchestra · Google Cloud AI Research · Python 3.11 · Gemini（一部 OpenAI 可）· Semantic Scholar · pdflatex / bibtex · CVPR 2025 / ICLR 2025 テンプレート · Apache-2.0

01 — 研究メモから投稿形式の論文を作るパイプライン

IDEA + EXPERIMENTAL LOG → LaTeX + PDF

アイデアのメモと実験ログだけを材料に、
文献調査・図・本文・査読対応までを順に回す。

PaperOrchestra は、論文執筆前の素材（研究アイデアの説明と実験結果のログ）から、学会テンプレートに沿った LaTeX 原稿とコンパイル済み PDF を生成するマルチエージェントの研究実装です。論文 arXiv:2604.05018 のコードとして公開されています。

処理は 5 つのエージェントに分かれます。アウトラインを作るエージェントが図の計画・文献調査の方針・各節の構成を JSON で決め、文献調査と図の生成を並列で走らせ、本文を書き、最後に LLM の査読者のスコアが上がる間だけ改稿を受け入れます。

5
エージェント（図の生成は任意）
2
同梱テンプレート（CVPR / ICLR 2025）
3
内容の改稿ラウンドの上限
5
同梱の評価スクリプト（autoraters）
何をするか

素材 → 原稿の変換

研究そのもの（実験の実行やアイデアの考案）は行いません。入力は人が書いたアイデアと実験ログで、出力はそれを論文の体裁にまとめた原稿です。実験ログにない数値や実験を足さないよう、各プロンプトで繰り返し指示しています（07）。

位置づけ

研究コードとしての公開

README の末尾に「Google の公式サポート製品ではない」と明記されています。論文の評価に使ったデータセットはリポジトリに含まれず、後日別途公開予定です。パッケージ化やテストはなく、CLI と Streamlit のデモを直接実行する形です。

02 — パイプラインの全体像

CLI の --use_plotting で 2 つの実装が切り替わります。図の生成を使わない場合（methods/paper_writer.py）は、文献調査が単独で走り、raw_materials/figures/ に置いた図をそのまま原稿に使います。図の生成を使う場合（paper_writer_with_plotting.py）は、文献調査と図の生成を 2 スレッドで並列に実行し、各段の所要時間を time_breakdown.json に記録します。

失敗したら最初からやり直す。 どの段で例外が出ても、write_single_paper はアウトラインから全体を再実行し（生成済みのファイルは上書き）、3 回失敗すると False を返して終わります。途中の段から再開する仕組みはありません。

03 — 入力として用意するもの

CLI が読むファイル（ファイル名は引数で変更可）
場所ファイル内容
--raw_materials_diridea_sparse.md問題設定、仮説、提案手法の概要、期待する貢献。--idea_filename で変更
--raw_materials_direxperimental_log.md実験設定、データセット、比較手法、数値の表、定性的な観察。--experimental_log_filename で変更
--raw_materials_dirfigures/（任意）図の生成を使わないときに原稿へ入れる図。PDF / PNG / JPG。図の一覧とキャプションは figures/info.json（name と caption の配列）から読む
--latex_template_dirtemplate.tex節の骨組み。アウトラインはここの \section{...} を土台にする
--latex_template_dirguidelines.md学会の執筆規定（ページ数、匿名化、数式・図表の書き方）。各エージェントと書式チェックが参照する

テンプレートは templates/cvpr2025 と templates/iclr2025 が同梱されています。README は、templates/ にサブフォルダを足せば独自のテンプレートを追加できると説明しています。その場合も template.tex と guidelines.md の 2 つは必須で、ないと実行前の確認で止まります。

入力の例

Streamlit デモには、CVPR 2025 の論文（TSAM: Temporal SAM Augmented with Multimodal Prompts）から抽出した素材が例として入っています（frontend/examples/cvpr_example.json）。アイデア側は「SAM は時間方向の文脈を持たず、手動プロンプトに依存する」という問題設定と、時間分岐・疎/密のプロンプト生成モジュールという手法の概要です。実験ログ側には、データセットの分割、比較手法 7 つ、本体の比較表、アブレーション表、ハイパーパラメータの感度表、定性的な観察が Markdown で書かれています。

## Problem Statement
The Segment Anything Model (SAM) has established a new baseline for static image segmentation;
however, it is structurally ill-equipped for Referring Audio-Visual Segmentation (Ref-AVS). ...
## Core Hypothesis
## Proposed Methodology (High-Level Technical Approach)
## Expected Contribution

上はアイデア側の見出し構成（抜粋）。実験ログ側は「1. Experimental Setup / 2. Raw Numeric Data / 3. Qualitative Observations」の 3 部構成です。

04 — 5 つのエージェントの入出力

  1. Outline Agent — 計画を JSON で決める

    アイデア、実験ログ、template.tex、ガイドラインを 1 回の呼び出しで読み、3 つのキーを持つ JSON を出力します。

    出力
    outline.json
    • plotting_plan: 作る図ごとに figure_id、plot_type（plot か diagram）、データの出どころ、目的、アスペクト比（12 種から選ぶ）
    • intro_related_work_plan: 序論の「導入の主張」と「問題のギャップ」の仮説、検索方針 3〜5 件。関連研究は 2〜4 の手法クラスタに分け、それぞれの限界の仮説、限界を裏づける検索クエリ、提案手法との接点を書く
    • section_plan: 残りの節（要旨、手法、実験、結論、付録）の構成と要点。使うデータセット・比較手法・指標・最適化手法・基盤モデルのすべてに citation_hints を付ける

    序論は 10〜20 本の基礎的な文献、関連研究は 30〜50 本の技術的な比較対象と、引用の層を分けるよう指示しています。

  2. Literature Review Agent — 文献を集めて序論と関連研究を書く

    アウトラインから検索タスクを作り、Gemini の Google 検索ツールで候補論文を探し、Semantic Scholar で実在と公開日を確かめてから採用します（詳細は 05）。集めた論文の要旨を渡して序論と関連研究の 2 節だけを書かせ、ほかの節は空のまま残します。

    出力
    updated_template.tex、references.bib、citation_map.json（引用キー → タイトル・要旨など）、引用候補を書き戻した outline_v1.json

  3. Plotting Agent — 図を作る（任意）

    plotting_plan の図ごとに、最大 5 並列で次の段を回します。

    • 参考例の検索: PaperBanana のベンチマークデータ（ref.json）から近い例を 10 件選ぶ。データがなければ例なしで続行
    • 計画 → スタイル調整 → 生成。plot は Gemini に matplotlib のコードを書かせて実行し、diagram は画像生成モデル（既定 gemini-3-pro-image-preview）で描く
    • 批評ラウンド: 生成画像を見て修正点を出し、作り直す。「No changes needed.」が返るか --plotting_max_critic_rounds（既定 3）回で終了
    • キャプションを生成
    出力
    plotting_results.json、画像ファイル、latex_writeup/figures/info.json

  4. Section Writing Agent — 残りの節と表を書く

    序論と関連研究が入った template.tex に、要旨・手法・実験・結論・付録を書き足して全文を返させます。図はファイル名とキャプションの一覧に加えて、PNG / JPG なら画像そのものを渡し、図の内容と矛盾する説明を書かないよう指示します。表は booktabs 形式で、数値は実験ログの値をそのまま使います。

    出力
    latex_writeup/raw_draft_paper.tex

  5. Content Refinement Agent — 査読と改稿を繰り返す

    草稿を pdflatex → bibtex → pdflatex ×2 でコンパイルし、LLM の査読者（autoraters/agent_review.py）にスコアと講評を出させ、講評に沿って改稿させます。改稿を受け入れるかはスコアで決めます（06）。内容の改稿のあと、ページ画像を VLM に見せて図表のはみ出しなどを指摘させる書式修正を 1 回行います。

    出力
    content_refinement_workdir/ 内の各版の tex / PDF、peer_reviews/、作業ログ。最終版を final_paper.pdf にコピー

05 — 文献の集め方と検証

文献調査エージェントは、LLM が挙げた論文をそのまま引用せず、外部のデータベースで照合できたものだけを残します。

methods/agents/literature_review_agent.py と utils/scholar_utils.py の処理
段階処理
検索タスクの作成序論の検索方針と関連研究の限界クエリは「探索」タスク、citation_hints は「狙い撃ち」タスクにする
候補の発見Gemini に Google 検索ツールを持たせて候補を返させる（最大 10 並列）。探索は 10〜15 本、temperature 0.4。狙い撃ちは元論文 1 本を探し、temperature 0.1。どちらもプロンプトに公開日の上限を書く
実在の確認候補のタイトルで Semantic Scholar の検索 API を引き、上位 3 件とのタイトルのあいまい一致率（発行年が合えば +10）が 70 を超えたものだけを採用
除外公開日が --research_cutoff（既定は実行時の年月）より後の論文、要旨が取れない論文は捨てる。要旨は 1,500 文字で切る
引用資産の生成著者・年・タイトルから引用キーを作り、references.bib と citation_map.json を出力。見つかった論文をアウトラインの該当節へ書き戻す
執筆集めた論文の 9 割以上を序論と関連研究で引用し、citation_checklist にあるキー以外は使わないよう指示する
カットオフ日は「先行研究」と「同時期の研究」を分けるためにも使う。 カットオフ後の論文は比較対象として扱わず、実験ログで実際に比較していない論文に対して「上回った」と書かないよう、執筆プロンプトで指示しています。

06 — 改稿を受け入れるかの判定

査読者は総合スコア（Overall、1〜10）と、独創性・品質・明瞭さ・重要性・健全性・表現・貢献の 7 軸（各 1〜4）、確信度（1〜5）、Accept / Reject の判定、強み・弱み・質問を返します。改稿エージェントは改稿版をコンパイルして再査読し、前の版と比べて次のように判定します。

ContentRefinementAgent.run の分岐（Overall と Confidence 以外の軸の増減を合計して比較）
条件記録される結果次の動作
Overall が上がったACCEPTED_SCORE_INCREASE改稿版を採用して次のラウンドへ
Overall が同じで、各軸の上昇の合計 ≥ 下降の合計ACCEPTED_NEUTRAL_IMPROVEMENT改稿版を採用して次のラウンドへ
Overall が同じで、下降の合計 > 上昇の合計REJECTED_DEGRADATION前の版に戻してループを終了
Overall が下がったREJECTED_SCORE_DECREASE前の版に戻してループを終了

ラウンドの上限は 3 です。その後の書式修正は内容の変更を禁じたうえで 1 回だけ行い、コンパイルできれば採用（ACCEPTED_COMPILE_SUCCESS）、できなければ書式修正前の版を残します。

新しい実験の要求には応じない。 査読者が実験ログにない追加実験や比較を求めても、改稿エージェントはその要求を無視し、既存の結果の見せ方だけを直すよう指示されています。回答は別紙の反論文ではなく、本文の該当箇所に書き込みます。

07 — 捏造と情報漏れを防ぐ指示

すべての執筆系プロンプトの末尾に、utils/prompt_utils.py の UNIVERSAL_NO_LEAKAGE_PROMPT が付きます。

KNOWLEDGE ISOLATION

与えた素材だけで書く

学習データの知識に頼らない、既存の論文を思い出して再構成しない、外部の事実を持ち込まない、と指示します。評価用に既存論文から素材を抽出して再生成するとき、元の論文の記憶で書くのを防ぐための指示です。

ANONYMITY

二重盲検用に匿名化する

著者名、所属、謝辞、「corresponding author」などを推測して入れないよう指示します。同梱の CVPR ガイドラインも、自己引用を第三者として書くことなどを定めています。

エージェントごとの個別の指示
エージェント指示の内容
Outline問題のギャップと主張は、実験ログにあるデータセットと評価の範囲に合わせる。著者が分からない文献は推測せず「'X' を提案した論文」と書く
Literature Review渡した論文以外は引用しない。実験ログで比較していない論文を「上回った」と書かない
Section Writing表の数値は実験ログの値をそのまま使う。素材で裏づけられない数式を足さない。渡した図はすべて使い、画像と矛盾する解釈を書かない
Content Refinement数値の主張はすべて実験ログで確かめる。引用は citation_map.json のキーだけを使う
限界を書かない指示がある。 改稿エージェントのプロンプトには「Never explicitly state a limitation.」という一文があります（本文執筆エージェントは「限界と今後の課題に触れるのが望ましい」と指示）。査読スコアを上げる方向に働く一方、実際の投稿原稿に使うなら、限界の記述は人が確認して補う必要があります。

08 — 出力ディレクトリの中身

--output_dir を省略すると ./paper_output_<日時> が作られます。主なファイルは次のとおりです。

paper_output_xxx/
├── raw_materials/                  # 入力のコピー
├── outline.json                    # 文献調査後は outline_v1.json で上書き
├── literature_agent_output/        # references.bib, citation_map.json, updated_template.tex
├── plotting_results.json           # --use_plotting 時
├── latex_writeup/
│   ├── template.tex, references.bib, guidelines.md, *.sty
│   ├── figures/ (+ info.json)
│   └── raw_draft_paper.tex         # 本文執筆エージェントの草稿
├── content_refinement_workdir/
│   ├── peer_reviews/review_v0.json …   # 各版の査読結果
│   ├── pdf_screenshots/                # 書式チェック用のページ画像
│   ├── content_refinement_worklog.json # 各ラウンドのスコアと採否
│   ├── format_refinement_worklog.json
│   └── final_refined_paper.pdf
├── time_breakdown.json             # --use_plotting 時。各段の秒数
└── final_paper.pdf                 # 最終版

ディレクトリ名は methods/paper_writer*.py と content_refinement_agent.py のコードから整理したもの。各版の tex / PDF など、一部は省略しています。

09 — 評価スクリプト（autoraters）

autoraters/ には、生成した論文を評価するためのスクリプトがあります。論文の評価実験で使ったもので、agent_review.py だけはパイプライン内の査読にも使われます。

各スクリプトの役割（コードから要約）
ファイル評価の内容
agent_review.pyAgentReview 形式の査読。強み・弱み・質問と、Overall（1〜10）を含む複数軸のスコアを JSON で返す。メタレビューの関数もある
citation_f1.py元論文の参考文献を LLM で P0（必須）/ P1（あるとよい）に分類し、生成論文の引用と照合して適合率・再現率・F1 を出す。Semantic Scholar を使い、datasets/ を前提にする
lit_review_quality.py序論・関連研究の質を節ごとに 0〜100 点で採点し、根拠を書かせる
sxs_lit_review_quality.py2 本の論文の文献レビューを並べて比較する
sxs_paper_quality.py2 本の論文の PDF をページ画像にして並べ、論文全体の質を比較する

いずれもバッチ処理用の関数として書かれており、CLI の引数解析はありません。使うには Python から関数を呼び出します。データセットが未公開のため、README どおりにそのまま再現できる状態ではありません。

10 — 実行方法

  1. 環境を作る

    conda create -n paper_orchestra python=3.11
conda activate paper_orchestra
pip install -r requirements.txt

    PDF のコンパイルに pdflatex と bibtex を使うため、TeX Live などの LaTeX 環境も必要です（requirements.txt には含まれません）。

  2. .env に API キーを書く

    SEMANTIC_SCHOLAR_API_KEY=...
GEMINI_API_KEY=...                 # または VERTEX_AI_PROJECT と VERTEX_AI_LOCATION（Vertex が優先）
OPENAI_API_KEY=...                 # OpenAI のモデルを使う場合のみ
SMTP_EMAIL=... / SMTP_PASSWORD=... # デモで完了メールを送る場合のみ

    2026-11-15 のコミットで、使うプロバイダーのキーだけを要求するように変わりました。Gemini のクライアントは Gemini のモデルを最初に呼ぶときに作られます。

  3. CLI で 1 本書く

    python paper_writing_cli.py \
  --raw_materials_dir ./my_materials/ \
  --latex_template_dir templates/cvpr2025 \
  --output_dir ./paper_output_my_paper \
  --use_plotting true
    paper_writing_cli.py の引数
    引数既定値内容
    --raw_materials_dir（必須）アイデアと実験ログのディレクトリ
    --latex_template_dir（必須）テンプレートのディレクトリ
    --output_dir./paper_output_<日時>出力先
    --idea_filenameidea_sparse.mdアイデアのファイル名
    --experimental_log_filenameexperimental_log.md実験ログのファイル名
    --writer_model_namegemini-3.1-pro-previewアウトライン・文献調査・本文執筆のモデル
    --reflection_model_namegemini-3.1-pro-preview改稿エージェントのモデル
    --research_cutoff実行時の年月文献の公開日の上限（例: 2024-11）
    --use_plottingFalse図の生成を有効にする（true / 1 / yes）
    --plotting_model_namegemini-3.1-pro-preview図の計画・コード生成・批評のモデル
    --image_model_namegemini-3-pro-image-preview概念図を描く画像生成モデル
    --plotting_max_critic_rounds3図の批評ラウンドの上限

    paper_writing_cli.sh は、データセット内の論文 ID を指定して nohup conda run でバックグラウンド実行する例です。データセットが公開されるまではパスを自分の素材に書き換えて使います。

  4. Streamlit のデモで試す

    streamlit run frontend/app.py   # 通常は http://localhost:8501

    サイドバーでモデル（gemini-3.1-pro-preview / gemini-3-flash-preview）、テンプレート、図の生成の有無、通知先のメールアドレス（必須）を選び、アイデアと実験ログを貼り付けるかファイルで渡します。CVPR の例を読み込むボタンもあります。デモは裏で paper_writing_cli.py を起動し、執筆の進捗と改稿の各版を表示します。

11 — 使う前に確認すること

コードと README から確認した注意点
項目内容
OpenAI で動く範囲モデル名で Gemini / OpenAI を切り替える共通関数（utils/llm_backend_utils.py）を通るのは本文執筆エージェントだけ。アウトライン、文献調査（Google 検索ツールを使う）、改稿、図の生成、査読は Gemini の関数を直接呼ぶ。--writer_model_name に GPT 系を指定してもアウトラインの段で Gemini として呼ばれる
生成コードの実行図の生成では、LLM が書いた matplotlib のコードを exec() でそのまま実行する。サンドボックスはないため、隔離した環境で動かすのが安全
API キーの表示utils/scholar_utils.py は読み込み時に Using S2 API Key: ... と Semantic Scholar のキーを標準出力に出す。ログを共有するときは伏せる
PaperBanana の参考データ図の参考例はリポジトリの 1 つ上の階層にある PaperBanana/data/PaperBananaBench/ を読む。リポジトリには含まれず、ない場合は警告を出して例なしで生成する
図の 2 つのモード図の生成を有効にすると、raw_materials/figures/ の手持ちの図は原稿用フォルダにコピーされない（生成した図だけを使う）。無効のときは figures/info.json がないと本文執筆エージェントに「図なし」と伝わる
データセット論文の評価に使ったデータセットは未公開。paper_writing_cli.sh と citation_f1.py は datasets/ の存在を前提にしている
コストと時間文献調査は検索タスクごとに LLM と Semantic Scholar を呼び、改稿は各ラウンドでコンパイルと査読を行う。例外時は全体を最大 3 回やり直すため、呼び出し回数は入力と失敗の有無で大きく変わる
Semantic ScholarAPI キーなしでも検索は試みるが、タイムアウト 5 秒・失敗時は候補を捨てる実装のため、レート制限にかかると集まる文献が減る
デモの後始末サーバー停止時に子プロセスを止める仕組みは Linux の prctl を使う。ほかの環境や接続が切れた場合は pkill -f paper_writing_cli.py で手動で止める
出力の扱い改稿の採否は LLM 査読のスコアで決まり、内容の正しさを保証する仕組みではない。限界を書かない指示もある（07）。投稿や公開に使う場合は、引用・数値・主張を人が確認する
