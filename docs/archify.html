Archify

agent skill for architecture · workflow · sequence · dataflow · lifecycle — tt-a1i/archify v2.16.0

1 — 概要
何をするか

Archify は Cursor、Claude Code、Codex CLI、opencode 向けの Agent Skill。システムの説明・リポジトリ・Mermaid 断片を受け取り、エージェントが型付き JSON IR を書き、Archify がそれを決定論的に自己完結 HTML へコンパイルする。出力はブラウザで開き、テーマ切替（T）・スタイル切替（S）・エクスポート（E）が使える。リポジトリは tt-a1i/archify、現行安定版は v2.16.0。

5 modes図タイプ
JSON IR型付き中間表現
9 checksshowcase 合格条件
0 deps検証もスタンドアロン
  • 汎用 auto-layout や Mermaid テーマではなく、階層・間隔・経路・強調をエージェントが判断する。共有された自動接続点は決定論的に分散し、1 点に矢印が集まらない
  • 納品前に schema・レイアウト・HTML/SVG・経路・ラベル余白の検査を全通過させる。失敗時は Node のスタックではなく、ルールコードと対象と実測値を含む修復用 JSON が返る
  • 読者側の操作はすべて「書かれた事実」の範囲に閉じる。検索・上流/下流到達・経路プローブ・ロール比較・ガイド付きストーリーは、トポロジを創作せず実行時影響も主張しない
  • 成果物は 1 枚の HTML。書き出しは常に図全体で、一時的なビューア状態を含まない

3 — 図の種類
質問に合わせたモード選択

1 枚でリポジトリ全体を説明しようとせず、見たい観点を 1 つ選ぶ。どれを選ぶか迷ったら、CLI に聞ける。

node bin/archify.mjs guide "Show an API request with Redis cache miss"
node bin/archify.mjs guide "Map Kafka topics, consumer groups, replay, and DLQ" --json

architecture

コンポーネント・クラウド資源・境界。主経路と trust boundary。任意で deployment-ownership プロファイルを有効にすると、担当者・リージョン・DB のプライベート配置・境界越えラベルが揃わない限り fail closed になる。

workflow

CI/CD・承認・ツール呼び出し・ランブック。新規は schema_version: 2 の readable-v2 契約で、列 0..5 は論理ランクのまま配置とラベル余白をコンパイラが決める。既存 v1 の固定座標は維持される。

sequence

API 呼び出し連鎖・キャッシュフォールバック・非同期トレース。既定は固定幅レイアウト。参加者ラベルが収まらないときだけ meta.column_fit: "spread" にする。

dataflow

パイプライン・系譜・PII 境界。ステージ横断の flow ラベルと classification。

lifecycle

状態機械・待機・リトライ・終端。フェーズ列 0..4 が主レールを占め、イベント / 終端列 N（0..2）は主列 N + 2 の真下に揃う。復帰可能な状態は type: "failure" に加えて、実際に稼働状態へ戻る遷移を持たせる。

Mermaid 入力

貼られた Mermaid を機械パースして描画するのではなく、構造だけ読んで archify スタイルで置き直す。flowchart → workflow（またはコンポーネントなら architecture）、sequenceDiagram → sequence、stateDiagram → lifecycle。スタイル指定は捨て、トポロジと意味だけ残す。

4 — 処理の流れ
JSON IR → validate → deliver → visual-check

5 モードとも同じループ。レンダラのソースを触らず、診断が指した箇所だけ JSON を直して再実行する。

flowchart TD
  A["Generate typed JSON IR"] --> B["validate --quality showcase --json"]
  B -->|diagnostics| E["診断された subject だけ直す"]
  E --> B
  B -->|pass| P["preview（任意 / last-good ループ）"]
  P --> D["deliver（原子的に置換 + 受領書）"]
  B -->|pass| D
  D --> V["visual-check（ブラウザ実測）"]
  V --> R["人による知覚レビュー"]
01
スキーマと例を読む

該当する schemas/<type>.schema.json、schemas/common.schema.json、そして examples/ の同型 JSON を 1 本だけ読む。例はフィールド形状の参照で、事実の流用元ではない。

02
まず候補を書く

レンダラ内部を覗く前に候補ファイルを書く。主経路 1 本、短い枝、疎なラベル、主要ノードは 12 個まで。meta.quality_profile: "showcase" を既定にする。

03
毎回 validate する

validate <type> <candidate>.json --quality showcase --json。artifact 検査 4 項目だけの受領書は基本検証で、showcase 合格ではない。9 項目すべてと composition エラー 0・警告 0 が条件。

04
deliver で確定する

deliver <type> <candidate>.json <out>.html --quality showcase --json。仕様のバイト列を凍結し、検査を通った候補だけを原子的に置換して、双方の SHA-256 とバイト数を返す。

3 つの主張を混ぜない: deliver は決定論的な成果物検査を証明し、visual-check <out>.html --json は実ブラウザでの挙動を 1440×900 / 1600×1000 / 1920×1080 / 2048×1320 で実測する（受領書は visualReview: "pending" のまま、Chrome が無ければ skipped）。見た目の良否の判断は人間または画像を見られるレビュアーの担当。
失敗の扱い: 非ゼロ終了を成功と書かない。deliver が失敗したときは前の成果物がそのまま残るので、そのパスに visual-check をかけても古い last-good を見てしまう。診断の subject と evidence を確認し、supportedFixes の範囲だけ直す。2 ラウンド続けてエラー最小値が改善しなければ止めて未解決の診断を報告する。
手置きフォールバック: シェルが使えないときは assets/template.html に architecture の SVG を手配置。色はインラインではなく CSS のセマンティッククラスを使う。テーマ切替が壊れない。
5 — レイアウト原則
空間ナラティブ

可読性は「全依存を矢印で描くこと」ではなく、1 本の物語が辿れる配置から来る。

  1. 主経路は 1 本 — 枝は主経路の最近傍ノードから出す。ルーティング制御を足す前に、価値の低いエッジを削る。
  2. ラベルは意味データ — 衝突したらまずラベルを移し、経路と間隔を調整し、最後に意味を保ったまま短くする。削除は幾何の修復ではない。両端点から完全に自明で、プロトコル・動作・方向・同期性・境界越えの情報を含まない場合だけ省く。
  3. 間隔は「空き」で測る — 中心間距離ではなく実際のクリアランス。ラベルの空きは実測マスク幅を超えていること。
  4. 自動経路は端点の面を所有する — 面は方向の契約で、最初と最後のセグメントはその面に垂直に出入りする。診断が求めるまで via / channelX / channelY / labelAt を書かない。1 回の修復で足す幾何制御は 1 つまで。
  5. 詳細はカードへ — ポリシーや技術メモは summary cards に置き、矢印を増やさない。不透明な無関係ノードを横切るエッジ、曖昧な共有通路、他の経路を覆うラベルは受け入れない。
1 画面に収める

スタンドアロンのデスクトップビューアは「最初の 1 画面で完結する成果物」として作る。1 枚のレスポンシブ HTML で済ませ、デバイス別 HTML や別トポロジは作らない。ビューアが調整してよいのは外側の読み幅だけで、authored な SVG / viewBox・比率・意味的な配置・通常の文書フローは保つ。

  • 納品前に実 HTML を 1440×900・1600×1000・1920×1080 で開く。大画面向けなら 2048×1320 も見る。各サイズで scrollWidth <= innerWidth と scrollHeight <= innerHeight を満たすこと。
  • あふれたら、ノード・ラベル・主パネルを縮める前に、本当に冗長な内容を削るか間隔を詰める。
  • 最大サイズで下部に目立つ空き帯が残るなら、authored な Y 座標を再配分して viewBox の高さを比例して増やす。埋め草の文や装飾カードは足さない。
  • overflow: hidden、内部スクローラ、SVG 高さの引き伸ばし、文字の縮小で合格を偽装しない。狭い画面では縦スクロールしてよい。
既定は省略、明示だけ有効化

7 — 差分レビュー（Architecture Delta）
マージ前に構成変更を読む

設計レビューや PR レビューでは、検証済みの architecture スナップショット 2 つを比べる。compare は両方を独立に検証し、authored な安定 ID だけでコンポーネントと関係を対応付け、追加・削除・変更・移動・経路変更を分けて分類する。

node archify/bin/archify.mjs compare architecture base.json head.json architecture-delta.html --json
  • 削除されたノードと関係は元の座標を保ち、移動したノードは MOVE FROM のファントムを残す。端点が変わった関係は旧経路と新経路の両方を出す。
  • + / ~ / − / ↔ と線種で意味を示すので、色やモーションに依存せず読める。
  • 整形・キー順・要素順・wraps・sources の集合的な変更はセマンティックハッシュと成果物バイト列を変えない。失敗時は前の成果物が残る。
  • リポジトリの不一致、共有コンポーネント ID がゼロ、関係 ID の欠落、境界キーの曖昧さは fail closed。
  • 成果物は AUTHORED SNAPSHOTS と表示し、リポジトリ証拠のゲートを両方通ったときだけ REVISION-PINNED INPUTS になる。
主張の境界: Delta は authored な事実の差分だけを述べる。リスク、影響範囲、安全性、マージ可否、検証済みの PR 影響は主張しない。Review 再生はビューア専用で、1 回の明示的な起動で安定順に 1 回だけ進み、ループしない。

現行版と非目標

v2.16.0（2026-08-30）は workflow の制約駆動コンパイラ（schema v2 の readable-v2 契約と --layout-json 受領書）、5 レンダラの meta.locale による範囲限定ローカライズ、通知のみの組み込み更新チェックを追加した。自動 Mermaid パース、汎用 auto-layout、ホスティング共有、WYSIWYG 編集は意図的に現在のスコープ外（ROADMAP.md、CHANGELOG.md）。
