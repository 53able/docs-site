01 — エージェントとアプリをつなぐイベントプロトコル

ONE INPUT IN, ONE EVENT STREAM OUT

アプリは RunAgentInput を 1 つ送り、
エージェントは型付きイベントの列で答える。

AG-UI（Agent–User Interaction Protocol）は、AI エージェントとユーザーが触るアプリケーションの間の通信を標準化するオープンなプロトコルです。エージェントはトークンを少しずつ返し、応答の途中でツールを呼び、状態を更新し、人の判断を待ち、サブエージェントを起動します。README は、こうした挙動がリクエスト／レスポンス型に収まらず、フレームワークごとに配線が異なることを課題に挙げ、それを 1 本のイベントストリームに置き換えると説明しています。

アプリが送るのは RunAgentInput（会話、アプリ側のツール、共有状態、コンテキスト）だけで、エージェントはテキスト、ツール呼び出し、状態、推論、進捗などを型付きのイベントとして流します。同じエージェントを Web アプリ、モバイル、ターミナル、Slack から使えます。

02 — MCP・A2A・生成 UI 仕様との関係

README は AG-UI を、互いに補い合う 3 つのエージェント向けプロトコルの 1 つと位置づけています。1 つのエージェントが 3 つすべてを使うことも多く、AG-UI の後ろに MCP や A2A を話すエージェントを置くこともできます。

03 — 1 回の run の流れ

やり取りの単位は run です。アプリが RunAgentInput を 1 つ送って run を開き、エージェントは RUN_STARTED と RUN_FINISHED（または RUN_ERROR）で囲んだイベント列を返します。会話（thread）は同じ threadId を持つ run の連なりで、メッセージと状態は run をまたいで蓄積されます。

ONE WAY IN

アプリから送るのは 1 回だけ

消費側からエージェントへ流れるメッセージは RunAgentInput 1 つで、run の途中にアプリから送る経路はありません。承認やツールの結果は、run をいったん終えて次の run の入力に載せます（06）。

NO SIDE CHANNEL

見えるものはすべてストリームにある

エージェントの見える振る舞いを別経路で送りません。入力とそれに答えたイベントを記録すれば、UI が各時点で何を知っていたかを再現できる、というのが仕様の設計原則です。テストやリプレイがしやすく、トランスポートにも依存しません。

仕様は 2 つの役割を区別します。イベントを出す側を producer（エージェント、プロキシ、ブリッジ、テストダブル）、読む側を consumer（クライアント SDK、UI、レコーダー、別のプロキシ）と呼び、各ルールがどちらを縛るかを明記しています。

04 — RunAgentInput のフィールド

仕様 1.0「Run Input」より
フィールド必須内容とルール
threadId / runId必須会話と run の識別子。RUN_STARTED と RUN_FINISHED はこの値を持つ。parentRunId は別の run から起動されたときに任意で付ける
messages必須それまでの会話全体。producer はこれを完全な履歴として扱う。画像・音声・動画・文書の content part も載る。使えない part があっても run を失敗させず、飛ばして続ける
tools任意アプリ側で実行する「フロントエンドツール」の一覧。省略と空配列は同じ意味
context任意説明と値の組。producer はモデルが参照できるように注入する（方法はシステムプロンプトなど実装次第）
state任意run の開始時点の共有状態。省略は {}。最初のスナップショットまでは、差分はこの値を基準に計算する
forwardedProps任意アプリ固有の値をそのまま渡す経路。中継者は変更してはならない
resume任意前の run が割り込み（interrupt）で終わったときの回答（06）
protocolVersion任意consumer が話すバージョン。producer は RUN_STARTED.protocolVersion で自分のバージョンを返す。省略はバージョン導入前の相手を意味する
activity メッセージは送り返さない。 進捗表示用の activity メッセージは consumer 側の描画材料であり、consumer は messages から除いてから送ります。パースできない入力や既知フィールドの不正値は、RUN_STARTED の前にトランスポートのエラーとして拒否されます。

05 — 8 つのイベントファミリー

必須なのは run の開始と終了だけで、最小のエージェントは数個のイベントを出せば動きます。その他のファミリーは、出す内容があるときに使います。

README の Event reference と仕様 1.0 の Event Streams より
ファミリーイベント用途

Text messagesTEXT_MESSAGE_START _CONTENT _END _CHUNKテキストの逐次送信。_CHUNK は開始・本文・終了をまとめた簡略形で、クライアントが展開する
Tool callsTOOL_CALL_START _ARGS _END _RESULT _CHUNK引数のストリーミングと結果。1.0 で結果に文字列だけでなく画像や文書の part を入れられるようになった

PassthroughRAW CUSTOM外部システムのイベントやアプリ固有のイベントを通す

06 — run の終わり方と、次の run への引き継ぎ

1.0 で RUN_FINISHED に outcome が加わり、run がどう終わったかを区別できるようになりました。run の途中にアプリから送る経路がないため、外部の入力が必要な場合は run を終えて、次の run がその答えを運びます。

仕様 1.0「Runs and Steps」「Tool calls」「Interrupts and Resume」より
終わり方いつ使うか次の run で渡すもの
success（outcome 省略も同じ）完了した通常の新しい run
success ＋ pendingToolCallIdsフロントエンドツールを呼んで止まった。producer は結果を作らない呼び出しごとの tool メッセージを messages に入れる。失敗や拒否も「答え」として返す
interrupt承認・認証情報・選択など、外からの入力を求めて止まった。Interrupt を 1 つ以上持つresume に割り込みごとのエントリ（回答か abandoned）を入れる
cancelledユーザー・アプリ・producer の上限などで意図的に止めた。失敗ではない通常の新しい run（resume ではない）
RUN_ERROR失敗した—（consumer は失敗として扱い、成功と報告しない）

interrupt と resume のルール

  • 割り込みの id は run 内で一意。reason は自由な文字列、message は人向けの説明、toolCallId は承認対象のツール呼び出し、responseSchema は回答の形（フォームを組み立てるため）。
  • resume は直前の割り込みをすべてカバーしなければなりません。エントリがないことは放棄の意味になりません。この確認は consumer の責任で、欠けていれば run を始める前に拒否します。
  • producer は前の run の割り込みを覚えておく必要がなく、状態を持たない実装でも適合します。ただし未回答の割り込みに気づいた場合、その操作を実行したり success で終えたりしてはいけません。
  • expiresAt を過ぎた割り込みには回答できず、abandoned として明示的に閉じます。
フロントエンドツールと interrupt は別の往復です。 フロントエンドツールの呼び出しは通常の会話履歴で答え、run は success で終わります（地図の表示や画面遷移のように、結果が次の run を必要としないことも多いため）。interrupt は producer が明示的に「止まって尋ねる」ときの仕組みで、resume で答えます。

07 — 共有状態と会話履歴の同期

STATE_SNAPSHOT

全置換

consumer は状態をそのまま置き換え、マージしません。差分で表せない変更や、再同期に使います。

STATE_DELTA

JSON Patch で差分

基準は consumer の現在の状態です。run の最初は入力の state、以降はその run のスナップショットと差分を適用した結果です。

MESSAGES_SNAPSHOT

会話全体の再提示

同じ id は位置を保ったまま置き換え、新しい id は末尾に追加し、含まれないものは削除します。activity と reasoning のメッセージは削除の対象外です。

状態は置き換えられるまで thread 内で保持され、次の run の入力 state として送り返されます。これで両者が同じ値を共有し続けます。仕様は、状態とメッセージが毎回往復するため、producer がそこに秘密情報を入れないよう求めています（SHOULD NOT）。

08 — 処理モデル：未知は除去、既知の不正は失敗

仕様の設計原則は「読む側は寛容に、書く側は厳格に」です。producer は schema が定義するものだけを出し、consumer は知らないものに出会っても run を止めません。ただし、知っているフィールドに不正な値が入っていれば run を失敗させます。

仕様 1.0「Processing Model」より
受け取ったものconsumer の扱い
知らない型のイベントrun を止めずにイベントごと捨て、型名を警告する
知らないプロパティ・union のメンバーその部分だけ取り除き、パスを警告する。必須の位置にあれば、それを含む値ごと除く
既知のフィールドに schema が許さない値（例：数値の messageId）修正・型変換・無視をせず、run を失敗させる
JSON Patch 操作の未定義メンバーRFC 6902 に従い、保持する（除去しない）

クライアントの処理は「互換変換 → ミドルウェア → 検査（除去）→ チャンク展開 → 検証」の順です。ミドルウェアが除去より前に動くので、古い形のイベントを境界で新しい形に変換でき、新しい拡張も理解できる相手まで届きます。SSE と Protobuf のどちらで届いても、同じイベントには同じ判定を下すことが求められます。

import { HttpAgent } from "@ag-ui/client"

const agent = new HttpAgent({ url: "http://localhost:8000/" })

// 関数形式のミドルウェア：logging → auth → filter → エージェントの順に包む
agent.use(loggingMiddleware, authMiddleware, filterMiddleware)

await agent.runAgent()

docs/concepts/middleware.mdx の例を簡略化。agent.use() のミドルウェアは runAgent() で適用され、connectAgent() では現在適用されません。

09 — トランスポート

仕様は 2 つのバインディングを定め、どちらでもイベントの意味は変わりません。独自のバインディングも、仕様の「binding contract」を満たせば使えます。

仕様 1.0「HTTP + SSE」「HTTP + Protobuf」より
項目HTTP + SSEHTTP + Protobuf
リクエストPOST、本文は JSON の RunAgentInput。Accept: text/event-stream（Protobuf を受けられるなら application/vnd.ag-ui.event+proto も並べる）
応答の形data: 1 つにイベント 1 つ（JSON）。改行は LF4 バイトのビッグエンディアン長 ＋ エンコード済みイベント 1 つのフレームが続く
選択常に受けられるよう準備する（producer が Protobuf 非対応なら SSE が返る）Accept が許せば producer が選ぶ。Content-Type でパーサーを決める
開始後の失敗ストリーム内の RUN_ERROR。HTTP 200 だけで成功と判断してはいけない
途中で切れた場合終了イベントのない「truncated run」。再接続はなく、やり直しは新しい runId の run

10 — 最小構成：30 行のサーバーとクライアント

AG-UI のエージェントは「RunAgentInput を受け取り、イベントをストリームで返す HTTP エンドポイント」です。README の例は API キーなしで動きます。

エージェント（Python 3.9+、FastAPI）

pip install ag-ui-protocol fastapi uvicorn
# server.py
import uuid
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from ag_ui.core import (
    PROTOCOL_VERSION, RunAgentInput, RunStartedEvent, RunFinishedEvent,
    TextMessageStartEvent, TextMessageContentEvent, TextMessageEndEvent,
)
from ag_ui.encoder import EventEncoder

app = FastAPI()

@app.post("/")
async def run_agent(input_data: RunAgentInput, request: Request):
    encoder = EventEncoder(accept=request.headers.get("accept"))

    async def events():
        yield encoder.encode(RunStartedEvent(
            thread_id=input_data.thread_id, run_id=input_data.run_id,
            protocol_version=PROTOCOL_VERSION,
        ))
        message_id = str(uuid.uuid4())
        yield encoder.encode(TextMessageStartEvent(message_id=message_id, role="assistant"))
        for chunk in ["Hello ", "from ", "AG-UI!"]:
            yield encoder.encode(TextMessageContentEvent(message_id=message_id, delta=chunk))
        yield encoder.encode(TextMessageEndEvent(message_id=message_id))
        yield encoder.encode(RunFinishedEvent(thread_id=input_data.thread_id, run_id=input_data.run_id))

    return StreamingResponse(events(), media_type=encoder.get_content_type())

クライアント（TypeScript、Node.js 20+）

// client.ts — npm install @ag-ui/client tsx
import { HttpAgent } from "@ag-ui/client";

const agent = new HttpAgent({ url: "http://localhost:8000/" });

agent.addMessage({ id: crypto.randomUUID(), role: "user", content: "Hi there!" });

await agent.runAgent({}, {
  onRunStartedEvent: ({ event }) => console.log(`run started (AG-UI ${event.protocolVersion})`),
  onTextMessageContentEvent: ({ event }) => { process.stdout.write(event.delta); },
  onRunFinishedEvent: () => console.log("\nrun finished"),
});

uvicorn server:app --port 8000 で起動し、npx tsx client.ts を実行すると Hello from AG-UI! が流れます。サーバーを対応フレームワークのものに替えても、クライアントは変わりません。

アプリの雛形から始める場合は npx create-ag-ui-app@latest を使います。フロントエンド（Next.js 上の CopilotKit か、ターミナルクライアント）と、選んだエージェントフレームワークをつないだ構成を生成します。テンプレートは OpenAI を呼ぶため、npm run dev の前に OPENAI_API_KEY を設定します。

12 — 使う前に確認すること

仕様 1.0 とドキュメントに書かれた注意点
項目内容
モデル出力は信頼しないツール引数・ツール結果・状態・RAW / CUSTOM の payload は信頼境界を越えて届く。アプリは実行前に検証し、ストリームの内容を実行可能なマークアップとして描画してはいけない（MUST NOT）
副作用のあるツール実行前のユーザー同意を取るべき（SHOULD）。承認していない操作を「承認済み」と表示してはいけない（MUST NOT）。プロトコル自体は同意を強制しない
Python / .NET SDK の除去処理仕様は未知のプロパティをアプリに渡す前に除去するよう求めるが、Python と .NET のモデルは寛容にパースするだけで、除去の段階をまだ持たない。閉じた文字列集合（role など）の未知の値は、TypeScript の参照実装でも除去ではなく失敗になる
HTTP 200 と成功ストリーム開始後の失敗は RUN_ERROR で届く。ステータスコードだけで成功を判断しない
再接続なしSSE の Last-Event-ID は使わない。切れたストリームには戻れず、新しい run としてやり直す
capabilities は参考情報AgentCapabilities の宣言は省略＝非対応ではなく「未宣言」。宣言と異なるイベントが来ても consumer は拒否しない。取得方法は仕様で定めていない
新しい outcome と古い consumer知らない outcome は除去され、省略扱い＝success として読まれる。cancelled が 1.0 で定義されたのはこのため
ミドルウェアの適用範囲agent.use() のミドルウェアは runAgent() にだけ適用され、connectAgent() には現在適用されない
ドキュメント間の差docs/concepts/architecture.mdx には「16 種類のイベント」とあり、1.0 の 31 種類と一致しない。規範は仕様 1.0（docs/spec/1.0）と schema.json
