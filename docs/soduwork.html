01 — 依頼者の承認で作業を閉じるエージェント基盤

REQUEST → CRITERIA → ASSIGN → RUN → AI REVIEW → SIGN-OFF

チャットは回答で終わる。SoduWork の依頼は、依頼した人が承認したときに終わる。

SoduWork は、チームと AI エージェントが同じ課題プールで作業するためのセルフホスト型の基盤です。依頼には作業前に受け入れ基準が付き、エージェントが作業し、別のハーネス・別のモデルの AI が基準に照らしてレビューし、最後に人が承認します。誰が依頼し、誰が作業し、どのプラグインが動き、誰が承認したかは記録に残ります。

エージェントそのものは作りません。Pi、OpenCode、Qwen Code、Codex などの既存のエージェント実行環境（README では「ハーネス」）を 1 つのアダプター層で動かし、その上に課題・レビュー・プラグインの配布・権限と監査を載せます。開発元は MDiRi で、英語と簡体字中国語の README があります。

工程ごとにエージェントとモデルを選ぶ

工程ごとにハーネスを選び、会話の途中でも切り替えられます。定型の工程は安いモデルやローカルモデル、重要な工程は強いモデルに回し、長い作業は自前のクラウド Runner に渡します。

GOVERNANCE

どの AI に何をさせるかを組織が決める

プラグインは共有前にレビューされ、チームや個人に付与し、取り消せます。ロール、利用量、コスト、監査ログを Hub が持ちます。

VERIFIED DELIVERY

基準を先に決め、承認で完了とする

すべての依頼が受け入れ基準を持ち、独立した AI レビューが 1 項目ずつ確認し、最終判断は人がします。

02 — 扱う問題

README は、AI エージェントで出力は速くなったが、その出力を信頼することと、うまくいったやり方を残すことは自動では手に入らない、という問題設定から始まります。

README「Why SoduWork」より
問題SoduWork の対応
出力は速いが、信頼するまでが遅い。AI が節約した時間が、出力の確認に戻っていく依頼そのものを仕様にする。作業前に基準を決め、別の AI レビューが各項目を確認し、人が承認する
うまくいったやり方がチャット履歴に埋もれる。個人なら先月の成功を再現できず、チームなら 1 人のやり方を他の人が使えない一度うまくいったらプラグインとして保存する。自分で再利用するか、チームに公開し、改善が全員に届く
AI ツールが増え、どれに何をさせるかの基準がない1 つの作業台で、自分のプラグインがどのハーネスでも動く。会話の途中で切り替えても履歴とファイルが残る
結果がワークフローに入らず、コピー＆ペーストで回され、引き継ぐたびに背景を説明し直す課題が文脈を持つ。人もエージェントも続きから再開でき、誰が何をしたかが記録される

03 — 依頼から承認までの流れ

依頼、実行、レビュー、再利用はすべて 1 つの共有課題プールで行われます。承認されたやり方をプラグインとして保存すると、次の依頼でチームがそれを使います。

役割ごとの関わり方（README「How it works」より）
役割関わる場所
1 人で開発する人依頼をプールに入れ、エージェントに処理させ、承認だけをする
専門職AI と作業をうまく終えたら、そのやり方をプラグインとして保存し、チームに公開する
マネージャー依頼を入れると、AI が基準を補い、人かエージェントに回す。最後に承認する
新しく入った人組織が蓄積したプラグインで、チームの水準どおりに作業する。足りない点を見つけたら改善する
エージェント同士では受け渡さない：工程の間と人の間の受け渡しは、プラグインの定義と担当者の判断で決まります。README は「エージェントが自分の判断で他のエージェントに作業を渡すことはない」と明記しています。

04 — ハーネス：作業するエージェントの実行環境

README の「ハーネス」は、作業を実行するエージェントの実行環境のことで、モデルとは別物です。SoduWork はすべてのハーネスを 1 つのアダプターインターフェイスで接続するため、課題・プラグイン・レビューは特定のハーネスに依存しません。Agent Client Protocol（ACP）に対応したプログラムは、カタログへの宣言で追加できます。

個人用からチームの共有へ

チャットの中でプラグインを作るか保存し、ローカルで事前チェックして試します。そのまま自分用に持っておくか、レビューに出してチームのカタログに公開します。JSON を手で書く必要はなく、組み込みの Plugin Developer にチャットで作業を説明すると定義ファイルが作られます。

docs/plugin-authoring.en.md「Core objects」より
オブジェクト役割変更の規則
PluginVersion機能、入口、任意の実行グラフ不変。内容を変えるには SemVer を上げる
PluginBinding組織やプロジェクトの MCP、シークレット、エージェント、モデル、Runner への紐付け設定可能。アップグレード前に互換性を確認
WorkflowRun実際の実行、進捗、証拠永続。失敗した工程から再開

パッケージは「手順」だけを定義し、組織の URL、マシン、モデル、認証情報は書きません。環境との結び付けは Binding が受け持ち、実行時にバージョン・経路・文脈・証拠が固定されます。同じバージョン番号で内容が違うものは拒否されます。

PERSONAL

個人のプラグイン

作成・取り込み・事前チェック・インストール・削除はクライアントで行います。既定で非公開で、自動ではアップロードされません。識別子は local:<uuid> です。

ORGANIZATION

組織への公開

Hub が事前チェックをやり直し、不変の候補を隔離区域に置きます。クライアントからの初回公開ではシステムの安全な領域にある Ed25519 鍵で署名し、管理者が Key ID と SHA-256 の指紋を照合して発行者を登録し、バージョンを個別にレビューして有効にします。

同梱のプラグイン定義は 26 件（hub-backend/plugins/）で、deep-research、document-studio、presentation-studio、software-delivery、meeting-to-action などの JSON 定義と、DingTalk・Feishu・WeCom 連携のパッケージが含まれます。

06 — ワークフロー：工程を DAG で書く

プラグインは必ずしもワークフローを持つ必要はなく、手順・スキル・コネクターだけでも会話や課題から使えます。複数のエージェント、明示的な受け渡し、承認、品質チェック、公開、失敗からの再開が必要なときにワークフローを加えます。ノードは 1〜100 個、dependsOn で非循環に繋ぎ、戻りの辺の代わりに失敗時の方針と再試行（最大 5 回）を使います。

{
  "schemaVersion": 1,
  "key": "weekly-brief",
  "version": "1.0.0",
  "name": "Weekly brief",
  "workflow": {
    "nodes": [
      { "key": "draft", "type": "ai",
        "config": { "agentKind": "local:pi", "prompt": "Write deliverables/brief.md from this week's tasks." } },
      { "key": "check", "type": "ai_review", "dependsOn": ["draft"],
        "config": { "agentKind": "local:qwen", "prompt": "Check each claim against the sources. Block if any claim has no source." } },
      { "key": "done", "type": "publish", "dependsOn": ["check"] }
    ]
  }
}

README の例。Pi が週報を下書きし、Qwen Code が出典と照合し、出典のない主張があれば止める。

ノード種別（docs/plugin-authoring.en.md「Optional workflow DAG」より）
種別実行内容と用途
aiRunner 上のエージェント CLI。分析、実装、スキルや MCP の利用
ai_review独立したレビューへの振り分け。自分の作業を自分で承認しない
spec人が決める要件の基準
human_review人による業務レビューや受け入れ
approvalリスクの高い操作の明示的な承認
qualityクリーンな Runner 作業領域でのビルド・テスト
script管理されたコマンドの実行と証拠の記録
toolHub の信頼済みツール登録簿のツール
merge方針に従った Hub / Runner 経由のマージ
deploy紐付けた環境への Runner によるデプロイ
deploy_chain環境を順にデプロイ・確認・受け入れ・ロールバック
validate成果物の宣言的なチェック
condition入力にもとづく分岐
publish完了と納品の受領記録

AI ノードの指示、ツール、結果は元の会話に流れ込み、人の判断も同じ会話で行います。承認が欠けている・取り消された・却下された場合、後続のノードは止まります。承認待ちは完了とは見なされません。

07 — 構成：Hub・クライアント・Runner

HUB

唯一の事実の置き場所

FastAPI と SQLAlchemy のサーバー（hub-backend/）。課題、ワークフロー、承認、証拠、プラグイン、監査を持ちます。ローカルでは SQLite、チーム運用では PostgreSQL を使います。

ADMIN CONSOLE

ブラウザの管理画面

React + Vite（hub-frontend/）。モデルカタログ、プラグインの隔離・レビュー・公開・付与・ロールバック、監査を扱います。プラグインのエディターではありません。

DESKTOP CLIENT

チャットと承認の作業台

Electron（client/）。Windows、macOS、Linux 用。会話、課題、承認、アプリのウィンドウを扱い、サインイン画面の「Connection」で接続先の Hub を選びます。

RUNNER

実際に作業を実行する側

Hub と WebSocket で接続します。ディスパッチごとに ID があり、同じ作業を二重に取りません。ハーネスはそれぞれ別のサブプロセスで動き、イベントは送信前に実行ホストに保存され、切断後に再送されます。

README「Architecture」の「The hard parts, handled」より
難しい点SoduWork の扱い方
クライアントごとに事実が食い違うHub を唯一の事実の置き場所にする。課題・ワークフロー・承認・証拠は Hub にあり、どのクライアントも同じ事実を見る
エージェントが持つべきでない権限を持つ権限は付与されるもので、前提にしない。組織の方針、実行環境で使えるもの、利用者の選択の 3 つでセッションが使えるものを決める。インストールしただけでは許可されない
1 つのハーネスへの依存全ハーネスに 1 つのアダプターインターフェイス。上位の層は特定のハーネスに依存しない
手順を持ち運べない手順と環境を分ける。プラグインは手順を定義し、ハーネス・モデル・Runner・シークレットは紐付け時に選ぶ。バージョンは不変で持ち運べる
作業の経緯をたどれない対話と実行を分ける。クライアントはチャットと承認を、実行環境と Runner は作業をローカルまたはリモートで行い、すべての実行が監査記録に入る

08 — 導入

Python 3.12 以上、Node.js 22.19 以上、Git が必要です。

A. ソースから 1 台で起動する

git clone https://github.com/mdiri-ai/SoduWork
cd SoduWork

sh start.sh --desktop        # macOS / Linux
.\start.cmd --desktop        # Windows PowerShell
start.cmd --desktop          # Windows コマンドプロンプト

初回は依存関係をインストールし、Hub・管理画面・デスクトップクライアントをこのマシンで起動します。ローカルのソースモードは独立した SQLite と専用のデスクトッププロファイルを使い、既定でループバックだけで待ち受けます。リポジトリの .env や既存のモデル認証情報は読み込みません。

  1. admin のパスワードを設定する

    起動時に求められます（12〜128 文字）。

  2. チャットモデルを追加する

    管理画面の「Capabilities → Model catalog」で接続したサービスを選び、「Add model」でプロバイダーの正確なモデル ID を入れ、「Chat model」として保存します。サービスの認証情報を保存しただけでは、選べるモデルは作られません。

  3. デスクトップクライアントで同じ Hub にサインインする

    サインイン画面の「Connection」が、管理画面と同じ Hub を指しているか確認します。

  4. 新しい会話で Pi と追加したモデルを選び、小さな作業を試す

    接続確認が通っても推論が通るとは限りません。残高、モデルの権限、プロトコルの対応が影響します。エージェント一覧が空なら「Agent management」と Runner の接続を、モデル一覧が空ならモデルが有効か、両方の画面が同じ Hub を使っているかを確認します。

  5. 担当と受け入れが必要なら要件を作る

    目的・入力・受け入れ基準を書き、「Arrange execution」でエージェントとモデルを選び、納品物を確認してから受け入れます。普通の会話には、プロジェクトもプラグインも自動化も必要ありません。

B. Docker でチーム用に立てる

python3 ops/self-host/deploy.py up
python3 ops/self-host/deploy.py credentials   # 初期の管理者パスワードを表示

Hub、管理画面、PostgreSQL を 1 台のサーバーで起動します。チームに開放するには前段に HTTPS のリバースプロキシを置きます。

C. インストーラー版とデモ環境

Releases に Windows（.exe）、macOS（Apple Silicon / Intel の .dmg）、Linux（.deb / .rpm / .tar.gz）のパッケージがあります。初回起動時に「Connection」で Hub のアドレスを入れます。https://service.soduwork.ai を入れると公開デモ環境に接続できますが、README は実際の業務データや機微な情報を上げないよう求めています。

09 — データの行き先

README「Where does my data go?」より
データ行き先
課題、プラグイン、チャット履歴セルフホストなら自分の Hub に保存。作業は自分が選んだフォルダーで行う
モデルへのリクエストRunner から、設定したモデルプロバイダーへ。実行ごとに短命の認証情報を発行し、キーはハーネスの設定ファイルに平文で書かない
プロンプトとファイル設定したモデルプロバイダーやコネクターから見える。セルフホストのモデルを使えば推論を自分の環境内に留められる
利用量の記録接続先の Hub に、会話 ID とタイトル、エージェント・モデル・プロバイダーの識別子、トークン数とコスト、時刻が送られる。任意の分析ではなく運用上の記録
更新の確認インストーラー版は起動時と 6 時間ごとに、接続先の Hub にバージョン、プラットフォーム、CPU、更新チャネルを送る。ソースから起動した場合は確認しない
分析・クラッシュ報告公開ソースには、MDiRi への分析やクラッシュ報告の送信は含まれない
接続先の既定値：クライアントの既定の接続先は運営元のホスト型サービス（https://service.soduwork.ai）です。利用量の記録と更新確認をオフにする設定は現時点でなく、これらの通信を運営元に送らないには自分の Hub を選ぶ必要があります。選んだ接続先は再起動や更新後も保持されます。

10 — 注意点

パブリックベータで、本番利用は自分で評価する前提

README は、本番で使う前に評価するよう求めています。release-scope の文書も、実際に試したプラットフォームだけを報告し、合成データでの確認は実モデルや本番での受け入れの代わりにならないと書いています。

Runner とスキルは汎用のサンドボックスではない

実際の隔離の強さは、ハーネスと実行環境に依存します。README は、信頼できる Hub にだけ Runner を接続するよう求めています。プラグインの事前チェックや取り込みはスクリプトを実行せず、信頼も確立しない、と plugin-authoring の文書にあります。

クラウドへの引き継ぎで移るのは文脈だけ

クラウド Runner へ渡すと、作業ファイル、会話、目的は移りますが、実行中のプロセスやブラウザのセッションは移りません。クラウド Runner のサーバーは自分で用意します。

配布する場合の設定

  • 自動更新の署名鍵は既定でどれも信頼されていません。インストーラーを配布する前に client/update-trust.json と hub-backend/client-update-trust.json に Ed25519 公開鍵を設定し、SODUWORK_CLIENT_SIGNING_KEY_ID を指定する必要があります。未設定なら、クライアントは自動更新のダウンロードとインストールを拒否します。
  • client/package.json の homepage と Linux の maintainer は自分のものに置き換えます。

その他
