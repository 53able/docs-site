Open Code Review

ocr — Git 差分を読み、構造化されたレビューコメントを返す Go 製 CLI

1 — 概要
何をするツールか

Open Code Review（コマンド名 ocr）は、Alibaba が社内の AI コードレビューアシスタントとして 2 年運用したものを OSS 化した CLI です。Git の差分を読み取り、変更ファイルをツール実行可能なエージェント経由で LLM に渡し、行単位で位置づけられたレビューコメントを生成します。

エージェントはファイル全文の読み取り、コードベースの検索、他の変更ファイルの差分参照ができるため、差分の表面だけを見た指摘に留まりません。差分レビューに加えて ocr scan はファイル全体をレビューするので、意味のある差分がない未知のコードベースやディレクトリの棚卸しにも使えます。

Go実装言語
Apache-2.0ライセンス
200 PRAACR-Bench の評価対象
1/9汎用エージェント比のトークン量

ベンチマーク AACR-Bench は 50 の人気 OSS リポジトリ・200 件の実 Pull Request・10 言語から構成され、80 名以上のシニアエンジニアが相互検証した 1,505 件の正解課題を持ちます。同じモデルを使った場合、汎用エージェントより Precision と F1 が高く、トークン消費は約 9 分の 1 です。Recall は汎用エージェントより低く、これはノイズを減らすために精度を優先した意図的なトレードオフです。

2 — 設計方針
汎用エージェントで起きること

README は、Skill を使った汎用エージェントによるレビューで繰り返し観測される問題として次の 3 点を挙げています。原因は、レビュー手順に対する強制力を言語モデルだけに委ねている点にあるとしています。

  • カバレッジの欠落 — 変更量が大きいほど、一部のファイルだけを見て残りを飛ばす。
  • 位置のずれ — 指摘の行番号やファイル参照が実際のコード位置と合わない。
  • 品質の不安定さ — 自然言語で書かれた Skill はデバッグが難しく、プロンプトの小さな差で結果が揺れる。
決定論的エンジニアリング

間違えてはいけない工程は、モデルではなくコードで保証します。

  • ファイル選別 — レビュー対象と除外対象を規則で確定させ、重要な変更を取りこぼさない。
  • ファイルのバンドル — 関連ファイルを 1 レビュー単位にまとめ、束ごとにサブエージェントを独立コンテキストで走らせる。大規模変更でも安定し、並列化しやすい。
  • ルールのマッチング — ファイルの特徴に応じたレビュールールをテンプレートエンジンで割り当て、情報ノイズを入口で断つ。
  • 位置づけと再検証 — コメント位置の解決と内容の再評価を独立モジュールとして持つ。
エージェント

動的な判断とコンテキスト収集にモデルの力を集中させます。

  • 用途特化プロンプト — コードレビュー向けに調整したテンプレートで、効果を上げつつトークンを削る。
  • 用途特化ツールセット — 本番データのツール呼び出し履歴（呼び出し頻度分布、ツール別の反復率、新規ツールが呼び出し連鎖に与える影響）を分析して絞り込んだ 6 種類。
効果の範囲: グルーピングは最適化であって正しさのゲートではありません。LLM 応答が失敗・空・解析不能なら警告を出して 1 ファイル 1 グループへフォールバックします。
3 — レビューの流れ
ocr review が実行する 6 段階

Enter を押してから結果が出るまでに、次の順で処理が進みます。オーケストレーションは internal/agent/、ツール実行ループとメモリ圧縮は internal/llmloop/ にあります。

01
bootstrap
LLM エンドポイントを config → 環境変数 → シェルの rc ファイルの順で解決し、テンプレート・ツールレジストリ・システムルールを読み込む。
↓
02
diff provider
Workspace / Commit / Range の 3 モードで git diff・ls-files・show を叩き、差分リストを作る。コンテキスト行数は Git 既定と同じ 3 行に固定。
↓
03
filter & rules
5 つのゲートでバイナリ・除外パス・非対応拡張子を落とし、残ったファイルごとにレビュールールを選ぶ。
↓
04
semantic grouping
ファイルのメタデータ（パス・状態・増減行数）だけを渡す 1 回の LLM 呼び出しで、関連ファイルをグループにまとめる。差分本文は渡さない。
↓
05
subtask dispatch
グループごとに goroutine を立て、並列度 --concurrency（既定 8）で走らせる。各サブタスクは plan フェーズ（条件付き）→ main ループ → コメント収集。
↓
06
output writer
行位置の解決とレビューフィルタを同期実行し、--format と --audience に応じて text / json / sarif を書き出す。
差分の 3 モード
モード指定方法返す差分
Workspaceフラグなしステージ済み + 未ステージ + 未追跡の変更
Commit--commit <sha> / -cそのコミットが導入した変更（git show 相当）
Range--from <a> --to <b>merge-base(a, b)..b
未追跡ファイルの扱い: ディスクから読み取って全文追加として扱うため、コミット前にレビューできます。モードフラグは相互排他で、混在させるとエラーになります。
グルーピングの 3 つのガード
ガード働き
maxFilesPerGroup = 10大きすぎるグループを 10 ファイル単位に分割する。
トークン予算差分合計がプロンプト上限を超えるグループは 1 ファイル 1 グループに割り直す。

4 — ファイル選別とルール
5 ゲートのフィルタ

各差分は internal/agent/selection.go の whyExcluded を上から順に通ります。最初に該当したゲートが除外理由になります。

  1. binary バイナリファイルを最初に落とす。
  2. user_exclude プロジェクトの exclude パターンに合致したものを落とす。ユーザー指定が常に優先。
  3. user_include include パターンに合致すれば、以降 2 つのゲートを飛ばして即採用する。
  4. unsupported_ext 拡張子の許可リスト supported_file_types.json にないものを落とす。
  5. default_path 組み込みのテストファイル除外パターン（**/*_test.go、**/*.test.{js,jsx,ts,tsx}、**/__tests__/** ほか）に合致したものを落とす。

ゲート通過後に selectFiles が 2 つの判定を追加します。新パスが /dev/null なら deleted、差分だけで max_tokens の 80% を超えるなら too_large です。

ノイズディレクトリは別レイヤー: vendor/、node_modules/、target/ などは差分プロバイダ側（internal/diff/git.go）で先に落とされ、プレビューでは provider_directory と表示されます。ここに include を書いてもレビュー対象には戻りません。
ルールの 4 層優先チェーン

ファイルごとに「何に注目してレビューするか」を決める文面は、次の 4 層を上から試し、最初にパターンが合致した層が勝ちます。上位層のファイルが存在しない場合は黙って次へ落ちるだけで、エラーにはなりません。

優先度出所パス
1（最高）--rule フラグユーザー指定。渡せば常に勝つ。
2プロジェクト設定<repo>/.opencodereview/rule.json — コミットして共有できる。
3グローバル設定~/.opencodereview/rule.json
4（最低）システム既定バイナリに埋め込まれた system_rules.json

rule.json の形

{
  "include": ["src/**/*.{ts,tsx}", "src/**/*.go"],
  "exclude": ["**/*.test.ts", "**/generated/**"],
  "rules": [
    {
      "path": "src/api/**/*.go",
      "rule": "All exported handlers must validate request bodies before use."
    }
  ]
}
  • include は許可リストではありません。組み込みのテストファイル除外を迂回させるためのもので、ここに合致しないファイルも通常どおり残りのゲートを通ります。
  • exclude はフィルタ内で最優先です。
  • rules は宣言順に評価され、最初にグロブが合致した path の rule がそのファイル用のプロンプトになります。

グロブは bmatcuk/doublestar/v4 で、*・**・{a,b,c}・?・[abc] に対応します。パスは小文字化してから照合されるため大文字小文字は区別しません。どのルールが当たるかは ocr rules check <path> で確認できます。

5 — エージェントループ
plan フェーズと main ループ

サブタスクは最大 2 フェーズで構成されます。plan フェーズは 2 つのしきい値のどちらかを満たしたときだけ走ります。単一ファイルの大改修は 1 つ目が、複数の中規模ファイルはグループ合計の 2 つ目が拾います。小さな変更では計画が遅延だけを生むため、黙って飛ばして main ループに入ります。

// PLAN_MODE_LINE_THRESHOLD = 50, PLAN_MODE_GROUP_LINE_THRESHOLD = 100
if maxFileChanged >= PlanModeLineThreshold                { plan }
if fileCount >= 2 && total >= PlanModeGroupLineThreshold { plan }

plan フェーズの LLM 呼び出しには Tools を渡さないため、モデルは計画中にツールを呼べません。読み取り専用のツール定義はプレーンテキストとして {{plan_tools}} に埋め込まれ、後で何が使えるかだけを伝えます。返ってきたチェックリストが main プロンプトの {{plan_guidance}} になります。

main ループの終了条件

  1. task_done が呼ばれた。
  2. MAX_TOOL_REQUEST_TIMES（既定 100）を使い切った。
  3. 有効なツール結果のないラウンドが 3 回続いた。
  4. コンテキストがキャンセルされた。
  5. 圧縮してもメッセージバッファが警告しきい値を下回らなかった。

いずれの場合も、そこまでに集めた code_comment 呼び出しがレビューコメントになります。

6 つの組み込みツール
ツールplanmain役割
task_done—○ループの終了を宣言する。
code_comment—○行範囲と修正案を持つレビューコメントを出す。
file_read—○変更後スナップショットからファイルの一部を読む。
file_read_diff○○別ファイルの差分を読み、ファイル横断の懸念を確認する。
file_find○○ファイル名のキーワードでファイルを探す。
code_search○○リポジトリ全体をリテラルまたは正規表現で検索する。
コンテキスト用ツールは指摘先ではありません: file_read 系の 4 つは現在のファイルの差分を理解するために存在し、その過程で見つけた他ファイルの問題は設計上無視されます。ファイル横断の懸念は「今見ている差分から観測できるとき」だけコメントになります。ツールレジストリは --tools <path> で同じ形の JSON に差し替えられます。
レビューラウンド

main ループはグループごとに複数回走ります。回数は --effort プリセットで決まります。

2 回目以降は、確定済みの指摘を {{confirmed_comments}} として渡しつつ plan を外して再実行します。明らかな問題が出尽くした後は計画がカバレッジの上限として働いてしまうためです。新しい指摘が出ない、確定コメント数の上限に達する、--max-tokens-budget を使い切る、のいずれかで打ち切ります。

メモリ圧縮

長いツール実行ループはいずれコンテキストウィンドウを溢れさせます。MAX_TOKENS = 200000 を基準に 2 段階で動きます。

しきい値動作
60%バックグラウンドで非同期に圧縮を開始。ループはそのまま進む。
80%次のリクエスト送信前に同期で圧縮する。

メッセージは frozen（先頭 2 件）・compress（要約対象）・active（直近の完全なラウンド）の 3 ゾーンに分割されます。compress ゾーンは XML に整形して要約させ、結果を最初のユーザーメッセージに <previous_review_summary> として追記します。

入力と出力は別枠: MAX_TOKENS はプロンプト側の上限だけを指します。出力上限は MAX_COMPLETION_TOKENS = 16384 で、--max-tokens を上げても出力予算は膨らみません。
6 つのプロンプトテンプレート

internal/config/template/task_template.json が {role, prompt_file} の参照リストを持ち、読み込み時に Markdown 本文へ展開されます。プレースホルダはグループごとに解決されます。

キー役割
GROUPING_TASK変更ファイルを意味のあるグループに束ねる。
PLAN_TASK計画フェーズ。チェックリストを出力する。
MAIN_TASKメインのレビューループ。code_comment を発行する。
MEMORY_COMPRESSION_TASKcompress ゾーンを要約する。
REVIEW_FILTER_TASKループ後に、明らかに誤ったコメントを取り除く。
RE_LOCATION_TASK位置を解決できなかったコメントを再アンカリングする。
プレースホルダ記法の例外: ほとんどが {{…}} ですが、RE_LOCATION_TASK だけは単一波括弧の {diff}・{existing_code}・{suggestion_content} を使います。テンプレート自体は CLI から差し替えられず、変更するには JSON を編集して再ビルドします。
6 — コメント生成と後処理
code_comment の入力

コメントは行番号ではなく コードの断片 に紐づけて発行されます。existing_code を手がかりに ocr 側が行番号を計算するため、モデルが行数を数え違えても位置がずれにくくなります。

{
  "name": "code_comment",
  "input": {
    "path": "string — 任意。このコメントのファイルパスを上書きする",
    "comments": [
      {
        "content": "string — 設定した言語で書かれた指摘本文",
        "existing_code": "string — 差分から取ったアンカー用の断片",
        "suggestion_code": "string — 任意。修正案の断片"
      }
    ]
  }
}

comments は配列なので、1 回のツール呼び出しで複数の指摘を出せます。path を省略した場合はレビュー中のファイルが自動で補われます。

位置解決の 3 段構え
  1. ハンク照合 — 差分ハンクの新側（文脈行 + 追加行）を動的スライディングウィンドウで走査し、新ファイルの行番号を得る。外れたら旧側（文脈行 + 削除行）を試す。
  2. ファイル全文走査 — どのハンクにも合わなければ、変更後のファイル内容を 1 行ずつ走査して連続一致を探す。
  3. 再アンカリング — それでもテキスト一致しないとき、RE_LOCATION_TASK でモデルに位置を再指定させる。existing_code が言い換えられていた場合に効く。

最終的に一致しなければ start_line / end_line は 0 になります。専用のフラグはなく、下流は start_line == 0 を「位置未確定、手動で探す必要がある」の合図として扱います。

ループ終了後の 2 パス

  • レビューフィルタ — ワーカープールが捌け切った後、REVIEW_FILTER_TASK が差分と照らして明らかに誤った指摘を取り除く。ここでのエラーはログに残して無視する。--no-filter でこの工程を丸ごと省略できる。
  • 2 度目の行解決 — Agent.Run から戻った後、コマンド側がコメント集合全体に対して行番号解決を再実行し、複数ファイルにまたがる指摘や再アンカリング済みの指摘を拾い直す。
自動化しない判断
  • エンドポイント探索にフォールバックを置かない — 設定・環境変数・rc ファイルから (URL, token, model) が揃わなければ、推測せず非ゼロ終了する。
  • サブエージェントの失敗は隔離するがリトライしない — 1 グループの失敗は警告になり、残りは続行する。再試行は CI パイプライン側の仕事とする。
  • ファイル横断の推論はグループ内に限る — 同一グループのファイルは 1 つの会話を共有する。他グループのファイルはツール経由で読めるが、指摘の対象にはしない。
7 — CLI の使い方
導入から初回レビューまで

前提は Git 2.41 以上 と Node.js 18 以上、そして LLM の API キーです（委譲モードを使う場合は API キー不要）。

# 1. インストール — ocr コマンドがグローバルに入る
npm install -g @alibaba-group/open-code-review
ocr version

# 2. プロバイダとモデルを対話 UI で設定する
ocr config provider
ocr config model

# CI など TUI のない環境では同じ設定を直接書く
ocr config set provider                    anthropic
ocr config set model                       claude-opus-4-6
ocr config set providers.anthropic.api_key sk-ant-xxxxxxxxxx

# 3. 疎通確認
ocr llm test

# 4. レビュー
cd path/to/your-repo
ocr review                                   # ワークスペースの全変更
ocr review --from main --to feature-branch   # ブランチ範囲（merge-base 起点）
ocr review --commit abc123                   # 単一コミット
先に対象を確かめる: ocr review --preview はフィルタだけを走らせ、LLM を呼ばずに対象ファイルと除外理由を表示します。トークンを 1 つも消費しません。

8 — 連携と運用
委譲モード — レビューをホストエージェントに任せる

委譲モードでは、ocr は決定論的な部分（ファイル選別、ルール解決、除外判定）だけを担当し、実際のレビューはホストのコーディングエージェントが自分の LLM で行います。ocr 側の LLM 設定は不要です。Claude Code、Codex、Cursor など、すでにサブスクリプションを持っているエージェントでそのクォータを再利用したいときに使います。

# 1. 何をレビューすべきかを出す（モード / ref メタデータ / 対象 / 除外理由）
ocr delegate preview
ocr delegate preview --from main --to feature
ocr delegate preview -c abc123

# 2. 対象パスに当たるレビュールールをまとめて取る
ocr delegate rule src/main.go src/handler.go

# 3. 差分は git から直接取る
git diff <merge_base>..<to> -- <path>   # range モード
git show <commit> -- <path>             # commit モード
git diff HEAD -- <path>                 # workspace モード（追跡済み）

GitHub Actions

リポジトリルートの action.yml が PR レビュー用の composite action を定義しています。インライン コメント、固定サマリ、非破壊な増分投稿に対応します。

  • llm_url / llm_auth_token / llm_model が必須入力で、それぞれ OCR_LLM_* 環境変数に対応します。
  • llm_use_anthropic でプロトコルを切り替えます（Anthropic か OpenAI 互換か）。
  • language（既定 English）でレビュー出力の言語を指定します。
  • llm_reasoning_effort は OpenAI 互換プロトコル専用で、Anthropic プロトコルと併用すると即座に失敗します。

GitLab CI、Bitbucket Pipelines、Gerrit、GitFlic CI、Codeup CI の例がリポジトリの examples/ にあります。

セッションの保存と閲覧

すべてのレビューは JSONL としてディスクに残ります。1 行が 1 イベント（送信プロンプト、LLM 応答、ツール呼び出し、ツール結果、発行コメントなど）で、データベースはありません。

~/.opencodereview/sessions/<encoded-repo-path>/<session-id>.jsonl

ocr viewer はこの JSONL を直接読む組み込み HTTP サーバーです。既定のアドレスは localhost:5483。リクエストごとに遅延スキャンするため、別ターミナルで走っているレビューも JSONL が現れた時点で一覧に出ます。

DNS リバインディング対策: viewer は Host ヘッダをループバック許可リストと照合します。--addr :3000 のようなワイルドカードバインドは自動追加されないため、LAN から開くと forbidden host になります。許可するには OCR_VIEWER_ALLOWED_HOSTS にホスト名をカンマ区切りで設定します。
テレメトリ

有効化すると、ジョブ全体を包む review.run、差分読み込みの diff.parse、レビューしたグループごとの subtask.execute.group.<group-key> という 3 種類のパイプラインスパンと、判断地点ごとの短命な event.<name> スパン（plan.skipped、token.threshold.exceeded、subtask.error など）を発行します。LLM の往復とツール呼び出しはメトリクスとしてのみ記録されます。プロンプトと応答の内容がテレメトリに添付されることはありません。
