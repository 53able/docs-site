SkillEvaluator

NVIDIA/SkillEvaluator · PyPI 1.0.1（2026-11-18） · Python 3.12〜3.14 · CLI skillevaluator · サポートレベル Experimental · Apache-2.0

01 — スキルの品質と、エージェントへの効果を測る

VALIDATE → DEDUPLICATE → RUN WITH / WITHOUT SKILL → REPORT

スキルが正しく書けているかを静的に調べ、次に同じタスクをスキルあり・なしでエージェントに解かせて差を出す。

SkillEvaluator は、Agent Skills 仕様のスキル（SKILL.md と付随ファイルのフォルダー）や、ルール・ワークフロー・プラグインを検査する Python の CLI です。NVIDIA の Verified Skills パイプラインの一部として公開されています。

検査は 3 つの Tier に分かれます。Tier 1 は API キーなしで動く静的検査（構造、セキュリティ、PII、品質スコアなど）、Tier 2 は埋め込みと LLM による重複・類似の検出、Tier 3 は Docker などのサンドボックスで実際のエージェントを動かし、スキルあり・なしの結果の差（Skill Lift）を測ります。各 Tier は独立していて、必要なものだけを実行できます。

CLI で直接

skillevaluator validate ./my-skill --tiers 1 は LLM のキーなしで Tier 1 の静的検査を行います。README は「500 以上の静的ルールと検出パターン」と説明しています。完全に調べるにはスキャナーの準備が要ります。

CI

リポジトリの CI に組み込む

skillevaluator ci init が GitHub リポジトリにセットアップ用の PR を作ります。GitLab 用の手順もあります。

AGENT

エージェントから呼ぶ

npx skills add NVIDIA/SkillEvaluator でスキルとして追加し、「Is my skill any good?」と聞くと、エージェントが CLI を実行します。

0.9.0 から上げるときに影響する変更

  • 基本パッケージに Bandit と uv が入りました。Tier 2・3 は引き続き extra（[all] など）が必要で、管理対象のスキャナーは初回利用時にダウンロードされます。
  • 著者情報（metadata.author など）の要求は既定で推奨扱いになりました。厳密にするには --profile registry を使います。ポリシーのダイジェストが変わります。
  • 重大度の上書きに使うキーが SECURITY.Unknown (AE1) から SECURITY.Incomplete referenced artifact analysis (AE1) に変わりました。severity_overrides で旧名を使っている場合は書き換えが必要です。
  • 検証できないフックのペイロードは Critical のセキュリティゲート失敗になり、重大度の上書きや --llm-verify では解除できません。
  • 管理対象の SkillSpector は 2.13.4 になりました。NVIDIA Build の既定モデルは nvidia/nemotron-3.5-lightning-30b-a3b です（以前の既定モデルはホスト型エンドポイントが廃止され、HTTP 404 になっていました）。SkillSpector の Anthropic / Bedrock の既定は Claude Opus 5.5 です。
  • 既存の CI ワークフローは固定したピンのままで、更新は明示的に行います。1.0.1 用のテンプレートは ci/bundles/1.0.1/ にあります。

1.0.1 の修正

  • OpenCode のスナップショットを既定で無効にしました。.git のない作業領域で、タスク完了後に broken pipe で失敗する問題への対処です。利用者が明示した設定は保持されます。
  • Claude のゲートウェイを使う場合に、独自形式のモデル ID が Docker、ローカル、ネイティブ Harbor の各コマンドでそのまま渡るようになりました。
  • フォルダー単位の検査で、スキル探索の除外（results、evals、.versions）を、指定したルートより下だけに適用するようになりました。これらの名前のディレクトリの中にチェックアウトしたリポジトリで、スキルが 1 つも見つからなくなる問題の修正です。
  • Tier 3 の価格ファイルで、JSON の重複キー、真偽値のレート、有限でない値、負の値を拒否します。

03 — 3 つの Tier の役割

まとめて実行するコマンドは skillevaluator validate です。--tiers を指定しなければ、スキルに対しては 3 つの Tier をすべて実行します。終了コードへの影響（ゲート）は Tier ごとに異なります。

README「Three-tier overview」より
Tier答える問い単独のコマンド追加で必要なもの
Tier 1：Validation安全で、形式が正しく、ハーネスと互換かskillevaluator tier1 ./my-skill --no-llm静的検査を完全に行うには外部スキャナー。LLM 検査にはプロバイダー
Tier 1：Harness Checkエージェントがスキルを読み込むかskillevaluator harness-check ./my-skill1.0.1 以降。キーもエージェント実行も不要
Tier 2：Deduplication指示が繰り返されていないか、他のスキルと重ならないかskillevaluator tier2 ./my-skill埋め込みとチャットのモデル。スキル間の比較には --catalog
Tier 3：Live Agent Evaluationスキルがエージェントの役に立つかskillevaluator tier3 ./my-skillプロバイダー、対応エージェント、サンドボックス（既定は Docker）
validate のゲートの既定（docs/tier1-reference.mdx、docs/ci-integration.mdx より）
Tier終了コードへの影響切り替え
Tier 1常にゲート。失敗、または必須スキャナーの証拠が不完全なら非 0—
Tier 2既定でゲート--no-block-on-dedup で参考扱い
Tier 3既定は参考扱い--block-on-agent-eval でゲートに含める

終了コードは 0（全ゲート合格）、1（ゲート失敗、実行が完了しなかった、内部エラー）、2（未知のフラグや存在しないパスなどの使い方の誤り）の 3 種類です。対象はスキルのほか、ルール（.mdc）、ワークフロー、プラグイン（agent_plugin.yaml または .claude-plugin/plugin.json）で、--type を省くと自動判定されます。

04 — Tier 1：静的検査

静的検査はモデルのキーを必要としません。validate の既定のチェックは次の 10 個で、dependency は --checks で明示したときだけ実行されます。

docs/tier1-reference.mdx「The checks」より
チェック内容
schemafrontmatter と配置。name（1〜64 文字の kebab-case、ディレクトリ名と一致、anthropic と claude は使えない）と description（1〜1024 文字）が必須。重複キーや BOM などハーネスごとに読み込みが変わる書き方も指摘する。SKILL.md は 500 行以下が推奨
version任意の metadata.version が major.minor.patch 形式か

品質スコアの内訳

quality-check の 4 カテゴリ（docs/tier1-reference.mdx より）
カテゴリ重み見ているもの
Correctness35%frontmatter、命名、例、パス、スキルの種類ごとの構造
Discoverability25%description の質、起動条件の書き方、目的、範囲、命名
Reliability25%エラー処理、前提条件、制限、トラブルシューティング、実装上の安全策
Efficiency15%推定トークン量、本文の長さ、繰り返し、指示の明確さ、参照ファイルの使い方

評価は 90 以上が A、80 以上が B、70 以上が C、60 以上が D、それ未満が F です。合格には既定の --min-score 70 以上で、かつ HIGH / CRITICAL の品質指摘がないことが必要です。SKILL.md の推奨トークン量は 5,000 で、文字数を 4 で割った推定値を使います。超えると MEDIUM の指摘と Efficiency から 15 点の減点がつきます。

品質ルールの設定ファイル

--quality-config PATH（quality-check、tier1、validate で使える）で一部のルールを変えられます。1.0.0 で、従来の Reliability のルールに加えて次の 4 つが設定可能になりました。どれも points、message、suggestion と 1 つの設定値を持ち、points: 0 で無効になります。書かなかった項目は同梱の quality-default.yaml の値のままです。

設定できる品質ルール（CHANGELOG.md 1.0.0、docs/tier1-reference.mdx より）
ルール設定値同梱の値減点
efficiency.token_budgetmax_tokens5,00015
discoverability.description_too_shortmin_chars2020
discoverability.description_too_longmax_chars2005
correctness.reserved_nametermsanthropic、claude15
 
efficiency:
  token_budget:
    max_tokens: 8000

terms のようなリストは同梱のリストを置き換えます（足し合わせない）。予約語のルールは HIGH の指摘なので、スコアに関係なく品質チェックを失敗させます。ただし schema チェックは別に固定のリスト（anthropic、claude）を持っていて、この設定ファイルでは変わりません。設定ファイルに未知のキーや範囲外の値があると、検査を始める前に終了コード 2 で止まります。

LLM を使う検査（任意）

プロバイダーを設定すると、rubric-eval が 9 項目の LLM-as-judge 評価を行います。項目は、description と使う場面の明確さ、指示の明確さ、例の質、文書の網羅性、範囲の定義、書式、肯定・否定のクエリでの起動シミュレーション、手順全体の完結性、エラー処理です。各項目 0〜10 点で 7 以上が合格、全体は重要度で重み付けした平均で、全項目の合格が必要です。--llm-verify は静的検査の指摘を LLM が文脈つきで見直し、確信度の高い誤検知を INFO に下げます（指摘自体は残ります）。

ポリシー

同梱のポリシーは default と registry の 2 つです。default では metadata.author と metadata.id は推奨にとどまり、registry では欠けると HIGH でブロックされます。--policy ./policy.yaml で重大度の上書きなどを重ねられます。

05 — ハーネスチェック：エージェントがスキルを読み込むか

仕様どおりに書かれたスキルでも、エージェント（ハーネス）ごとに YAML パーサー、探索するフォルダー、サイズ上限が違うため、あるエージェントでは読み込まれ、別のエージェントでは黙って捨てられることがあります。harness-check はファイルを読むだけで、モデルもエージェントも実行せずに、6 つのハーネスでの扱いを「読み込む」「劣化する」「読み込まない」で予測し、直し方を示します。

skillevaluator harness-check ./my-skill

│  ❌ claude-code  not loaded  .agents/skills is not scanned                              │
│  ✅ opencode     loads                                                                  │
│  ✅ hermes       loads                                                                  │
│  ✅ openclaw     loads                                                                  │
│  ❌ copilot-cli  not loaded  description is 1,028 UTF-16 units, 4 over the 1,024 limit  │
╰────────────────────────────────────────────────────────────────── ❌ 2 of 6 not loaded ─╯

README の出力例（README 自身が「バージョン付きプロファイルの要約の例示」と注記）。

対象は Claude Code、Codex、Copilot CLI、Hermes、OpenClaw、OpenCode で、判定規則はハーネスごとのバージョン付きプロファイル（src/skillevaluator/harness/profiles/*.yaml）に入っています。-v で各プロファイルの確認済みバージョンと日付を表示し、--harness-version HARNESS=VERSION で別のリリースを指定できます。

1.0.1 から PyPI 版に含まれる：0.9.0 にはありません。validate では Tier 1 の既定のチェック（harness）として実行され、既定ポリシーでは参考扱いです。skillevaluator --version で手元の版を確かめられます。

06 — Tier 2：重複と類似の検出

Tier 2 には 2 種類の検査があります。Docker や評価データセットは不要ですが、スキルの本文をプロバイダーに送ります。

INTRA-SKILL

1 つのスキルの中の繰り返し

context-optimization-check（別名 dedup-scan）。Markdown は見出し単位、Python はドキュメント文字列とシグネチャ、シェルは関数とコメントで分割し、埋め込みのコサイン類似度 0.80 以上の組をまとめた後、チャット LLM がその重なりが意図的か（例：references/ での詳細化）を判定し、作者への対応案を返します。

INTER-SKILL

スキル同士の重なり

similarity-check。コレクション内、または保存したカタログ（--catalog）と比べます。既定ではスキルの name と description だけを埋め込み、--full-body で SKILL.md 全体を使います。埋め込みだけで動きます。

スキル間の類似度の分類（docs/tier2-reference.mdx より）。既定の報告しきい値は 0.75
分類コサイン類似度重大度
EXACT_DUPLICATE≥ 0.95CRITICAL（ブロック）
HIGH_SIMILARITY≥ 0.90HIGH（ブロック）
SIMILAR≥ 0.75MEDIUM（参考）
LOOSELY_RELATED≥ 0.50LOW（参考）
DISTINCT< 0.50INFO（既定では報告しない）

カタログを渡さずに 1 つのスキルだけを調べた場合、スキル間の比較はレポートに「not run」と表示されます。

07 — Tier 3：スキルあり・なしでエージェントを走らせる

Tier 3 は、同じ評価ケースを「スキルを入れたエージェント」と「入れないエージェント」（ベースライン）の 2 つの系統（arm）で実行し、採点結果の差を Skill Lift として出します。実行は Harbor（オープンソースのエージェント評価フレームワーク）が担い、実験的なバックエンドとして NeMo Gym も選べます。

  1. 評価ケースを用意する

    現実的な依頼、観察できる成功条件、範囲外の依頼（否定ケース）を書いたガイダンスから生成します。成果物は ./my-skill/evals/evals.json で、明示・暗黙・文脈・否定のカテゴリにまたがるケースができます。--no-llm ではモデルを使わずテンプレートの下書きを作ります。

    skillevaluator create-eval-dataset ./my-skill --full --prompt eval-guidance.md

    文書は、スキルのファイルを読むことやスクリプトを使うことを成功条件にしないよう求めています。ベースラインに不利になり、比較が成り立たなくなるためです。

  2. ケースをレビューして検証する

    skillevaluator tier3 validate ./my-skill --strict

    この検証は構造と表現を調べるだけで、ケースが実際の使われ方を代表しているかは人が確認します。evals/ がないと、終了コードが失敗にならずに「missing」と報告されることがあるため、ファイルの存在は先に確認します。

  3. 準備状態を確かめる

    skillevaluator doctor --env-mode docker

    doctor が確かめるのは準備状態で、推論が成功するかまでは保証しません。

  4. 2 系統で実行する

    skillevaluator tier3 evaluate ./my-skill --env-mode docker --n-attempts 1

    --n-attempts 1 は、選んだケースを各系統で 1 回ずつ試すという意味です。モデルの呼び出しには料金がかかります。

  5. レポートを開く

    skillevaluator view ./my-skill

    既定の出力先は ./my-skill/evals/results/ で、report.html と result.json ができます。文書は、実行状況と網羅、Skill Lift、個々の試行（エージェントが何をしたか、スキルが起動したか）の順に見るよう勧めています。

対応エージェント（docs/agents-and-sandboxes.mdx より）。プロバイダーごとの既定は NVIDIA Build → OpenCode、OpenAI → Codex、Anthropic → Claude Code
エージェント備考
claude-codeHarbor が Claude Code 2.1.292 をインストール。別名 claude
codexHarbor が Codex 0.161.0 をインストール。reasoning_effort=high で実行
opencodeHarbor が OpenCode 1.19.5 をインストール
hermes実験的。Docker と NVIDIA Build の組み合わせのみ

NeMo Gym バックエンド（--backend nemo-gym）は実験的で、--env-mode docker のみに対応します。Gym は Python 3.13.14 以降が必要なため SkillEvaluator とは別の環境に入れ、固定コミットの完全なソースチェックアウトを editable でインストールします（公開版の nemo-gym==0.7.0 は非互換）。docs/tier3-runtime.mdx には、Codex、OpenCode（GPT-5.4-mini）と Claude Code（Claude Sonnet 4.6）で、スキルあり・なし両方の試行が完了した記録があります。文書は、これがスキルの品質やすべてのモデルとの互換性を示すものではないとしています。

実行場所（--env-mode）は既定の docker のほか、kata、local（手元にインストール済みの CLI を OS のサンドボックスポリシーの下で実行）、Daytona・E2B・Modal・EC2・GKE・Apple Container などの Harbor 対応の環境から選べます。

08 — Tier 3 のスコアの計算

docs/metrics-reference.mdx は、すべての数値の出所を式と実装ファイルつきで説明し、「文書と実装が食い違ったら実装が正で、文書のバグ」としています。Tier 1 の品質スコア（0〜100）と Tier 3 のスコア（0.0〜1.0）は、次元名を 4 つ共有するだけの別物で、互いの入力にはなりません。

6 つのシグナル → 5 つの次元

Discoverability必要なときに正しいスキルが読み込まれたかskill_executionツール呼び出し列の構造検査（決定的）
Effectivenessスキルがタスクの完了を助けたかgoal_accuracy と behavior_check の平均（0.5 / 0.5）LLM ジャッジ。ケースに宣言済みのチェックがあればそれも
Efficiencyツールやスキルを無駄に使わなかったかskill_efficiency各ツール呼び出しの分類（決定的）

測れないシグナル（期待出力のないケースの accuracy、ベースラインの skill_execution など）は N/A として平均から外し、0 としては数えません。ジャッジがエラーやタイムアウトになった場合は 0 点ではなく、その試行全体を失敗にします。

総合スコアと Skill Lift

overall = mean(Security, Correctness, Discoverability, Effectiveness, Efficiency) Skill Lift = overall(スキルあり) − overall(スキルなし)

Skill Lift は両系統が実行したケースと両系統が採点できたシグナルだけで計算するため、表示された 2 つの総合スコアの単純な差と一致しないことがあります。範囲は −1.0〜+1.0 で、+0.20 は「総合スコアが 0.20 高い」という意味であり、20% の改善ではありません。判定の目安は +0.05 以上で PASS、−0.10 以下で FAIL、その間が NEUTRAL です。ケース単位の対応のある値があれば、ブートストラップ（シード 0、2,000 回以上、95%）の区間も出します。

試行の合否と pass@k

--n-attempts k では各ケースを各系統で k 回実行します。1 回の試行は、goal_accuracy が 1.0、security が 1.0、総合スコアが --pass-threshold（既定 0.50）以上、の順に確かめて合格になります。ケースは k 回のうち 1 回でも合格すれば合格です。合格率には 95% の Wilson 区間がつき、両系統が同じケースを実行した場合は McNemar の正確検定の値も記録されます。

09 — 結果の読み方と、文書が認めている限界

metrics-reference には、確立していないことを列挙した節があります。結果を社内外に示す前に読んでおく内容です。

docs/metrics-reference.mdx「What has not been established」「What the project has done about judge reliability」より
項目文書の記述
ジャッジの一致度人手でラベル付けした実行記録との評価者間一致度の研究は公開されていない。tier3 validate-grader は 16 ケースの小さな同梱スイートとの一致を測るだけ
ジャッジの実測値同梱スイートの評価用分割では、試した 2 つのジャッジモデルとも、既知の失敗タスクを総合スコアのしきい値で全件合格にした（15/15 の誤合格）。accuracy は形式違いや偽の成功報告にも部分点を与えた
次元と重み次元の定義、Effectiveness 内の 0.5 / 0.5、5 次元の等重みは設計上の選択で、妥当性は検証されていない
しきい値0.50 の合格ライン、Lift の ±帯、10 ケースの十分性基準などは議論のための既定値で、誤差モデルから導いたものではない
対照群比較はスキルあり・なしのみ。スキルの「内容」の効果と、「指示が 1 つ増えたこと」の効果を分けていない
統計区間Wilson 区間やブートストラップ区間は、その 1 回の構成（データセット、エージェント、モデル、環境）の範囲を述べるだけで、汎化の主張にはならない

総合スコアのうち Correctness と Effectiveness の 2 次元（およそ 5 分の 2）が LLM ジャッジのばらつきを含みます。決定的なチェックも、エージェント自体が確率的に動くため、再実行すれば値は動きます。

データセットの十分性

各結果には dataset_sufficiency が付き、次の 3 条件をすべて満たすと sufficient、そうでなければ provisional と表示されます。この表示は判定、スコア、終了コードを変えません。

  • 否定ケースを 1 件以上含む 10 件以上のケース
  • 合格率の 95% Wilson 区間の半幅が 0.20 以下
  • 両系統で採点されたケースが 10 件以上
文書の例：「この 20 ケースで、このエージェントとモデルでは、スキルありの総合スコアが共通の基準で 0.21 高く、ブートストラップ区間は 0 を含まなかった」は妥当な読み方。「このスキルはエージェントの性能を 21% 上げる」は妥当でない。--n-attempts 1 で数ケースの実行は、ベンチマークではなく動作確認として扱うよう書かれています。

10 — 導入と実行

A. キーなしで品質を見る

pip install skillevaluator          # または: uv tool install --python 3.13 skillevaluator

API キー、スキャナー、GPU、Docker のいずれも不要です。100 点満点のスコア、評価、指摘が出ます。これは静的な品質だけで、公開用の証拠（publication evidence）は INCOMPLETE のままです。手元にスキルがなければ、リポジトリ同梱の src/skillevaluator/tier3/reference_skills/text-analyzer を使えます。

B. 3 つの Tier をすべて実行する

11 — CI とエージェントから使う

CI のゲート

文書が推奨するキー不要のゲートは次のとおりです。終了コードで合否が決まるため、出力を解析する必要はありません。

skillevaluator validate ./skills --profile default --tiers 1 \
  -r json,markdown,sarif -o reports --min-score 70

JSON は機械処理用、Markdown は PR コメント用、SARIF は GitHub Code Scanning 用です。skillevaluator ci init を使うと、Tier 1 を必須ゲート、Tier 2 と Tier 3 を独立した参考チェックとする設定の PR が作られます。.pre-commit-hooks.yaml には、キー・ネットワーク・Docker なしで動く pre-commit フック（skillevaluator-quality、skillevaluator-schema、skillevaluator-lint-scripts）もあります（1.0.0 で追加）。

CI テンプレート

CLI を使わずに設定する場合は、ci/bundles/1.0.1/ の記入済みテンプレートをコピーします。README によると、テンプレートは 11 種類の CI チェック（quality、schema、version、PII、license、Unicode、script linting、Harness Check、security、code integrity、dependency auditing）を扱い、モデルのキーは不要です。ただし dependency auditing は validate の既定のチェックには含まれず、脆弱性情報のサービスに接続してパッケージのメタデータを送ることがあります（docs/github-actions.mdx）。

12 — 注意点

サポートは Experimental

README はサポートレベルを Experimental とし、コミュニティによるベストエフォートで SLA や NVIDIA のエンタープライズサポートはないと明記しています。不具合は GitHub Issues、脆弱性は SECURITY.md の非公開の手順で報告します。

PyPI 版と main の差

本ページは main の文書をもとにしています。v1.0.1 のタグ以降、main には次のような未リリースの変更があります。

  • Tier 3 のセキュリティ採点が、eval、env -S、git grep -O のページャーを通して実行される rm や、"rm" -rf /workspace のように引用符付きで書かれた rm も破壊的なコマンドとして検出する（CHANGELOG では 1.0.1 の欄に書かれているが、コミットはタグより後）
  • Tier 3 で、実行記録の任意項目 final_metrics が壊れていても、結果の収集全体を中断せずに使用量を「不明」とする
  • GitHub の全 Tier CI で、環境のシークレットを使いつつデプロイメントの記録を作らない設定（environment-deployment: false）ができる。既定は従来どおり記録する

0.9.0 から上げる場合は、02 節の影響する変更を先に確認します。

データの送信と料金

  • Tier 1 の LLM 検査、Tier 2、Tier 3 の採点とデータセット生成は、スキルの本文や実行記録を設定したプロバイダーに送ります。社外に出せないスキルでは、送信先のモデルを先に決めておく必要があります。
  • Tier 3 はエージェントとジャッジの両方でモデルを呼ぶため、料金がかかります。マネージドのサンドボックスを使う場合はその費用も発生します。
  • validate を --tiers なしで実行すると、データセットがなくても autopilot が 1 件のスターターケースを作って Tier 3 まで進みます。1 件のケースは動作確認であり、性能の評価にはなりません。

スコアの扱い

  • Tier 1 の品質スコアは静的な文章・構造の評価で、スキルがエージェントの役に立つかは示しません。効果を見るのは Tier 3 です。
  • Tier 3 の結果は、1 つのスキル・データセット・エージェント・モデル・環境の 1 回の測定です。08 節の限界を踏まえて読みます。

その他

  • このプロジェクトは追加のサードパーティ製 OSS（スキャナー、Harbor、エージェント CLI など）をダウンロード・インストールします。README は利用前にそれぞれのライセンスを確認するよう求めています。
  • 研究成果として論文（arXiv:2608.20614）と NVIDIA Developer のブログ記事が出ています。引用する場合はリリースかコミットも記録するよう CITATION.cff で求めています。
