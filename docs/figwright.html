Figma プラグイン経由でデザインを読み書きする、無料の双方向 Figma MCP サーバー

awdr74100/figwright · @figwright/mcp v0.7.0 · 2026-11-02 時点の main · MIT

概要

Figwright は、MCP サーバー @figwright/mcp と Figma プラグインを、ローカルの WebSocket でつなぐツールです。Claude Code、Cursor、Codex などの MCP クライアントから、Figma のデザインを読んでコードにすることも、コードや仕様から Figma のキャンバスに直接デザインを組むこともできます。

Figma 公式の Dev Mode MCP は有料の Dev Mode シートが必要です。Figwright は Plugin API を使うので、Figma の無料プランで動きます（プラグインの読み込みにはデスクトップアプリが要ります）。サーバー、リレー、プラグインはすべて手元のマシンで動き、デザインデータを外部へ送りません。

読む方向と書く方向

Read Figma → コード

Figma で選択したフレームを、プロジェクトのスタックに合わせたコードにします。レイアウト、タイポグラフィ、変数、コンポーネントを重複を除いた形で取り出し、スクリーンショットからの推測に頼りません。

依頼の例: 「この Figma の選択範囲を React コンポーネントにして」

Write コード・仕様 → Figma

フレームやテキストから、オートレイアウト、スタイル、変数、コンポーネント、画面全体まで、キャンバスを直接作成・編集します。ファイルにある既存のコンポーネントと変数を優先して使います。

依頼の例: 「この仕様から料金セクションを Figma に作って」

どちらの方向も、固定のコンパイラで変換するのではなく、ツールが正確なデザイン情報を返し、モデルがそれをもとに利用者のコードベースや Figma ファイルに合わせて生成します。リポジトリではこの方針を provider-first と呼んでいます。

構成

MCP クライアントは @figwright/mcp を起動し、stdio で通信します。サーバーはツール呼び出しをローカルの WebSocket で Figma プラグインへ中継し、プラグインが Figma の Plugin API で実行します。エージェントごとにサーバープロセスが 1 つ起動し、プロセス同士でリーダーを 1 つ選びます。

リーダーが止まっているのにポートを握ったまま応答しない場合（ターミナルで Ctrl-Z した、デバッガで止めたなど）、フォロワーは約 12 秒で異常と判断し、待ち続けずに即座にエラーを返します。リーダーはポートを取った時点で $TMPDIR/figwright/leader-3055.json に PID などを書き残します。フォロワーはプロセス表と突き合わせて本人だと確かめてから PID を名指しし、停止状態なら SIGCONT を送って復帰を試みます。Windows ではこの特定と復帰は行わず、汎用のメッセージだけを出します。

セットアップ

必要なもの: MCP クライアント、Node.js 20.19 以上または 22.12 以上、Figma。サーバーは npx で独立したプロセスとして動くので、プロジェクトのビルドに使う Node のバージョンとは無関係です。Node 18、21、22.0〜22.11 は対象外です。

  1. MCP クライアントにサーバーを登録するClaude Code なら .mcp.json に追加します。ほかのクライアントも同じ形です。グローバルインストールは不要です。
    .mcp.json
    {
  "mcpServers": {
    "figwright": {
      "command": "npx",
      "args": ["-y", "@figwright/mcp@latest"]
    }
  }
}
  2. Figma プラグインを読み込むFigma Community にはまだ公開されていません。最新の GitHub Release からプラグインの zip を取得して展開し、Figma デスクトップアプリで Menu → Plugins → Development → Import plugin from manifest… から manifest.json を選びます。
  3. 接続するFigma で Plugins → Development → Figwright を開くと、ローカルのサーバーに自動で接続し Connected と表示されます。エージェントに ping を実行させて確認します。
  4. スキルを入れる（任意）エージェントが適切な場面で Figwright を使い、決まった手順に沿うようになります。 
    npx skills add awdr74100/figwright/skills
  5. 試すFigma でフレームを選んだ状態で「この Figma の選択範囲を React コンポーネントにして」、または「この仕様から料金セクションを Figma に作って」と依頼します。

更新とバージョンずれ

リリースごとにサーバーとプラグインが一緒に出るので、両方を更新します。スキルは任意で、入れた方法で更新します。

  1. サーバーを再起動する@latest の設定なら起動のたびに最新版を取得するので、インストール作業はありません。ただし開いているセッションは起動時のサーバーを使い続けます。Claude Code では /mcp で figwright を選び Reconnect します。ほかのクライアントは再起動します。パッケージとして入れている場合は、先に npm i -D @figwright/mcp@latest（またはグローバルに -g）で更新します。
  2. プラグインを差し替える最新リリースの zip を展開し、manifest.json と dist を、最初に読み込んだフォルダへ上書きします。開発用プラグインはそのフォルダから直接動くので、再インポートは不要です。プラグインを閉じて開き直します。
  3. スキルを更新するnpx skills update を実行します。その後に始めたエージェントのセッションから新しい版が使われます。
サーバーとプラグインはずれるのが普通の状態です。 サーバーは npx @latest で毎回更新され、プラグインは手で入れた zip のまま残ります。古いプラグインは新しい引数を無視し、エラーを出さずに { ok: true } を返すので、書き込みが一部しか反映されないまま成功と報告されることがあります。プラグインが MIN_PLUGIN_VERSION（現在 0.7.0）より古いと、パネルのヘッダーに警告が出て、プラグインに届くツールの結果すべてに「未検証」の注記が付きます。パネルの Debug タブでサーバーとプラグインのバージョンを並べて確認できます。

古いプラグインの接続を拒否する方式も実装して試されましたが、拒否された古いプラグインが毎秒 7 回ほど再接続を繰り返したため取りやめています。現在は接続を拒否せず、結果に注記を付けて知らせる方式です。プロトコル自体を解釈できない場合（PROTOCOL_VERSION の不一致）だけは接続を拒否します。

グラウンディング

Figma のデータを利用者のコードベースと突き合わせるツール群。コード生成で既存のものを再利用するための土台です。design_diff は保存した基準からの変更点だけを返します。

get_design_contextcomponent_maptoken_mapicon_mapdesign_diff

ツールのほかに、MCP プロンプト figma_to_code と code_to_figma も登録されています。figma_to_code は読み取り結果のうち、コードへの対応が自明でないフィールドの読み方を説明します。batch は複数の編集を 1 回でまとめて適用し、途中で失敗したら巻き戻します。

figma-codegen（Figma → コード）

Figma の選択範囲を、プロジェクトの他の部分と同じ書き方のコードにするスキルです。既存のコンポーネントとトークンを再利用し、足りないものだけを新しく作ります。基本は「描画されたスクリーンショットより、グラウンディングツールの結果を信じる」です。

  1. get_design_context（detail full、dedupeComponents: true）構造ツリーを取得します。トークンは Primary/500 や spacing/4 のような名前に解決され、スタイルは globalVars に重複なくまとめられ、各インスタンスに mainComponent と componentProperties が付きます。レイアウトとバインディングはこれが正です。
  2. component_mapFigma のコンポーネントをローカルのコードコンポーネントに対応付け、high / medium / low / unmapped の状態を付けます。high と medium は candidate.filePath から import して再利用し、作り直しません。ambiguousWith が付いたものは候補が拮抗しているので、確認してから使います。コンポーネントにないプロパティ（unmatchedProps）は、その場しのぎのマークアップで埋めず、拡張の TODO として残します。
  3. token_mapFigma の変数（と単色のペイントスタイル）をプロジェクトのトークンに対応付けます。対応があれば生の hex や px ではなく candidate.ref（bg-primary-500、var(--color-primary-500) など）を使います。Tailwind や UnoCSS の標準スケールに当たるものは framework-builtin として p-4 のようなユーティリティにします。figmaModes を持つトークンはテーマで値が変わるので、プロジェクトのダークモードの仕組みに載せます。
  4. グラウンディングで運べない素材を書き出すロゴ、写真、アイコンは画素を持たないので、放っておくと灰色の箱になります。画像フィルは save_image_fills で元画像を、アイコンは先に icon_map で既存の SVG を探し、合成後の見た目が必要なときだけ get_screenshot を使います。

最後に、検出したスタックでコードを出力します。スタック情報は component_map と token_map の結果に含まれるので、analyze_project を別に呼ぶ必要はありません。

デザインの変更に追従する

生成後に design_diff→.figwright/snapshots/ に基準を保存→デザイン変更後に再度 design_diff→変わったノードのコードだけ直す

2 回目の design_diff は、ノード単位・プロパティ単位の差分（追加・削除・変更、解決済みの値、Card / Header / Title のようなパス）を返します。画面全体を作り直さず、該当するコードだけを編集します。基準ファイルをコミットすればチームで共有できます。ツール自身は git を操作しません。

figma-build（コード・仕様 → Figma）

figma-codegen の逆方向です。接続中の Figma ファイルのデザインシステムを再利用し、ハードコードした値で図形を描くことを避けます。URL からファイルを開く機能はないので、対象ファイルを Figma で開いておき、最初に ping で接続を確かめます。

  1. Figma ファイル側を読むget_variable_defs で変数、scan_components / get_local_components で既存コンポーネント、get_styles で共有スタイルを確認します。結果が空でもチームライブラリを使っているファイルなら、トークンはライブラリ側にあります。「トークンなし」と判断して値をハードコードしないでください。
  2. 元のコードを読むスタック（Tailwind、Chakra、MUI、CSS Modules など）と、設定・テーマ・トークンのファイルを確認します。値はそこから取ります。
  3. 組み立てる値の出どころは、既存のコンポーネント・変数・スタイル → 元コードの実際の値 → 一貫したスケール、の順です。create_instance でコンポーネントを配置し、色は bind_variable_to_paint、数値は bind_variable_to_node、共有スタイルは apply_style_to_node で結びます。関連する子要素はオートレイアウトにし、サイズは set_layout_props の HUG / FILL / FIXED で決めます。
  4. 見た目で確かめるget_screenshot で描画結果を見て直し、再度スクリーンショットを撮ります。元の意図との一致に加え、はみ出しやクリップ、端の揃い、余白のスケール、文字の階層も見ます。
新しく作った TEXT ノードの既定フォントは Inter です。 実際のフォントを指定します。コード由来の色は sRGB なので、Display P3 のファイルでは space: "SRGB" を付けて書きます。付けないとコードより彩度が高く塗られます。

新しいデザインシステムの要素（変数、スタイル、コンポーネントとバリアント）を作るのは、既存のものに相当するものがないときだけです。アニメーションを含むソースは、Figma の Motion（beta）として apply_animation_style や apply_manual_keyframe_track で付けます。少しずつずらして動く行は、timelineOffset を増やした apply_animation_style を 1 回の batch にまとめます。

複数エージェントと複数ファイル

複数の MCP サーバーが、リーダーとフォロワーに分かれて 1 つのプラグインを共有できます。さらに、各エージェントが自分のファイルを claim すれば、別々の Figma ファイルで同時に作業できます。

状況動作
claim していない呼び出しは、利用者が最後に操作したファイルに向かう。タブを切り替えると、エージェントが見るファイルも変わる。
複数ファイルが開いていて未 claimすべての結果に MORE THAN ONE FIGMA FILE IS OPEN の注記が付く。スキルはこれを見たら最初に claim するよう指示している。
list_filesプラグインが開いているファイルを一覧する。
use_file({ fileName })そのファイルをこのサーバープロセスに固定する。パネルを閉じて開き直しても、タブが裏にあっても届く。
同名のファイルが 2 つ名前での指定を拒否し、list_files が出す sessionId での指定を求める。
use_file({ release: true })claim を外し、前面のファイルに従う動作に戻す。
claim の単位は MCP クライアントのサーバープロセスです。 2 つのエージェントで別々のファイルを扱うなら、エディタを 2 つ、またはターミナルを 2 つ使います。1 つのクライアント内のサブエージェントは同じサーバーを共有するので、claim も共有されます。

プラグインとエディタ別の制限

Figma 側のパネルには 3 つのタブがあります。Activity はすべての呼び出しを所要時間付きで並べ、触ったノードへ移動できます。Payload はモデルが受け取った内容そのものを表示します。Debug は接続状態、バージョン、ワンクリックの診断バンドルを出します。パネルは Figma のライト・ダークテーマに追従し、右下をドラッグして大きさを変えられ、その大きさは次回も保たれます。ヘッダーの Run in background でパネルを隠しても接続は保たれます。その上の ✕ はプラグインごと閉じ、接続も切れます。

エディタ読み取り・書き出し書き込み補足
Figma Design可可すべての機能が使える。
Dev Mode可不可Figma がプラグインを読み取り専用にするため、ノード・ページ・変数・スタイルの書き込みはすべて失敗する。コード生成には向く。パネルのリサイズと Run in background もない。
FigJam一部一部フレーム、セクション、図形、テキストは使える。コンポーネント、変数、スタイル、Motion はこのエディタに存在しない。

get_metadata がエディタの種類（editorType / mode）を返し、エディタの制約で失敗したツールはエラーにその理由を書きます。エージェントは再試行せずに計画を変えられます。

セキュリティ

Figwright にクラウドサービスはなく、テレメトリも送りません。デザインデータが流れるのは、プラグイン、ローカルリレー、MCP クライアントの間だけです。

境界内容
待ち受けWebSocket は 127.0.0.1:3055 にだけ bind し、ネットワークからは届かない。
Host の検査ループバック（localhost、127.0.0.1、[::1]）以外を拒否する。ブラウザ経由の DNS リバインディングはここで止まる。
Origin の検査Origin がない（フォロワーかプラグインのホスト）か、プラグインの sandbox の Origin だけを通す。リーダーの HTTP エンドポイント（/rpc、/ping、/abdicate）は Origin 付きの要求をすべて拒否し、CORS プリフライトなしでは送れない media type を要求する。
Figma 側プラグインは公開の Plugin API だけを使い、開いているファイルにしか触れない。他のファイル、アカウント、組織のデータには届かない。
ファイル書き込み書き出し系ツールは、エージェントが渡したパスにだけ書く。
ファイル読み込みimport_image と set_image_fill は渡されたパスを読むが、先頭 8 バイトが PNG・JPEG・GIF でなければ拒否する。/rpc 経由の呼び出しではパスを解決しない。
エージェントの操作のレビューは省けません。 書き込みツールは Figma ファイルを変更し、書き出しツールはエージェントが選んだパスにファイルを書きます。悪意のあるデザインや、プロンプトインジェクションされた指示に従うエージェントは、どちらも誤用できます。最終的な境界は MCP クライアントのツール承認です。同じユーザー権限で動くマルウェアも防げません。

環境によってプラグインのホストが拒否される場合は FIGWRIGHT_ALLOW_ANY_ORIGIN=1 で Origin の検査を外せますが、Host の検査は外れません。SECURITY.md は設定したままにせず報告するよう求めています。脆弱性は GitHub の private vulnerability reporting で受け付け、セキュリティ修正の対象は最新リリースだけです。

起動トラブル

MCP クライアントはサーバーの command を対話シェルを通さずに直接起動します。fnm、nvm、asdf、volta、mise などシェルのフックで PATH を設定するバージョン管理ツールを使っていると、その設定が効きません。Figwright 固有ではなく、npx で起動する MCP サーバー全般に起きる問題です。

command not found（npx や node が見つからない）

通常のターミナルで which npx を実行し、その絶対パスを command に書きます。クライアントがサーバーごとの env に対応していれば、env.PATH にバージョン管理ツールの bin を足す方法もあります。

-32000 / Connection closed / いつまでも接続しない

npx … @latest は起動のたびにレジストリへ問い合わせます。直接起動された環境では npm の設定、社内プロキシ、プライベートレジストリが効かずに失敗することがあり、MCP のハンドシェイク前にプロセスが終わります。パッケージを入れて、起動時の問い合わせをなくします。

プロジェクトに入れる（@latest を外す）
pnpm add -D @figwright/mcp   # または npm i -D @figwright/mcp

# .mcp.json の args を ["-y", "@figwright/mcp"] にする
グローバルに入れてバイナリを直接指定する
npm i -g @figwright/mcp
which figwright-mcp
# .mcp.json の command に、出力された絶対パスを書く
プラグインが Waiting のまま接続しない
  • MCP クライアントが起動していて、Figwright が設定されているか（ping を試す）。サーバーはクライアントが開いている間しか動きません。
  • プラグインを同じマシンの Figma で開いているか。リレーは 127.0.0.1 限定です。
  • ファイアウォールやセキュリティツールがループバック接続を止めていないか。

開発者向け

パッケージ役割
packages/mcpnpm に公開する @figwright/mcp。リレー、リーダー選出、ツール、コードベースとの突き合わせ（join/）、スタック検出（profile/）、design_diff（diff/）、プロンプト。
packages/pluginFigma プラグイン。ui/ は Vue 3 + Vite + Tailwind v4 のパネル、src/ は Plugin API を実行する sandbox（ツールごとの handler）、protocol/ は両者が共有するパネル制御の取り決め。
packages/shared型、Zod スキーマ、msgpack のコーデック、プラグインとサーバーのプロトコル。ビルド時にサーバーへ同梱し、単独では公開しない。
skills/figma-codegen と figma-build。各 SKILL.md が入口で、詳細は references/ に分かれる。

Node 26、pnpm 12、TypeScript（strict）、tsdown、Vite、Vitest、oxlint、oxfmt、knip を使います。CI は typecheck、lint、format:check、knip、build、test を通すことを求め、Windows では build と test だけを別ジョブで実行します。

  • サーバーはソースではなくビルド済みの dist で動きます。 packages/mcp や packages/shared を変えたら pnpm build してサーバーを再起動します。dist を使う e2e テストは、dist がないと skip されます。
  • MCP SDK と Zod は実行時に各ツールの JSON Schema を生成するため、型検査が通っても公開スキーマが変わることがあります。mcp-wire.test.ts と json-schema-generation.test.ts がそれを検出します。
  • 既存ツールへの引数追加は、すでに入っている古いプラグインでは黙って捨てられます。test/plugin-contract.test.ts がプラグインへ届く引数の一覧を記録し、変化を検出して互換性の判断を促します。
  • コミットと PR は Conventional Commits で、scope は codegen、design、grounding、tools、relay、plugin、skills、deps、repo の 9 種類に限られます。

注意点

  • プラグインは Figma Community 未公開で、GitHub Release の zip を開発用プラグインとして読み込みます。読み込みにはデスクトップアプリが必要です。
  • 更新時はサーバーの再接続とプラグインの差し替えの両方が必要です。プラグインだけ古いと、書き込みが一部しか反映されないことがあります。結果に「未検証」の注記が出たら、プラグインを更新してください。
  • 複数ファイルを開いたまま claim せずに作業すると、タブの切り替えで読み書きの対象が変わります。use_file で固定してください。
  • Dev Mode では書き込みができません。デザインを組むときは Design モードで開きます。
  • ツールの中身が正しくても、エージェントの判断は誤り得ます。書き込みと書き出しは MCP クライアントのツール承認で確認してください。
  • バージョンは 0.x で、v0.7.0 時点でも描画の忠実度に関わる修正が続いています。
