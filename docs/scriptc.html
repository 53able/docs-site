1 — 概要
scriptc とは

scriptc は、TypeScript と JavaScript をネイティブ実行ファイルと WebAssembly へ変換する実験的なコンパイラです。TypeScript コンパイラが検査した型を使って機械語を生成し、出力は Node.js がなくても動きます。専用アノテーションや言語拡張は不要で、型検査の厳しさはプロジェクトの tsconfig.json に従います。

プログラムが import する npm パッケージも、自分のコードと一緒にネイティブコードへコンパイルされます。コンパイルできない箇所はビルド時に診断コードとソース位置、多くの場合は書き換えの手掛かりを示して報告します。

対応しているのは JavaScript、TypeScript、Node.js API のサブセットです。既存プログラムがどこまでコンパイルできるかは scriptc coverage で確認します。

2 — 静的・動的ティア・ブロッカーの境界
TIER 01

静的コード

型が静的に決まるコードです。チェック済みの型と絞り込みから値ごとのネイティブ表現を選び、そのまま機械語へ変換します。

TIER 02

動的ティア

any、型なしの JSON.parse の結果、型のない JavaScript を扱う関数です。これもネイティブコードですが、型検査とプロパティ探索を実行時に行うため静的コードより遅くなります。

TIER 03

ブロッカー

ネイティブ表現がない構文や API です。アプリケーションコードでは SC 付きの診断でビルドを止めます。npm パッケージ内では、実行されたときだけ例外を投げるコードとしてコンパイルされます。

0.3 で --dynamic は削除されました。 0.2 までは QuickJS を実行ファイルに埋め込み、コンパイルできないコードを JavaScript として動かしていました。現在はアプリケーションとパッケージのコードをすべてネイティブコードにします。QuickJS 由来のコードは、ビルド時の comptime 評価器と、正規表現・Unicode ライブラリとしてだけ残っています。
実行時の型チェック: 型が実行時にしか分からない値は、特定の型として使う前に検査します。たとえば JSON.parse(...) as Config は、形が合わなければ expected number at $.port, got string のようなエラーを投げます。Node.js では同じ as は何も検査しません。

段階処理内容
フロントエンドTypeScript 7 API サーバーの tsc-ts（既定。tsgo も選択可）が別プロセスで型検査します。チェック済みの型と絞り込み情報を使って対応する操作を lower し、未対応の操作は診断にします。入力が変わらなければ結果をビルドキャッシュから再利用します。
型付き IRフロントエンドとバックエンドをつなぐ検証済みの中間表現です。ジェネリクスは特殊化、Union はタグ付き値、クロージャは捕捉変数を明示した形になります。
LLVM backendLLVM IR のサイズに応じて最大 64 のパーティションに分け、並列に最適化・コンパイルします。release / speed ではパーティション間で小さな関数を import し、境界をまたいだインライン化を保ちます。再ビルドでは変更のあったパーティションだけをコンパイルします。
リンクコンパイル済み C ランタイムを含むランタイムパックから、機能・最適化モードに必要な成果物をハッシュ付きマニフェストで選び、ターゲットのリンカと SDK / sysroot で出力します。

packages/compiler

フロントエンド、型付き IR、検証、直列化、LLVM バックエンド、ネイティブ helper との連携、coverage 分析を担当します。

packages/runtime

参照カウントと循環回収、fiber とコルーチン、イベントループ（kqueue / epoll）、mbedTLS ベースのネットワーク、Node.js API の実装を C で提供します。ターゲット別のパックは packages/runtime-* にあります。

native/llvm-codegen

検証、最適化、アセンブリ・オブジェクト出力を行う LLVM 22 helper です。CLI は packages/cli にあります。

4 — 出力ターゲット
出力ターゲット条件・制約
実行ファイルmacOS（arm64 / x64、14.0 以上）、Linux（arm64 / x64、glibc 2.34 以上または musl）、Windows（x64）ホスト向けはそのままビルドできます。別ターゲットは SCRIPTC_TARGET を指定し、zig と @scriptc/runtime-<target> パックを追加します。
WebAssemblyWASI Preview 1（wasm32-wasi）単体で動く .wasm と、Web やネイティブアプリから呼ぶ reactor（--lib）を作れます。ソケット、子プロセス、シグナル、fs.watch は使えません。
静的ライブラリiOS（実機 / シミュレータ、15.0 以上）、Android（arm64、API 26 以上）scriptc build --lib --profile で .lib.a を作り、Xcode や Android NDK でアプリにリンクします。async、Promise、タイマーは使えません。
コンパイラ自体が動くホスト: macOS 15 以上（arm64 / x64）、Linux（arm64 / x64、glibc 2.34 以上または musl）、Windows x64。npm のほか、GitHub Releases の単体アーカイブでも配布されています。
5 — どこまでコンパイルするか
領域代表的な対応補足
言語クラスと継承、クロージャ、ジェネリクス、判別可能な Union、分割代入、スプレッド、async / await、例外、イテレータ、リソース破棄、JSX（react / react-jsx）JavaScript は // @ts-check や checkJs があれば JSDoc の型を使います。
標準ライブラリString、BigInt、Array、Map、Set、JSON、Math、TypedArray、Buffer、正規表現、Datees2025 の標準ライブラリに対して型検査します。
Node APIfs、path、process、child_process、crypto（WebCrypto 含む）、zlib、timers、net、http、https、http2、tls、dgram、dns、worker_threadsAPI ごとの対応状況は Node.js compatibility reference に一覧があります。
npm型宣言（同梱または @types/）があり、webpack バンドルでないパッケージ。CommonJS や minify 済みも対象Node.js の解決規則で探し、実行ファイルに組み込みます。実行時に node_modules は読みません。
拡張境界comptime、ネイティブ FFI（C ABI）、@scriptc/threads の publish、@scriptc/experimentalビルド時評価、C ライブラリ呼び出し、ワーカー間での不変データ共有をそれぞれ明示します。
6 — CLI の使い方
npm install -g scriptc

scriptc run hello.ts
scriptc build hello.ts -o hello
scriptc coverage hello.ts
SCRIPTC_TARGET=wasm32-wasi scriptc build hello.ts
6 つのサブコマンド
コマンド目的
scriptc build file.ts実行ファイル（WASI なら .wasm）を作る。--emit=ir|llvm|asm|obj で途中段階で止め、--lib --profile でライブラリを作る
scriptc run file.tsビルドしてそのまま実行する。引数は渡さないため、引数が必要なら build して直接実行する
scriptc coverage file.tsビルドせずに、静的にコンパイルできる文の割合、動的ティア、ブロッカー、Node との相違を報告する
scriptc typesnpm パッケージの誤った型宣言を直す型パッチを package.json に書く・一覧する
scriptc cache warmコンパイル済みランタイムや TLS ライブラリを検証して読み込む
scriptc merge-profiles--profile-generate で集めたプロファイルを --profile-use 用にまとめる
前提: npm でのインストールには Node.js 24 以上が必要です。実行ファイルのビルドにはリンカとプラットフォームの SDK / sysroot が要ります（macOS は Xcode Command Line Tools の clang、glibc Linux は clang、Windows・musl Linux・クロスコンパイルは zig）。coverage と --emit=ir|llvm|asm|obj はコンパイラ単体で動きます。
7 — 正しさをどう確かめるか

Node との差分テスト

テストプログラムを Node.js とコンパイル済み実行ファイルの両方で動かし、標準出力、標準エラー、終了コードを比較します。サーバーは同じクライアントで両実装を検証し、数値の文字列化は Node.js の String(x) に対してファジングします。

メモリ安全性

同じテストを AddressSanitizer と終了時の参照カウント監査つきで再実行します。利用者も --sanitize で自分のビルドに同じ検査を入れられます。

Node との相違を報告

コンパイルできても挙動が変わりうる箇所は SC6xxx の警告として coverage と build が報告します。既知の相違は Limitations ページにまとまっています。

CI での止め方

scriptc coverage --fail-on=blockers でブロッカーがあれば終了コード 1 にできます。divergences や dynamic も指定でき、--print=diagnostics で JSON を出力します。

公式ドキュメントは、テストで確認できるのは試したケースだけで、Node.js との完全な互換性を保証するものではないとしています。
