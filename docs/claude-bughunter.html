01 — バグバウンティと外部レッドチーム向けのスキル集

SCOPE → RECON → HUNT → VALIDATE → CAPTURE → REPORT

スコープを先に確かめ、7 つの問いを通った発見だけを報告する。

Claude-BugHunter は、Claude Code に脆弱性調査の手順と知識を読み込ませるスキル集です。83 のスキル、15 のスラッシュコマンド、攻撃面を決定論的に整理するエンゲージメントエンジン（engine/）、ターミナルから使う cbh CLI で構成されます。対象は、書面で許可を得た資産（バグバウンティのスコープ内資産、ペネトレーションテストの契約範囲、CTF、自分のインフラ）に限られます。

スキルは名前で呼び出さず、テスト内容を自然文で書くと説明文が一致したものが読み込まれます。たとえば「このエンドポイントに ?url= パラメーターがある」と書けば hunt-ssrf だけが読み込まれます。

実案件で見つかった不足から

README は、バグバウンティ案件で「検証前に報告を書く」「プログラムごとの重大度の付け方を知らない」「証拠のスクリーンショットに Cookie や他人の個人情報が写る」といった不足が見つかり、レッドチーム案件では SOC による途中の修正に気づけない、エンタープライズ製品の攻撃チェーンを知らない、といった不足が見つかったと説明しています。各スキルはこれらを埋めるために追加されました。

数字の定義

681 と 433 の違い

README の見出しにある 681 は、公開された HackerOne 報告から整理したパターンの数です。433 は、そのうち報告の URL を個別に引用し、verify_citations.py で内容の一致を確認した件数です。CHANGELOG によると、裏付けのなかった件数は下方修正されています（例: hunt-source-leak 31→7）。

02 — 対象範囲：外部から届く攻撃面だけ

このスキル集は、内部の端末を侵害しなくてもインターネットから到達できる範囲を扱います。境界を越えた後の作業は、意図的に対象外です。

対象外部レッドチームの初期侵入：M365 / Entra ID、Okta、SharePoint オンプレミス、VMware vCenter、SSL VPN 機器、Android / iOS アプリ、サプライチェーンの偵察

境界の扱い：影響を示すためにスコープ外へ出る必要がある場合、検証ゲートは「さらに攻撃して証明する」ではなく DOWNGRADE か CHAIN-REQUIRED を返す設計です。ドメイン管理者級の目標に届いた場合も、チェーンは「認証情報を発見し、アクセスを確認した」時点で終わり、内部向けの専用ツールへ引き渡します。

03 — スキルの構成：4 つの層

README は 83 のスキルを、考え方・Web アプリの調査・境界の攻撃・報告の 4 層で説明しています。

THINK

方法論と心構え

bb-methodology の非線形な 5 フェーズの作業手順と、redteam-mindset のオペレーターとしての規律。防御側の脆弱性診断の感覚で早く手を止めてしまう癖を補正します。

HUNT WEBAPPS

脆弱性クラスごとの hunt-*

XSS、SQLi、SSRF、IDOR、LFI、SSTI、OAuth、GraphQL などのクラス別と、Next.js、Spring Boot、Laravel などのフレームワーク別のスキル。検出パターン、回避の表、チェーンの型を持ちます。

HIT THE PERIMETER

エンタープライズ製品の攻撃チェーン

M365 / Entra、Okta、クラウド IAM、vCenter、SSL VPN、APK / iOS、サプライチェーン偵察。2024〜2026 年の CVE チェーンと、認証情報を得た後の権限昇格の考え方をまとめています。

SHIP IT

検証・証跡・報告

triage-validation の 7-Question Gate、evidence-hygiene による Cookie と個人情報の伏せ字、Bugcrowd の VRT に沿った重大度、レッドチームの顧客向け報告書（MD + DOCX）。

04 — 6 フェーズの作業の流れ

作業は 6 フェーズに分かれ、左から右へ進みます。途中のフェーズから始めることもできます。Validate の結果は 4 つに分岐します。

フェーズと主なスキル（docs/architecture.md より）
フェーズ使う場面主なスキル・コマンド
1 Scopeプログラムの受付、スコープの整理bug-bounty、bb-methodology、osint-methodology、hunt <name>（作業フォルダーの作成）
2 Recon資産の列挙、サブドメイン、秘密情報、ID 基盤の把握offensive-osint、recon-scope-triage、web2-recon
3 Hunt脆弱性クラスごとのテストhunt-* 58、エンタープライズ製品の 8 スキル、security-arsenal、web3-audit
4 Validate報告を書く前の判定triage-validation、/triage、/validate
5 Captureスクリーンショットや HAR を添付する前evidence-hygiene（Cookie の伏せ字、他人の個人情報の黒塗り、HAR の整理）
6 Report最終報告の作成report-writing（CVSS 3.1 / 4.0）、bugcrowd-reporting、redteam-report-template

redteam-mindset と mid-engagement-ir-detection はフェーズをまたいで使います。後者は、テスト中に SOC が修正を入れた、別の攻撃者が動いている、といった変化を検知し、報告書の所見に変える手順です。

05 — 7-Question Gate：報告前の判定

triage-validation は、報告を書く前に次の 7 問を確認させます。1 つでも「いいえ」なら KILL です。

  1. 攻撃者が実際の HTTP リクエストで、今すぐ使えるか。
  2. 影響が、プログラムが受け付ける影響の一覧に入っているか。
  3. 資産がスコープ内か。
  4. 攻撃者が得られない特権アクセスなしで成立するか。
  5. 既知の挙動や、文書化された仕様ではないか。
  6. 「技術的には可能」以上の影響を示せるか。
  7. 提出しない一覧（self-XSS、セキュリティヘッダーの欠如だけ、など）に入っていないか。
判定の結果
結果意味
PASS7 問すべてに証拠付きで答えられた。報告へ進む。
KILL報告を書かない。提出しない一覧に該当した場合も KILL。
CHAIN-REQUIRED単体では影響が足りない。別の脆弱性と組み合わせる（/chain）。
DOWNGRADE重大度か重複の問いだけで落ちた。重大度の主張を下げて続ける。

README は、この判定を「生産的な研究者とノイズを分ける規律」と位置づけています。無効な提出はプラットフォーム上の有効率を下げるため、報告の前に止めることが目的です。

engine/ は自律的にテストするロボットではなく、判断を支える道具として作られています。既定の実行は、攻撃面を決定論的に整理し、どこにどの hunt-* スキルを当てるかの「地図」（arsenal.md）を出して止まります。エージェントを使った調査は --hunt を付けたときだけ動きます。

  • rank
  • map（既定はここまで）
  • hunt（--hunt）
  • validate
  • report
engine/README.md の構成表より

recon.py技術スタックの判定、JS バンドルからのエンドポイント抽出、JS 内の秘密情報の検出（伏せ字で記録）、gau と katana による入力パラメーターの収集。LLM は使わない。
skill_map.py各エンドポイント・パラメーターと脆弱性クラスの組を、実際にインストールされている hunt-* スキルと、最初に試す curl に対応付ける。

READ-ONLY

既定は読み取りのみ

調査と検証のエージェントには、スコープ内のホストだけを扱い、メール送信・書き込み・削除・露出した認証情報の使用など状態を変える操作をしないよう指示します。--allow-intrusive を付けたときだけ解除されます。

SCOPE AUDIT

PoC のスコープ外ホストを検出

確認済みの発見ごとに、PoC にスコープ外のホストが含まれていないかを決定論的に確認し、含まれていれば報告書に警告を付けます。

SEVERITY

検証側の重大度を採用

保存される重大度は、調査エージェントの推定ではなく、反対の立場で確認する検証エージェントが付けたものです。

# 既定：決定論的な地図だけ（エージェントなし）
python3 engine/engine.py --scope my-engagement.json

# 地図にもとづいてエージェントで調査（読み取りのみ、並列 3、最大 12 件）
python3 engine/engine.py --scope my-engagement.json --hunt --parallel 3 --max-hunts 12

# 実際の出力を使わずに配線だけ確認
python3 engine/engine.py --scope engine/engagement.example.json --base /tmp/eng --mock --hunt

サブドメインや資産の列挙（OSINT）はエンジンの外にあり、姉妹プロジェクトの Claude-OSINT が担当します。エンジンはスコープ内の起点ホストから偵察を始めます。

08 — cbh CLI：ターミナルから使う決定論的な実行役

cbh は補助的なインターフェイスです。会話の中で判断を伴う調査をするときはスラッシュコマンドを使い、CI や定期実行、ラボでの再現など、毎回同じ出力が欲しいときに cbh を使います。どちらも同じ skills/ と docs/disclosed-reports/ を参照します。

docs/cbh-cli.md「The five subcommands」より
サブコマンド内容
cbh recon <target>証明書の透明性ログ（crt.sh）と subfinder でサブドメインを集め、DNS を解決し、生存ホストのステータスとヘッダー、タイトルを取得する。偵察から調査への受け渡し用に manifest.json を出力する。
cbh surface <target>マニフェストから攻撃面を P1 / P2 / Kill に分ける（api・auth・admin は P1、静的ファイルや CDN は Kill）。
cbh classify <url>18 の URL パターンと、スキルの description のキーワードで、URL を hunt-* スキルに対応付ける。
cbh triage <finding.md>発見の記述に 7-Question Gate をキーワード照合で当て、PASS / DOWNGRADE / KILL を返す。証拠の記述がない問いは「未回答」扱い。
cbh report <finding.md>発見の frontmatter と見出しから、--platform で指定したプラットフォーム向けの下書きを作る。

HTTP は既定で Python 標準ライブラリから送ります。--burp を付けると Burp Suite のプロキシ経由になり、リクエストとレスポンスが Burp の履歴に残ります。会話の中から Burp を操作する場合は、Burp の MCP サーバーを Claude Code に登録します。

A. Claude Code プラグインとして導入する（推奨）

/plugin marketplace add elementalsouls/Claude-BugHunter

10 — 評価結果と注意点

スキルの効果は測定上ほぼゼロ

eval/BASELINE.md の最新の記録（2026-08-25、claude-opus-4-8、OWASP Juice Shop の 3 課題）では、スキルあり・なしのどちらも 3/3 を解き、スキルありのほうがターン数とコストが多くなりました。リポジトリ自身はこれを「よく知られた課題での天井効果」と説明し、スキルの価値を測るにはより新しい PortSwigger Web Security Academy のラボで測る必要があるが、まだ実施できていないと書いています。engine/README.md も「スキルは測定可能なタスクでほぼ能力を上げず、1 エージェントあたり 1.2〜1.5 万トークンを消費する」として、エンジンのエージェントはスキルを既定でオフにしています。3 課題の結果なので、効果の有無はまだ判断できません。

許可の確認は利用者に委ねられている

/hunt は、呼び出した時点で利用者が書面の許可を持っていると見なし、作業範囲記述書（SOW）を尋ねません。機微な顧客データを取り込まないためです。スコープは /scope と 7-Question Gate で確認しますが、許可そのものの有無はツールでは確認しません。許可のない対象に使うと、各国の不正アクセス関連法に触れます。

Anthropic の安全機構にかかる場合がある

README は、許可を得た作業でも Anthropic のサイバー関連の安全機構で応答が拒否されることがあり、正当な攻撃的セキュリティの作業には Cyber Verification Program（CVP）への申請が案内されていると説明しています。また、一部の高リスクな依頼では応答するモデルが自動で切り替わることがあり、長いエージェント実行では気づきにくいと注意しています。防御目的の作業に見せかけて回避するのではなく、CVP に申請するよう明記しています。

サードパーティのスキルとして検証してから入れる

83 の SKILL.md とシェル・Python の補助スクリプトがエージェントの文脈に入ります。SECURITY.md は、公開スキルにプロンプトインジェクションが含まれる例があるとして、リリースのタグやコミットに固定してから導入することを勧めています。リポジトリ側では、PR ごとに scripts/lint_skills.py で構造の検査と秘密情報・顧客識別子の混入検査を行い、インストーラーはネットワークに接続しません。

その他

  • README の冒頭にある実行例は説明用の架空のトランスクリプトです。
  • ライセンスは 2 つに分かれます。*.py・*.sh などのコードは MIT、*.md の手順・ワードリスト・重大度の基準などは CC BY 4.0 で、再利用時には作者名とリポジトリへのリンクが必要です。
  • offensive-osint と osint-methodology は Claude-OSINT と同一内容で、両方入れても、片方のアンインストールでもう片方が壊れないようインストーラーが管理します。
